# 命令FIFOの比較実験と公式ソース更新（2026年10月8日）

> 実験開始時の計画。実施済みの結果と残る制限は [結果と判断](結果と判断.md) を参照。

## 調べること

今回の問いは、「WallyからRasterIXへ命令を渡す際に、何語もためられるFIFOを使うと、どの程度の利点と費用があるか」である。

RasterIXが受け取りを止めたとき、APBの書き込みを待たせることはできる。そのため、「相手が止まることがある」という事実だけでは、何語もためられるFIFOを選んだ理由にはならない。FIFOを使わない接続も作り、同じ処理を実行して比べる。

## 比較する三つの回路

| 接続方法 | CPUの書き込みが完了する条件 | CPUの次の命令をためる場所 |
|---|---|---|
| 1語ずつ受け渡す接続 | RasterIXがその語を受け取ったと通知されること | なし。処理中の1語を保持するレジスタはある |
| 16語の非同期FIFO | FIFOにその語を格納できること | 最大16語分のFIFO |
| 512語の非同期FIFO | FIFOにその語を格納できること | 最大512語分のFIFO。これまでの構成 |

1語は32ビットである。実際の接続では、命令列の末尾を示す1ビットも一緒に渡す。

1語ずつ受け渡す接続は、要求を相手のクロックに同期させ、相手が受け取ったという通知をCPU側のクロックへ戻す。通知が戻るまではAPBの書き込みを終わらせない。通知を取り消したことも確認してから次の語へ進む。この確認手順にも時間がかかる。

したがって、この接続が遅かったとしても、「FIFOを使わない接続はすべて遅い」「FIFOなしでは正しく動かせない」とは結論しない。比較対象は、今回実装した具体的な接続方法である。

また、20 MHzと100 MHzという周波数の違いだけから、両方のクロックが無関係だとはいえない。実際の生成回路とタイミング制約を調べる必要がある。今回の比較は、安全にクロック間を渡す回路として、待ち合わせ方式と既存の非同期FIFOを比較するものであり、非同期FIFOしか使えないことを示す実験ではない。

## 条件をそろえる

CPUは20 MHz、RasterIXは100 MHz、表示は640×480画素とする。公式のWallyとRasterIXは同じ版を使い、三つの接続方法でゲームの実行ファイルを共通にする。

変更するのはCPUからRasterIXへの命令経路である。RasterIXからCPUへの応答FIFO、DDRメモリとの接続、表示回路、ゲーム入力は変えない。

比較用の三つの回路には、同じ計測用カウンタを追加する。カウンタ付き回路と、通常のリポジトリの回路は区別する。計測用の変更はリポジトリへ入れない。

## 何を測るか

| 測るもの | 分かること | それだけでは分からないこと |
|---|---|---|
| 完了した画面切り替えの回数／秒 | ゲームが表示回路へ何回画面を渡し終えたか | キャプチャ動画に何枚の異なる画面が映ったか |
| 命令書き込みでAPBを待たせたクロック数 | 実際にCPU側の命令経路へ待ちが返った量 | RasterIX内部のどの処理が待ちの原因だったか |
| 1回の連続した待ちの最大長 | 短い平均値に隠れた長い停止があるか | すべての入力に対する最大停止時間 |
| 命令を書き込む処理にかかった時間 | CPUのループ・バス書き込み・待ちを含む転送処理の負担 | RasterIXだけの処理時間 |
| LUT、レジスタ、BRAMの使用量 | 接続方法に必要な回路の大きさ | その回路を使う意義の有無 |
| 画面全体の読み戻し比較 | 今回調べた画面の画素が正しいか | 任意のゲーム・任意の入力で正しいこと |

APBを待たせた時間は、CPUの周波数から推測せず、FPGA内で実際に待ったクロック数を数える。20 MHzでは1クロックが50 nsである。例えば20,000クロックの待ちなら合計1 msになる。この例の数値は換算方法の説明であり、測定結果ではない。

「命令の準備」「命令の転送」「画面切り替え完了待ち」は区別する。内部処理の時間は外側の処理時間にも含まれるため、そのまま足して二重計上しない。

## ゲームの条件

ブロック崩しの開始位置を、0、1,800、3,600回のゲーム更新後に固定する。そこから30フレームの準備運転をし、180フレームを測る。計測終了時の残りブロック数はそれぞれ38、21、6である。

それぞれについて、毎回全体を描く方式、同じ設定で描ける図形をまとめる方式、変わった領域だけ描き直す方式を比較する。接続方法による差が、特定の描き方だけに限られるかを確認するためである。

各条件を3回繰り返す。ただし、同じ起動中に繰り返した試験であり、3回の電源投入試験ではない。描画方式を試す順番は繰り返しごとに変える。

別に、事前に作った同じ描画命令列を繰り返し送る試験も行う。これは命令を準備する時間の影響を小さくして、命令転送・描画・表示待ちの経路を調べるためである。通常のゲーム速度とは分けて扱う。

## 正しく比較できたか

各フレームのゲーム状態と命令転送量を保存する。接続方法を変えたときにゲーム状態や転送量まで変わっていれば、公平な比較になっていない可能性がある。

画面の正しさは、最終画面の307,200画素すべてを読み戻し、CPU側の簡単な描画処理で作った正解画像と比較する。画素が一致しない試験は、性能の比較に採用しない。この正解画像はRasterIXの描画処理を使わずに作る。ただし、ゲーム状態の計算自体は共通であり、ゲームのすべての仕様を独立に証明しているわけではない。

FPGAに書き込む前には、配線後のタイミング、配線の完了、設計規則違反、クロック間の接続に関する報告を確認する。ビットストリームが生成できたことだけを、正しく動く根拠にはしない。

## 追加する検証

- 公式RasterIXの単体テスト50件。
- Wallyの命令テスト50件と、更新された例外・メモリ処理に関係する3件、周辺機器の5件。
- APB接続と表示回路の既存シミュレーション。
- 相手がしばらく受け取らない状況、ランダムな受け取り停止、転送途中のリセットを入れた接続回路のシミュレーション。
- 32×32、64×64、256×256画素の2D画像を転送して表示する試験。RasterIX更新で変更されたテクスチャの経路を確認する。
- 通常のブロック崩しを継続して実行し、可能な限りWindows側の映像取り込みも確認する。

映像取り込みに失敗した場合は、メモリ上の画像確認と、外部端子を通した映像確認を区別して記録する。
