## 今回の比較で答える問い

「FIFOなしでは接続できないか」ではなく、「安全に接続できる別の方式と比べ、複数語をためることにどれくらいの効果と回路の費用があるか」を調べる。

相手が受け取りを止めたらAPBを待たせる、というユーザーの案も比較対象に含めた。具体的には、1語を保持し、相手が受け取ったという通知が戻るまで書き込みを完了させない回路を作った。この回路にもクロック間の通知に時間がかかる。今回の結果で、FIFOを使わないすべての接続方法の優劣までは決まらない。

比較するのは、この1語ずつの接続、16語FIFO、512語FIFOの三つである。実験用の回路と計測用カウンタは、製品のリポジトリから分離している。

## 更新後に見つけた設定の食い違い

最初のブロック崩しの実機チェックでは、307,200画素中519画素が正解画像と一致しなかった。全体描画、図形の呼び出しをまとめる描画、部分描画の三つで、同じ最終画像になった。文字の一部が欠けていた。

公式更新を確認すると、回路の `TEXTURE_PAGE_SIZE` の既定値は4,096バイトから2,048バイトに変わっていた。一方、ソフトウェアの既定値は4,096バイトのままだった。回路とソフトウェアが画像データを同じ区切り方で扱えるよう、Wally側のサンプルのCMake設定に2,048バイトを明記した。回路と公式RasterIX本体は、この修正のためには変更していない。

修正前後のCMakeキャッシュを比較し、RasterIXの構成項目の差がページサイズだけであることを確認した。修正後、同じ16語FIFO回路で全307,200画素が一致した。以降の90回の比較には同じ修正済み実行ファイルを用いた。

また、新しく追加したテクスチャ単体試験には、描画色を白に指定する処理が抜けていた。これにより画像を黒くする可能性があったため、試験プログラムを修正した。この試験側の誤りを、RasterIXの不具合として数えない。

修正前の測定で出た速度は、画面の正しさを満たしていないため、FIFOの性能比較には採用しない。ログと実際の画素データは保存した。

## 人工的に受け取りを止めた場合

以下は実機ゲームの測定ではなく、接続回路だけのシミュレーションである。送信側を20 MHz、受け取り側を100 MHzとして3,000語を送った。受け取り側にはランダムな停止も入る。表の値は、模擬送信側が待たされたクロック数である。

| 送信に追加する間隔 | 最初に受け取りを止める時間 | 1語ずつの接続 | 16語FIFO | 512語FIFO |
|---|---:|---:|---:|---:|
| なし | 0 µs | 12,173 | 0 | 0 |
| なし | 10 µs | 12,394 | 153 | 0 |
| なし | 200 µs | 16,156 | 3,953 | 2,464 |
| 1 µs | 0 µs | 9,174 | 0 | 0 |
| 1 µs | 10 µs | 9,393 | 0 | 0 |
| 1 µs | 200 µs | 13,198 | 3,613 | 0 |

送信側の1クロックは50 nsである。例えば3,953クロックは197.65 µsに相当する。

この条件では、FIFOの容量が大きい方が待ちを吸収できた。送信間隔が空けば、同じ停止時間でも結果が変わった。一方、1語ずつの接続では、相手が受け取りを続けられる場合でも、各語の受け取り通知を待つ時間がある。

この表から「実際のWallyもこの速さで送る」「実際のゲーム中も200 µs停止する」とは言えない。それらは実機の計測カウンタとゲーム実行時間で別に調べる。

## 実機測定の前提となる回路の確認

CPUは20 MHz、RasterIXは100 MHz、表示は640×480画素のままとした。更新後は以前の配置条件のままでは配線が混雑したため、Vivadoの配置・配線条件を調べ直している。周波数を下げて結果を合わせたり、負のタイミング余裕を合格と扱ったりしない。

16語FIFO版は、配置・配線後のセットアップ余裕0.000 ns、ホールド余裕0.019 nsで条件を満たした。1語ずつの接続版も、セットアップ余裕0.003 ns、ホールド余裕0.011 nsで条件を満たした。どちらも大きな余裕があるわけではない。これらの数値はFPGAのタイミング解析の結果であり、ゲームの速さではない。
