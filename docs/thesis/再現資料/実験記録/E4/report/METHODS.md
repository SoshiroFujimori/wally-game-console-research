# 測定の条件と検証方法

この資料は解析方法を記述する。結果の合否や数値は`成果と検証範囲.md`と、それが参照するJSON・CSVを確認する。以前の640×480出力回路やDVI出力の測定値を、今回のHDMI出力の試行に混ぜない。

## 描画方法の比較

同一の測定プログラムv009に、毎回の全体描画、呼び出しの統合、変更領域の描画を選ぶ引数を設けた。ゲームの序盤・中盤・終盤に相当する状態から、固定した入力で状態を進める。各試行30フレームを準備に使い、その後180フレームを記録する。3方式×3場面×3反復の27試行である。方式によらず、測定する状態の順序と最終的な画素が一致することを検証する。

比較用プログラムは描画1フレームにつきゲームを1ステップ進める。開始状態の指定は0、1800、3600ステップで、その後に準備30フレームと測定180フレームが続く。完成版のゲームは実時間に合わせて毎秒60ステップ進め、描画が遅いときには必要なステップをまとめて処理する。このため、比較用プログラムと完成版の通常プレイは別の実験として示す。

この比較の待ち方はsleepに固定している。部分描画だけの効果と、待ち方を変えた効果を混同しないため、sleepと連続確認の比較は別に18試行を実施する。いずれも今回の同一bitstreamを使う。試行の順序は実行前に保存した`plans/controlled-finalhdmi.json`、`plans/wait-finalhdmi.json`に従う。待ち方の選択には過去のDVI出力構成での結果を使用し、今回の再測定は同じ結論がHDMI構成でも成立するかの確認として扱う。

各CSVの時間はCPUから観測する経過時間で、次の関係にある。

| 名称 | 計算・意味 |
|---|---|
| ゲーム処理 | `logic_ns`。位置や当たり判定など |
| 描画準備 | `api_ns + swap_ns - write_ns`。描画API・命令生成に含まれる転送時間を一度だけ除く |
| 転送 | `write_ns`。CPUが命令を送る経路で過ごした経過時間 |
| 完了待ち | `wait_ns`。描画先の切り替え完了を待つ時間 |
| 全体 | `total_ns`。測定フレーム全体の経過時間 |

転送時間にはCPU処理、バス、FIFO、描画回路の受け取り待ちが含まれ得る。これを「GPUの演算時間」と呼ばない。描画準備時間にもCPU命令実行やメモリの待ちが含まれるため、すべてを個別の命令・キャッシュミスに分解した測定ではない。

試行ごとの平均時間や完了数/秒を求め、その3試行の中央値を図表に使う。試行が反復の単位であり、隣接する180フレームを180回の独立実験として数えない。図の範囲は試行の最小～最大で、信頼区間ではない。95百分位は各試行の180フレームに線形補間を用いて計算し、その値の3試行中央値を示す。

## 画面が正しいことの検証

1. 各フレームのゲーム状態のハッシュ列を方式間で比較する。
2. 各試行の最後のRGB565画像について、307,200画素すべてを期待画像と比較する。
3. 実際のHDMI入力をOBSの内部APIで録画し、全フレームから左右の壁や欠落した行の候補を調べる。
4. 主要場面の画像を目視し、文字・色・ボール・壁・クリア・ゲームオーバーを確認する。

1と2はゲーム状態と最終描画の検査、3と4は映像出力経路の検査である。一方だけの成功で両方が成功したとは扱わない。全中間フレームの全画素を期待画像と照合した検査ではない。

通常ゲームとは別の記録用プログラムでは、経過時間、全ステップの状態、各画面切り替え完了を保存し、独立した再実行プログラムで状態列を確認する。計測コードの負担があるので、このプログラムの更新間隔と通常版の処理数は分ける。

状態の再実行はホスト上の別プログラムで行うが、ゲームの状態更新コード自体は製品と共有する。実機が同じ規則に従って状態を進めたことの検査であり、ゲームの規則を独立に二重実装した検証ではない。基準画像は、共通の図形・文字の定義を別のCPU側の塗りつぶし実装で描く。RasterIX経由の描画と画素を比較できるが、共通の定義に含まれる誤りは別途のゲーム処理の検査や目視と組み合わせて判断する。

## キャプチャ画像との比較

640×480のRGB565最終画像と、1920×1080の録画画像を比較する。FPGA側の3:2拡大とOBS側の1.5倍拡大を踏まえ、対応する画素を選ぶ。圧縮や補間の影響を受けやすい色の境界を1元画素分除き、内部画素の99.5%以上で各色チャンネルの差が30/255以下、という基準を最初の720pゲーム録画前に固定した。

この比較は非可逆圧縮を含む映像の検査である。RGB565の厳密な全画素一致とは異なる。細い文字などは内部画素の基準から除かれる場合があるため、目視と形の検査を併用する。基準を結果に合わせて緩めず、記録用プログラム1回と通常ゲームの6回の最終場面に同じ基準を適用する。

OBSの`outputTotalFrames`は録画ごとに再開始するため、前回の録画終了値を含む単純な前後差が0や負になる場合がある。生の記録を保持しつつ、録画フレーム数には動画を実際に全復号した数を使う。OBSの描画・符号化で落ちたフレームの記録も保存するが、これだけではキャプチャ機器の入力重複を数えられない。異なるボール位置の数も、そのままゲームのFPSには換算しない。

## 起動と連続動作

映像を一度認識できたという確認だけで終わらないよう、FPGAを書き込み直す6回の起動を試す。各回にCPU・UART・タイマーの20 MHz、DDR3容量、プログラムのハッシュ、SDのアンマウントを確認する。OBSのプロセスID・生成時刻・入力設定・配置は6回を通して変えない。これはFPGA再書き込みによる起動であり、物理的な電源抜き差しの試験ではない。

アプリだけの再起動は3回。以前の画像の帯が重なって残らないかを別に検査する。15分間の試行では自動操作に加えて75秒ごとの再開始を使い、途中で静止したままにならないようにする。録画の10～880秒を30秒ごとの29区間に分け、各区間の異なるボール位置が30以上、位置変化が40回以上であることを検査する。この870秒の区間検査に加え、録画全体の壁・行の異常候補と代表画像を確認する。

## HDMIの原因を分ける試験

HDMI方式とDVI方式を選べる診断回路を作り、同じbitstream・クロック・配置配線・キャプチャ設定で比較した。15秒の送信停止後に方式を選び、12秒後と20秒後の画像を取得した。事前に保存した8試行の順序はDVI、HDMI、DVI、HDMI、HDMI、DVI、HDMI、DVIである。診断回路はリポジトリ外に置き、製品のソースには加えない。

この試験から言えるのは、使用した受信機で新たに映像を認識する際に、HDMI固有の信号形式全体が影響したという範囲である。特定の情報パケットだけが原因、すべての受信機で同じ挙動、電気的なHDMI規格適合、という主張には使わない。過去の失敗録画は削除しない。

## 変更の追跡

最終ソースを一つの大きなコミットにする前提にはしていない。HDMI出力、起動処理、ゲーム、呼び出しの統合、変更領域の描画、完了待ちの6段階を、外部のパッチとして保存した。パッチの順適用・逆適用・最終ハッシュを検証する。ゲーム本体に測定専用コードを入れず、測定プログラム・解析・録画・SD操作は外部に置く。

コミットとステージングは保留する。測定の生データと過去の報告は変更せず、新しい成果資料を別ディレクトリに作る。パッケージのmanifestにはコピー元、バイト数、SHA-256を記録する。
