# 発表原稿を作るための引き継ぎ

目的は、Nexys Video上のWallyと公式RasterIXで2Dゲームを動かし、描画の準備にかかる負担を測って改善すること。対象はブロック崩し。CPUの回路と20 MHzの周波数は変えていない。

中間発表には、別保存の[CPUの命令準備を調べた実験](../../E5/results-ja.md)を使用できる。呼び出し回数と図形数を変えた比較から、CPUの命令準備の具体的な負担を説明する。その時点ではHDMIの正常映像を確認できていなかった記録を保持する。

最終発表には、今回の同一構成での27試行を使える。序盤では、毎回全体を描く方式から変更領域だけ描く方式への変更により、CPUの描画準備が53.57 msから6.57 ms、画面切り替え完了数が12.44回/秒から48.65回/秒になった。各値は3試行の中央値。途中の状態ハッシュ列と各試行の最終307,200画素を照合した。

完了の待ち方を18試行で別に比較し、完成版には連続確認を使用した。通常版の80秒自動プレイは、FPGAの再書き込みを伴う6回の起動すべてで400点・残り3のクリアを確認した。完了数の中央値は58.34回/秒。15分間の録画でも継続した動きを確認した。これらの完了数/秒は光学的なFPSではない。

HDMIは同一診断回路の8試行で、新規認識がHDMI方式4/4、DVI方式0/4だった。最終候補は公式HDMIコアを変更せず使用し、1280×720で出力する。640×480のゲームを縦横1.5倍にして左右に黒帯を設ける。WindowsのUIを操作せず、OBS内部APIからFPGA入力だけを取得した。

公式RasterIXは変更していない。変更は6段階のパッチに分けたが、コミット・ステージング・pushはしていない。より高度なCPUが必須、あらゆる処理のボトルネックを完全に特定した、すべての中間画素が一致する、という結論にはしない。Wiiコントローラーや人が遊んだときの操作感は未検証。
