# 白い四角形を一つ表示するまで

[分野別の入口](README.md) · [用語を調べる](glossary.md)

ここでは、横位置100、縦位置80、幅16、高さ16の白い四角形を描く例を使う。座標と寸法は説明用である。実物のボールの各フレームを再現したログではない。また、実装を無視して一つのバス書込みで四角形が完成するように説明しない。

<a id="sec-1"></a>
## 1 ゲームの変数には画像そのものは入っていない

ゲームが`x=100`、`y=80`という位置を持っているとする。これらはCPUが計算に使う数値である。横方向へ3進むと決めれば、次の位置は`100+3=103`になる。加算して位置を書き換えるだけでは、画像メモリの色はまだ変わらない。

ゲームの状態を決める仕事と、その状態を絵へ変える仕事を分けて考える。ボールが壁へ当たったかを調べるのは前者であり、ボールがある場所を白く塗るのは後者である。状態を同じにしたまま描画方式を比べる実験が可能なのは、この区別があるためである。

<a id="sec-2"></a>
## 2 描画関数へ図形の情報を渡す

四角形の境界を、左上`(100,80)`、右上`(116,80)`、右下`(116,96)`、左下`(100,96)`とする。色は白とする。ここで指定したのは、16×16個の色をCPUが一個ずつ並べたものではなく、図形を表す少数の値である。

実際のゲームでは、`BreakoutRenderer.hpp`が描画APIを呼ぶ。座標を受け取る側は、現在の色、座標の対応付け、図形の種類と合わせて処理する。どの四頂点が一組かを決め、RasterIXが処理できる単位へ変える。関数の内部へ入る前提は[描画命令の詳説](commands.md)で扱う。

画素の境界には規則があるので、頂点の数値だけから、実装の全画素をここで断定しない。これは「座標を理解できない」という意味ではない。図形の座標を決めることと、画素のどの位置で内外判定するかを決めることが、別の設定だからである。[画素の具体例](rasterization.md)では、その規則を明示して計算する。

<a id="sec-3"></a>
## 3 ソフトウェアが回路向けの数値列を用意する

RasterIXへはC++の関数名を文字として送らない。回路が解釈できる描画命令と必要な値を、ソフトウェアがメモリ上へ並べる。CPU自身の機械語命令とも別物である。CPUは「描画命令の数値列を作って送る」というプログラムを、CPU用の機械語で実行している。

例えば「描画状態を設定する」「図形を処理する」「画像を保存する」といった仕事には、それぞれ対応する形式がある。ただし、これは役割を日本語に言い換えたものだ。実在しない命令番号や、「一図形は必ず何語」という固定長をここで作ってはいけない。実際の語の意味は、固定版のコマンド生成側と`CommandParser.v`を対にして確認する。

この時点でメモリにあるのは主に命令の列であり、完成した四角形の画像とは限らない。「メモリにある」という言葉だけでは、プログラム、描画命令、テクスチャ、画像のどれかが分からないため、必ず保存内容を添えて呼ぶ。

<a id="sec-4"></a>
## 4 CPUが命令列の一語を取り出して回路へ書く

現在のWally用接続では、送信用の関数が命令列から32ビットずつ読み、MMIOの番地へ書く。`0x10080000`は通常の命令語用、`0x10080004`は最後の語用である。Linux上のプログラムは、`mmap`で得た自分用の仮想番地を通じてアクセスする。

ここでMMIOへ書いた32ビットは、「このCPUがアクセスした番地にRAMのセルがあり、そこへ普通に保存される」という意味ではない。番地を見て選ばれたAPB回路が、その書込みを命令入力として扱う。[メモリとバス](memory-bus.md)と[Linux](linux.md)では、この番地の見方を分ける。

<a id="sec-5"></a>
## 5 APBの完了とRasterIXの完了を分ける

APB変換回路は32ビットの値と最後の語かどうかを、ストリーム入力へ提示する。接続先が受け取れなければ、APBを待機させる。FIFOを使う構成では、FIFOに保存できたところでAPBの書込みを完了できる。

したがって、CPUから見て一回の書込みが完了しても、その図形が描き終わったとは限らない。語がFIFOの中で待っている場合もある。一語方式では完了を返す時点が異なり、RasterIX側の受取り確認を送り側まで戻す。この違いが[比較実験](measurement.md)の解釈に関係する。

この段階で必要なのは、語が同じ順序、同じ値、同じ回数で渡ることだ。「受け側が速いから、たぶん大丈夫」と考える部分ではない。[APBとCDC](cdc-protocols.md)で、受理するクロックの立ち上がりを明示して追う。

<a id="sec-6"></a>
## 6 回路が図形の内側にある画素を求める

命令解析回路が語を解釈し、描画に必要な状態や図形の情報を後段へ渡す。図形を扱う回路は、画素の位置を候補として調べ、その位置が三角形の内側かを判定する。四角形を二つの三角形で塗る場合も、この処理を使う。

この計算は二次元の図形にも必要である。「三角形を処理する」というだけで立体のゲームを研究対象にしているわけではない。座標、辺の式、内外判定、色を扱うところまでは、二次元でも同じ問題がある。

白い不透明な図形なら、条件を満たす画素へ白い色を書く。テクスチャや半透明を使う場合は、画像から色を読む処理や、元の色と混ぜる処理が加わる。すべての設定で同じ処理時間になるとは限らない。

<a id="sec-7"></a>
## 7 内部作業領域とDDRの画像を区別する

本構成のRasterIX_IFは、内部の作業領域で描画し、その結果を外部メモリへ移す。画面全体が一度に内部領域へ入る設定ではないため、帯状の領域に分けて処理する。五本の帯は五枚の画面ではなく、一枚の画像を完成させるための部分である。

DDR上の表示用画像では、RGB565という16ビットの形式で一画素を表す。例えば白は`0xFFFF`である。640画素幅の画像で、画素`(3,2)`の先頭は画像先頭から`(2×640+3)×2=2566`バイトの位置になる。この式は画像の配置を説明するものであり、描画命令の番地の式ではない。

<a id="sec-8"></a>
## 8 表示する画像を切り替える

描画する画像と、現在表示している画像を二枚で分ける。描画が終わる前にその画像を表示へ渡すと、一枚の画面に古い状態と新しい状態が混ざる原因になる。いつ切り替えられるかを表示側と取り決める必要がある。

「描画命令の送信が終わった」「回路の描画が終わった」「表示先が切り替わった」「画面上のその画素が送出された」は、同じ出来事ではない。測定で使う完了の意味を取り違えると、得たFPSの説明も変わってしまう。

<a id="sec-9"></a>
## 9 表示回路が一定の順で画素を送る

表示側は、ゲームの`for`文の進み方とは別に、画素を順に読み出して映像信号を作る。フレームの間や行の間には、表示タイミングとして決められた区間がある。映像の更新周波数だけゲームが新しい画像を作れなければ、同じ画像を複数回表示することもある。

さらにキャプチャ機器やOBSは、その信号を受けて記録する別の段階である。プログラムの完了回数から、キャプチャが正しく新しい画像を記録した回数を無条件に推定できない。表示経路の違いは[画像と表示](framebuffer-display.md)に、数え方は[計測](measurement.md)に整理した。

<a id="sec-10"></a>
## 10 この例を使って設計を説明する

発表で全工程の専門用語を列挙する必要はない。まず「CPUが図形の情報を作り、描画回路へ渡し、描画回路が画像を作り、表示回路が画像を送る」と説明する。その後、質問された境界へ戻れるようにする。

| 質問 | 指し示すもの | それだけでは分からないこと |
|---|---|---|
| CPUと描画回路は何を渡すか | 数値で表した描画命令の列 | 個々の命令の意味は生成側と解析側を読む必要がある |
| FIFOは何を保存するか | 描画命令の語と区切り | 画像全体を保存する場所ではない |
| フレームバッファは何を保存するか | 画素の色 | ゲームの衝突判定や得点そのものではない |
| Linuxは何をするか | プログラムの実行、メモリ管理、機器アクセスの土台 | Linux自体が全画素を描いているとは限らない |
| 高速化で何を減らしたか | 同じ状態の画面を作るための描画・送信・待機などの仕事 | CPUのクロックを上げたという意味ではない |

答える対象の保存場所や完了条件を示せれば、単なる用語説明より、実際の設計へ結び付く説明になる。
