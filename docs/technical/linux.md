# Linuxの起動から描画回路への書込みまで

[分野別の入口](README.md) · [用語を調べる](glossary.md)

FPGAの設定ファイル、Linuxの起動用ファイル、ゲームの実行ファイルは、それぞれ用途が異なる。この章では、PCで作ったゲームがWallyで動き、最後に周辺回路へ値を書くまでを説明する。掲載する確認コマンドは、特記しない限りファイルを読むだけで、SDカードやFPGAを書き換えない。

<a id="sec-1"></a>
## 1 回路を作る道とプログラムを作る道

HDLから合成・配置配線して作るbitstreamは、FPGA内の回路を設定するデータである。C/C++からコンパイル・リンクして作る実行ファイルは、設定済みのCPUが実行する命令とデータである。

ゲームの文字を変更しただけなら、通常はゲームの実行ファイルを作り直す。バスの番地選択を変更したなら、回路を作り直し、ソフトウェアの番地も合わせる必要がある。どちらを変更したかで再生成と試験の範囲が変わる。

<a id="sec-2"></a>
## 2 クロスコンパイラが必要な理由

開発PCのCPUとWallyは、実行する命令の種類が異なる。PC自身用のコンパイラで作った実行ファイルをSDへ入れても、Wallyがその命令を理解できるとは限らない。PC上で動きながらRISC-V用の命令を出すコンパイラを使う。これがクロスコンパイラである。

さらに、命令の種類だけでなく、関数の引数をどのレジスタで渡すか、整数とポインタの大きさ、浮動小数点の扱い、ライブラリとの接続規約も合わせる。これがABIに関係する。ファイル名にriscvと付いているだけで、Linux用と組込み裸環境用が同じになるわけではない。

<a id="sec-3"></a>
## 3 コンパイルとリンクとELF

コンパイルは各ソースを機械語などへ変換する。リンクは、複数のファイルやライブラリの参照先を結び、実行時の配置に必要な情報をまとめる。ELFは、こうした実行ファイルやオブジェクトファイルに使われる形式である。

確認には例えば次を使う。`game`は確認したい実ファイルに置き換える。

```sh
file game
readelf -h game
readelf -l game
```

最初にアーキテクチャと32/64ビットの種類を見る。次にプログラムヘッダで、どの領域をどのように読み込むかを見る。動的リンクする実行ファイルでは、必要なローダやライブラリが実機側にあることも必要になる。静的リンクはその依存を減らせるが、実行ファイルの容量は増えやすい。

逆アセンブルすると、C++のどの部分が何命令になったかを追える。ただし最適化で関数が展開されたり、変数が消えたり、順序が変わったりする。ソース一行と機械語一命令は一対一ではない。

<a id="sec-4"></a>
## 4 起動では複数のプログラムが順に準備する

リセット直後から、いきなりゲームの`main`へ入るわけではない。本研究の起動経路では、ブート用の処理、OpenSBI、Linux、ユーザー空間の準備を経る。各段階は、次の段階が必要とするメモリ配置、CPUの状態、機器情報などを整える。

OpenSBIは、RISC-Vの上位のソフトウェアが低い層の機能を利用する境界を扱う。Linuxはメモリ、プロセス、ファイル、デバイスなどを管理する。BusyBoxなどのユーザー空間の道具が、シェルや基本コマンドを提供する。ゲームプログラムはその上で起動される。

Linuxへ渡すレジスタやメモリ状態には約束があり、「バイナリの先頭へジャンプすればよい」だけではない。[RISC-V Linux boot requirements](https://docs.kernel.org/arch/riscv/boot.html)は、その引渡し条件を調べる一次資料である。本研究の具体的なファイルと順序は[技術付録第III部](../thesis/技術付録.md#part_III)に対応付けている。

<a id="sec-5"></a>
## 5 device treeは回路を生成しない

device treeは、CPU、メモリ、周辺機器の番地、割込みなど、OSが知る必要のある構成を伝えるデータである。DTSは人が読むソース、DTBは起動時に渡すバイナリ形式である。

RasterIXのdevice treeノードを足しても、FPGAの中に描画回路が新しく現れるわけではない。逆に、FPGA内に回路を置いても、OSに予約メモリや番地の情報が正しく伝わるとは限らない。ハードウェアの実装とソフトウェアへの説明をそろえる必要がある。

本構成の[device tree](https://github.com/SoshiroFujimori/wally-game-console/blob/cdf907bc1752b0f300e4fc70b9a51b2bae983b7f/linux/devicetree/wally-nexysvideo-rasterix.dts)では、命令レジスタの範囲と32 MiBの予約領域を記述している。`compatible`を書くだけで適切なドライバが自動生成されるわけではない。

<a id="sec-6"></a>
## 6 mmapは物理番地を使える仮想範囲へ結ぶ

[WallyBusConnector.hpp](../thesis/再現資料/接続ソース/examples/rasterix/WallyBusConnector.hpp)は、`/dev/mem`を開き、`mmap`で4096 byteの範囲を対応付ける。その戻り値を32ビットのレジスタ列として扱う。

```cpp
void* mapping = mmap(nullptr, 4096, PROT_READ | PROT_WRITE,
                     MAP_SHARED, fd, 0x10080000);
```

`0x10080000`は対象の物理番地、`mapping`はプロセスから使う仮想番地である。両方が同じ数値になる必要はない。この方法は、使っているLinuxの設定と権限、MMIO領域の扱いに依存する。一般のアプリケーションすべてへ許す仕組みではない。

接続コードはまず`regs[3]`を読み、`0x52495831`に一致するか調べる。意図したレジスタ回路へ届いているかを確かめるためである。この確認だけで描画回路内部やDDR3のすべてが動くとは分からないが、接続先の取り違えを早く発見できる。

<a id="sec-7"></a>
## 7 命令配列からMMIOへコピーする

CPU上のライブラリは、RAM上の配列へ描画命令を作る。転送関数は、その配列から一語読み、命令口へ一語書く。最後の語だけ別のオフセットへ書いて区切りを付ける。

```cpp
for (uint32_t i = 0; i < size / 4; ++i) {
    regs[(i + 1 == size / 4) ? 1 : 0] = data[i];
}
```

`data[i]`を読むのは通常のメモリ操作、`regs[...]`へ書くのはMMIO操作である。一行の代入に見えても、CPUの実行、キャッシュやメモリ、APBの待ちが関係する。DMAがCPUの代わりにこのループを行っている構成ではない。

<a id="sec-8"></a>
## 8 volatileとfenceは異なる問題を扱う

`volatile`を付けたMMIOアクセスは、コンパイラに対して「この読書きそのものに意味がある」と伝えるために使われる。ただし、複数スレッドの同期、CPUのメモリ順序、キャッシュの書戻し、GPUの処理完了をすべて保証する機能ではない。

接続コードの`fence iorw, iorw`は、RISC-Vのメモリ・I/Oアクセスの順序を扱う。インラインアセンブリの`"memory"`指定は、コンパイラ側のメモリアクセスの並べ替えにも関係する。コンパイラとCPUは別の層なので、同じ「順序」の問題でも役割を分けて読む。

fenceが終わっても、FIFOに入った命令をRasterIXが全部実行し、表示が切り替わったとは限らない。描画や表示の完了は、そのための応答やカウンタで確認する。

一般のLinuxカーネル内では、MMIOの読書きには`readl`、`writel`などの適切なアクセサを使う。今回のユーザー空間接続を、そのままどの機器のカーネルドライバにもコピーする設計にはしない。[Linux device I/O](https://docs.kernel.org/driver-api/device-io.html)

<a id="sec-9"></a>
## 9 応答の読出しは値を消費する

接続コードは、状態の応答有効ビットを確認してから`regs[6]`を読む。この読出しはFIFOの出口から次の一語を受け取る操作になる。ログへ出すためにもう一回読むと、次の語を取り出すか、次の応答を待って止まる可能性がある。

値を表示したいなら、一回読んだ値を普通の変数に保存し、その変数を表示する。状態を眺めるレジスタと、読むと状態が進むレジスタを区別することは、機器のプログラム全般で重要になる。

<a id="sec-10"></a>
## 10 スレッドとCPUコア数を分ける

ライブラリが複数スレッドを使っていても、CPUコアが一個なら、二つのCPU命令を別々のコアで完全に同時実行できるわけではない。OSが実行を切り替える。一方、CPUとは別のFPGA回路は、その間にも動作できる。

「命令作成中に前の描画が進む」は、CPUとRasterIXが独立に動ける構成に基づく可能性である。しかし、どの測定区間で実際にどれだけ重なったかは、コード構造だけで数値として確定しない。待ち条件と計測点を確かめる。

二組の命令リストは、片方の内容を送っている間に、もう片方を準備する管理に関係する。二枚の表示用フレームバッファと同じ二組ではない。[命令の章](commands.md)で具体的に区別する。

<a id="sec-11"></a>
## 11 pollingとsleepと割込み

pollingは状態を繰り返し読む方法である。完了を早く見つけやすいが、待っているCPU時間を使う。sleepを使うとCPUを他の仕事へ回しやすいが、完了直後に起きる保証はない。OSが再び実行するまでの遅れも加わる。

割込みなら機器から完了を通知できるが、通知回路、割込み制御、ドライバ、起床処理が必要になる。今回の表示完了待ちをpollingで行ったことは、割込みが一般に不要という結論ではない。用途、待ち時間、CPUの他の仕事、実装費用を比べる。

<a id="sec-12"></a>
## 12 停止した場所を観察から絞る

| 最後に確認できたこと | 次に確認する境界 |
|---|---|
| FPGAを設定できた | クロック、リセット、CPUの起動、UART |
| ブートの文字が出た | SDの読出し、次の起動段階の配置 |
| Linuxのシェルが出た | 実行ファイルのISA、ABI、ライブラリ、権限 |
| ゲームが起動したがID不一致 | MMIOの番地、bitstream、device tree |
| ID一致だが応答が来ない | 命令列、接続、FIFO、解析回路、メモリ |
| 画像メモリが正しいが画面が出ない | 表示回路、クロック、端子、受信経路 |

同じ「動かない」でも、最後に成功した境界が違うと、次に読むべきソースが変わる。現在の固定版と実験用変更の対応は[再現の章](board-reproduction.md)を参照する。
