# 正しさの条件から試験と不具合の切り分けを作る

[分野別の入口](README.md) · [用語を調べる](glossary.md)

回路を設計できる理解には、正常時の説明に加え、何を確かめれば間違いを見つけられるかが含まれる。この章では、命令一語の接続を例に、仕様、検査、波形、実機の観察を結ぶ。

<a id="sec-1"></a>
## 1 最初に外から見える約束を書く

命令接続なら、入力で受け付けた語を同じ順で一度だけ出す、止まっている間は提示中の語を変えない、満杯なら待たせる、という約束を考える。リセット中とリセット前の残りをどう扱うかも決める。

この約束がないと、実行結果が想像と違っても、どちらが正しいかを決められない。例えばリセットで未処理語を捨てる仕様なら、リセット前後をつないで全語一致を要求する検査の方が間違っている。

<a id="sec-2"></a>
## 2 validではなく受理した瞬間を数える

readyが0の間、validを3周期立て続けても、3語を送ったことにはならない。同じ語を保持して受取りを待っているだけである。転送回数は、各立ち上がりでvalidとreadyが両方1かを数える。

この基準を入力と出力でそろえる。入力へ提示しただけでまだ受理されていない語を、内部に保存した語として数えない。出力データ線に数値が見えただけで、相手が受理したと数えない。

<a id="sec-3"></a>
## 3 期待する語の列を保存する

検査用に、入力で受理した語をリストの末尾へ追加する。出力で受理したとき、リストの先頭と比較して一致すれば取り除く。途中の語が抜けた、二回出た、順が逆になった、区切りが違う、といった不具合を区別できる。

この検査用リストをscoreboardと呼ぶことがある。実装と同じ内部ロジックをもう一度書くより、「入力と出力で守る約束」を直接調べる方が、同じ間違いを複製しにくい。

<a id="sec-4"></a>
## 4 停止中に値が変わらないことを確かめる

一語Dをvalid=1で提示し、相手をready=0にする。次の周期も受理されていなければ、Dとその区切りは保持される必要がある。途中で次の語Eへ変われば、Dが消える。

これは、下流がいつもready=1の試験だけでは見つからないことがある。停止を意図的に入れるのは、相手の平均速度が遅いと決めつけるためではなく、インターフェースが許す入力を与えて約束を確かめるためである。

<a id="sec-5"></a>
## 5 境界条件を選ぶ理由

空のときに読む、満杯のときに書く、同時に読み書きする、最後の語で止める、ポインタが一周する、途中でリセットする、といった条件を選ぶ。普段と違う制御の枝を通るため、不具合を見つけやすい。

ランダムな待ちを加える試験も使えるが、乱数の種を保存して同じ列を再現できるようにする。ランダムに長く実行したことだけで、全状態を調べた証明にはならない。

<a id="sec-6"></a>
## 6 assertionは必ず守る条件を機械に見張らせる

例えば「停止した語は次の周期も有効で同じ内容」「満杯なのに保存位置を進めない」などの条件を、シミュレーション中に監視する。これをassertionとして書ける。

条件には、どのクロックで見るか、リセット時は除外するか、同じ周期か次の周期かという時間の意味がある。「データが同じ」という式だけでは不足する。試験を書くときは、期待する一例の波形を手で作り、その式がどの立ち上がりを比べるか確かめる。

<a id="sec-7"></a>
## 7 シミュレーションで確認できる範囲

RTLシミュレーションは、与えた入力に対して論理と状態がどう進むかを調べる。通常の0/1のモデルでメタステーブルの実際の発生確率を直接測るものではない。

CDCでは、構造、同期用属性、IPの要件、制約、配置配線後の経路も確認する。論理試験が通ったことを、どの配線・クロック条件でも安全という意味へ広げない。

<a id="sec-8"></a>
## 8 形式検証は条件付きの全探索を目指す

形式検証では、指定したモデルと前提の下で、ある性質が成立するかを調べる。有限の入力例を流す試験と異なり、条件に含まれる多数の入力・状態を論理的に扱える。

ただしモデル外の電気的現象や、誤った前提を置いて除外した状態までは保証しない。「相手はいつかreadyを上げる」という前提を入れた進行の性質と、その前提なしの無条件完了は違う。本資料で新たに形式証明を完了したと主張しているわけではない。

<a id="sec-9"></a>
## 9 波形では最初に違った瞬間を探す

最後に画面が壊れた時点だけを眺めると、原因が広過ぎる。入力で何語目を受理したか、出力でいつ期待と違ったかを特定し、その直前の状態、ready、valid、データを見る。

一語の重複なら「二回目の受理で、なぜ保持レジスタに前の値が残っていたか」という問いへ縮められる。巨大なゲームを、数語の入力と一回の停止だけで失敗する試験へ縮められれば、原因と修正の評価がしやすくなる。

<a id="sec-10"></a>
## 10 正解画像はできるだけ別の経路で作る

実装自身と同じ計算をそのままコピーした参照画像は、同じ誤りを持つ可能性がある。ゲーム状態から単純な2D図形を描く別の方法など、検査したい部分と違う経路で期待値を作る。

ただし参照側も、座標の境界、描画順、文字画像、色の量子化などの約束は合わせる必要がある。仕様が違う二枚を比較して不一致と呼んでも、どちらの不具合か分からない。

<a id="sec-11"></a>
## 11 全画素一致と動画は役割が違う

640×480なら307,200画素を比べられる。一枚の全画素一致は、比較した場面とその時点の画像について強い根拠になる。しかし、その前後に別の画像がちらついたか、受信が途中で途切れたかまでは分からない。

動画には時間方向の情報がある一方、色変換、縮小、圧縮で値が変わることがある。メモリのRGB565と圧縮録画のRGBがbyte単位で一致しないことだけを、描画の誤りとしない。観察したい境界に合う比較方法を選ぶ。

<a id="sec-12"></a>
## 12 E6の不具合記録をどう読むか

E6は、ブロック崩しの比較だけでなく、大きいテクスチャでの不一致と、命令解析の重複を単体再現した記録も残している。[結果と判断](../thesis/再現資料/実験記録/E6/report/結果と判断.md)

一つのゲームで正常だった結果と、別の条件で問題が出た結果は両立する。後者を隠して万能の接続と呼ばず、前者の価値も失敗一件ですべて否定しない。入力条件、使った版、観測箇所を分けて説明する。

<a id="sec-13"></a>
## 13 仮説を一度に一つの境界へ絞る

画面が出ない場合、CPU、DDR3、RasterIX、表示回路、ケーブル、取り込みを同時に変更すると、直った理由が分からなくなる。例えば画像メモリが期待どおりなら、その時点の描画以前の経路は一部確認できたので、次は表示以降を調べる。

試験用パターンの表示は出力経路の確認になるが、CPUが描画命令を出した証拠にはならない。CPUからのID読出しはMMIO経路の確認になるが、テクスチャ計算の証拠にはならない。この対応を[観察点の図](../thesis/figs/test-observation-points.png)と併せて読む。

<a id="sec-14"></a>
## 14 変更後に必要な試験を選ぶ

文書だけの変更なら、リンクと数値と説明の整合を確認する。レジスタの意味を変えたなら、バス試験とソフトウェアのアクセスを確認する。FIFO構造を変えたなら、順序、停止、リセット、CDCと実機の条件を確認する。表示切替を変えたなら、未完了読出しと連続映像も見る。

試験の数を無条件に増やすより、変更によって壊れ得る契約を選ぶ。同じ試験の成功を何度も数えることと、異なる失敗原因を検査することは違う。

<a id="sec-15"></a>
## 15 説明用モデルの到達点

[付属のPythonモデル](../../examples/technical-models/README.md)は、この詳説の算数と、保持・受理・順序の考え方を手元で確かめるためのものだ。波形の代わりに短い表を出し、期待値と照合する。

これは実機の命令パーサ、AMD FIFO、Linux、電気的な接続を動かした試験ではない。モデルで理解した条件を、実際のソースと既存の検証へ対応付けることが次の段階になる。
