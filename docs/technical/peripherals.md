<a id="sec-1"></a>
## 1 ボタンの状態がゲームへ届くまで

外の機器が持つ状態、配線上の電圧、通信で受け取ったbyte列、CPUが読むレジスタ、ゲームが使う左右移動という順に意味が変わる。各段階で何が入力で何が出力かを定める。

ゲームへ「左を押した」を渡すだけでも、機器が返すbitの意味、押している間0か1か、読み取る周期、前回との差、切断時の扱いが必要になる。まず通信のデータを正しく読み、次にゲーム用の入力へ変換する。

<a id="sec-2"></a>
## 2 UARTとSPIとI2Cの違い

UARTは、送受信側が決めた速度に従い、開始・終了の区切りを付けてデータを送る。通常、相手から転送用クロック線を受け取る方式ではない。SPIはクロックとデータ、選択信号などを用い、クロックのどの変化で値を読むかを合わせる。

I2CはSCLとSDAを使い、番地と読書き方向を含めて相手を選ぶ。電気的な接続と転送手順が前の二つと異なる。「どれもシリアルなので同じUART回路が使える」とはならない。

| 観点 | 決める例 |
|---|---|
| 配線と電圧 | 入出力方向、信号の許容電圧、GND |
| 時間 | ビット周期、値を変える時点、読む時点 |
| 取引 | 相手の選択、長さ、読書き方向、終了 |
| 異常 | 応答なし、途中停止、切断、再試行 |

<a id="sec-3"></a>
## 3 I2Cの0と1は出力の仕方が違う

通常のopen-drainのI2Cでは、機器は線をLowへ引くか、線を離す。Highはプルアップ抵抗によって作る。複数の機器が同じ線を共有するため、片側がHighを強く出し、もう片側がLowを強く出すような衝突を避ける仕組みである。

FPGAでは、外部I/OでLowを出す状態と、高インピーダンスで離す状態を使い分け、実際の線の値も入力として読む。内部信号へ単に0/1を代入する場合と同じではない。SCLの延長など、相手側が線を保持する条件も機器仕様に応じて扱う。[NXP UM10204](https://www.nxp.com/docs/en/user-guide/UM10204.pdf)

<a id="sec-4"></a>
## 4 byteを一個受け取るにも状態が要る

通信の開始、相手の指定、bitの送信、応答の確認、データの受信、終了は別の段階である。状態機械は、今どの段階にいて、次に何を待つかを覚える。

例えば8ビットを受信するとき、毎回の取得で値をシフトし、一ビットを追加し、何ビット集まったか数える。八個集まった時点で一byteが有効になる。受信途中の値をCPUが完成済みデータとして読むことを避ける仕組みも要る。

<a id="sec-5"></a>
## 5 CPUから見えるレジスタを先に決める

説明用の設計案なら、操作開始、状態、受信値、エラー理由などを別のレジスタへ置く方法がある。次の表は提案例であり、現在の製品の番地表ではない。

| レジスタの役割 | 読書きの意味 |
|---|---|
| CONTROL | 新しい読取り要求を出す |
| STATUS | 処理中、完了、新しい値の有無を見る |
| DATA | 完了した一組の入力値を読む |
| ERROR | 応答なしなどの原因を読む |

完了を読んだら消すのか、明示的な操作で消すのかも決める。値を複数レジスタに分ける場合は、途中で更新されて別の時刻の値が混ざらない方法が必要になる。二重化して完成した組を公開する方法などが考えられる。

<a id="sec-6"></a>
## 6 低速の通信中にAPBをどう扱うか

外部機器から返事が来るまで数百µs以上かかるとき、その間ずっとAPBを待たせる設計も考えられるが、CPUの他の仕事を止める影響が大きくなる場合がある。

別案では、開始要求だけを短く受理し、通信は周辺回路内で進め、CPUは後で状態を読む。要求を受け付けた完了と、通信そのものの完了を分ける。RasterIXの命令入口で学んだ「どの段階で完了を返すか」という考え方が使える。

<a id="sec-7"></a>
## 7 押し続ける状態と押した瞬間

今の入力を`now`、前回を`before`とし、1を押下状態とする。新しく押したbitは`now & ~before`、離したbitは`~now & before`で求められる。ゲーム開始を押した瞬間だけ受け付けたい場合と、パドル移動を押している間続けたい場合を分けられる。

機器が0を押下として返すなら、先に意味をそろえる。通信仕様のbitの極性を、ゲーム中のすべての条件文へ散らすより、入力の境界で変換すると追いやすい。

<a id="sec-8"></a>
## 8 入力から画面までの遅れ

押してから見えるまでには、次の読取りを待つ時間、通信、ゲームの更新、描画、表示切替、受信機器の処理が関係する。描画のFPSだけでは入力応答のすべては分からない。

例えば入力を10 msごとに読む設計では、押す時刻によって次の読取りまで0〜約10 msの差が生じる。その後の仕事も別に必要になる。これは周期による待ちの説明例であり、Wii機器を実測した数値ではない。

<a id="sec-9"></a>
## 9 自動試験で何を代わりに確認できるか

既知の入力列をソフトウェアから与えると、同じゲーム状態を再現して描画を比較できる。通信機器の応答を模擬する回路を使えば、正常応答、応答なし、遅れなどを再現できる。

しかし模擬入力が正しく動いても、実物の配線、電圧、機器固有の初期化、信号品質まで確認したことにはならない。最終的には実機側の入力から画面の反応までを結ぶ試験が必要になる。

<a id="sec-10"></a>
## 10 実装前に確認する資料

機器の通信仕様と電圧、基板の回路図とI/Oバンク、採用するIPやRTLの仕様、CPUからのアクセス契約をそろえる。Arduinoなど別のボードを間に置く場合は、そのI/O電圧をFPGAへ直接接続してよいかも確認する。

本章だけから特定機器の端子番号や初期化byte列を推測して配線しない。ここで得たい理解は、資料から得た条件を、電気・通信・CPU・ゲームの各層へ漏れなく割り当てることである。
