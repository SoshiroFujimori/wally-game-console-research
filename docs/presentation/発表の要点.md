# 発表の要点

[スライドと発表原稿](中間発表_主要事項.md) / [技術付録](../thesis/技術付録.md)

この発表の中心は、**既存のCPUと描画回路をつなぐ接続を実装し、ブロック崩しの動作を実機で確認したこと**である。接続方法を、Wallyの学習者が参照できる拡張例として公開する。

## 1. FPGAとCPUの関係

FPGAは、デジタル回路を実装できるチップである。今回は、その中にCPU、SDカード制御、描画回路などを実装した。CPUもFPGAの中に作った回路の一つである。

ゲームのプログラムは、そのCPUが実行する。回路を記述するHDLと、ゲームを進めるプログラムは、作る対象が異なる。

**質問例：なぜFPGAを使ったのか。**

> CPUと描画回路の接続を、回路として変更できるからです。今回の目的はWallyに周辺回路を加える拡張例を示すことなので、既存の回路コードを組み合わせて実装できるFPGAを使いました。

対応するスライド：2。

## 2. 先行研究・授業と本研究の関係

3枚目では、FPGAにCPUや描画回路を実装する先行研究・開発を紹介する。WallyのCPU・SoCとFPGA実装は教材・授業を扱う[ASEE論文](https://doi.org/10.18260/1-2--57147)にも記載されている。RasterIXの描画・表示については[公式の設計コードと実装例](https://github.com/ToNi3141/RasterIX)を参照する。両者を組み合わせた既存例を示す図ではない。

『ディジタル回路設計とコンピュータアーキテクチャ』（DDCA）では、値を保存するレジスタ、加算などを行う演算回路、命令に応じて動作を指示する制御回路を組み合わせ、CPUを設計する。東京大学・広島大学・豊田高専・久留米高専などに教科書・教材の指定例がある。年度と版は学校によって異なる。

4枚目の図は、CPU内部の回路を組み立てる学習から、CPUと周辺回路をつなぐ学習、さらに描画・表示を追加する本研究へと、設計する範囲が広がる関係を示す。簡略図の線は機能のつながりを表し、完全な信号配線や実行順序を表すものではない。

本研究が提供するのは、Wallyに描画機能を追加してゲームを動かす具体例である。CPU設計を学んだ人が、周辺回路の追加へ進むときに、接続コード、プログラム、実機の動作を参照できる。

**質問例：教科書が使われていることと、この研究の価値はどうつながるのか。**

> 教科書の採用例は、CPU設計を学ぶ人がいることを示す背景です。本研究は、その先でWallyを拡張したい人に、描画回路の接続と動作するプログラムの例を提供します。

## 4. C言語のコードと回路の動きを対応させる

6枚目は、CPUが行う処理をC言語で表した概念例である。左がゲームをSDカードから読み込む処理、右が読み込まれたゲームの処理である。SDカードにはコンパイル済みの機械語を保存し、その機械語をDDRメモリへ読み込んでCPUで実行する。図中のC言語の文字列をCPUが直接実行するという意味ではない。

図の行番号はコードを参照するための番号であり、メモリのアドレスではない。

| 説明する処理 | 6枚目の行番号 | 対応する回路のスライド |
| --- | --- | --- |
| SDカードから受信した1バイトをDDRメモリへ保存する | 6 | 6枚目の左側 |
| DDRメモリに読み込んだゲームを呼び出す | 7 | 6枚目の左から右への矢印 |
| 描画命令の1語を接続回路へ書く | 13〜14 | 7〜9枚目 |

### SDカードからの読込み

6枚目の1〜7行目は次のコードである。

```c
unsigned char *sd =
    (unsigned char *)0x1304C;
unsigned char *ddr =
    (unsigned char *)0x80000000;
for(int i=0; i<size; i++)
    ddr[i] = *sd;
((void (*)(void))ddr)();
```

`sd`と`ddr`は、値が置かれた場所を指すポインタである。`unsigned char`は1バイトを扱う型である。`sd`に入れる`0x1304C`はSDカード制御の受信口を指し、`ddr`に入れる`0x80000000`はDDRメモリの保存先の例を表す。`size`は読み込むゲームのバイト数である。

6行目の`ddr[i] = *sd;`は、右辺を読んでから左辺へ保存する。まず`*sd`によって、SDカード制御の受信口から届いた1バイトを読む。次に、同じ値を`ddr[i]`が指すDDRメモリの場所へ書く。この一行に、周辺回路からの読出しとメモリへの書込みの二つが含まれる。

繰返しの最初は`i=0`なので、保存先は`0x80000000`である。次は`i=1`なので`0x80000001`へ保存する。一方、SDカード制御の受信口は毎回`0x1304C`のままである。同じ受信口から次のデータを受け取り、DDRメモリ側の保存先を順に進めることで、SDカードの内容をコピーする。

6枚目の左側は、この受信と保存を示す。右辺でCPUがSDカード制御から値を受け取り、左辺でDDRメモリ制御を通してメモリに保存する。実際の通信では、次のデータを受信するための要求や待ちも行う。受信口を読むだけでSD通信が進むわけではない。

### DDRメモリに読み込んだゲームの開始

7行目の`((void (*)(void))ddr)();`は、DDRメモリに置いたプログラムを呼び出す概念的な書き方である。

- `ddr`が保持する数値は、プログラムを置いた場所のアドレスである。
- `(void (*)(void))`により、そのアドレスを「引数も戻り値もない関数の開始位置」として扱う。
- 最後の`()`で、その関数を呼び出す。

呼出しによってCPUの実行先がゲームへ移る。6枚目の青い矢印は、読み込んだゲームへ実行が移ることを示す。CPUはDDRメモリ制御を通してゲームの命令を読み出す。この例では、ゲームの入口がコピーした領域の先頭にあると仮定している。一般の実行ファイルには配置や開始位置を調べる処理も必要であり、ファイルを先頭からコピーすれば何でも実行できるという説明ではない。

### ゲームから描画命令を送る

6枚目の8〜16行目は、読み込まれたゲームの処理を表す。

```c
void game(void) {
  while (1) {
    update_game();
    make_commands();
    for(int i=0; i<count; i++)
      *(unsigned int *)0x10080000 =
          commands[i];
  }
}
```

`while (1)`の中で、ゲームの処理を繰り返す。`update_game()`はボールの位置、当たり判定、得点などの更新をまとめた説明用の関数名である。`make_commands()`は、図形の位置や色を既存のRasterIX/OpenGL互換ライブラリへ渡し、描画命令の数値列を準備する処理をまとめた説明用の名前である。実際のソースの関数名をそのまま引用したものではない。

`commands`はその描画命令の配列、`count`は命令列に含まれる語の数である。12行目で`i`を増やしながら、13〜14行目で`commands[i]`の1語を`0x10080000`へ書く。`unsigned int`は対象環境では32ビットなので、ここでは一度に32ビットの値を送る。7枚目ではこの2行を一行にまとめて再掲する。

接続回路は`0x10080000`への書込みを受け取るように接続されている。そのため、このC言語の代入が回路への描画命令の送信になる。CPUが実行する機械語の命令と、描画回路に送るデータとしての描画命令は、それぞれ受け取って実行する回路が異なる。

### 概念例と実装の対応

このコードは短い説明用の断片であり、単独で動く完全なローダーやゲームではない。読込みと実行環境の準備には既存のブートローダーやOSを利用する。ゲーム本体の実装言語はC++であり、図は処理の関係をC言語で表したものである。

実際には、SDの初期化、要求、転送を進める送信、受信待ち、ファイル選択、エラー確認、プログラムの配置、命令フェッチの同期などを行う。また、図では`volatile`を省略しているが、実装のMMIOアクセスには必要である。実際のWallyBusConnectorは`mmap`で対応づけたアドレスを`volatile`ポインタで操作し、命令列の末尾を別のレジスタへ書き、`fence`で順序を制御する。画面切替や待ちも概念例には含めていない。

**質問例：読込み処理も新しく作ったのか。**

> 読込みや実行環境の準備には既存の仕組みを使っています。本研究では、ブロック崩しと、描画回路へ命令を送受信するWally用の接続部分を追加しました。

対応するスライド：6〜9。SDの受信口とコピーは[spi.h](../../console/fpga/zsbl/spi.h)・[boot.c](../../console/fpga/zsbl/boot.c)、描画命令の送信は[WallyBusConnector.hpp](../../console/examples/rasterix/WallyBusConnector.hpp)と[接続回路](../../console/fpga/src/rasterix_apb.sv)に対応する。

## 5. SDカード、CPU、DDR3、描画回路の役割

SDカードにはプログラムを保存しておく。CPUはSDカード制御を通して内容を読み込み、DDRメモリ制御を通してDDR3に保存する。実機ではブートローダーやOSがこの読み込みと配置を担当する。

CPUはDDR3上のゲームプログラムを実行し、ボールの位置、当たり判定、得点などを計算する。その結果を描くため、付属ライブラリを使って描画命令を用意し、描画回路へ送る。

描画回路は命令に従って画像を作る。画像はDDR3へ保存し、表示回路が読み出してHDMI端子へ映像を出す。

**質問例：ゲームの当たり判定も描画回路が行うのか。**

> 当たり判定や得点の計算はCPUが行います。描画回路は、CPUから指定された図形や文字を画像にします。

対応するスライド：6・7・10。

## アドレスから接続先を選ぶ仕組み

CPUが値を書き込むときは、書込み先のアドレス、書き込む値、書込みであることを示すイネーブル信号を出す。アドレスデコーダは、そのアドレスがどの回路の範囲に入るかを調べ、対応する回路の選択信号を有効にする。

今回の接続回路には、`0x10080000〜0x100800FF`の範囲を割り当てている。例えば`0x10080000`へ書くと接続回路が選ばれ、書込みデータを描画命令として受け取る。CPUが出す書込みイネーブルと、アドレスデコーダが出す選択信号は役割が異なる。前者は「書く操作」、後者は「どの回路への操作か」を表す。

既存の領域選択回路を使い、外部周辺回路の領域を有効にして描画接続回路へつないだ。アドレスデコーダの回路そのものを一から作り直したという意味ではない。

対応するスライド：8。[構成の派生設定](../../console/config/derivlist.txt)、[アドレスデコーダ](../../console/src/mmu/adrdecs.sv)、[周辺回路への接続](../../console/src/uncore/uncore.sv)を参照できる。

## 6. 接続回路で解決したこと

接続には二つの役割がある。

- **受渡しの形式を合わせる。** CPU側の書込みを受け取り、描画回路側の信号のやり取りに合わせて同じデータを渡す。この部分の回路を追加した。
- **異なるクロック間で渡す。** クロックは回路がデータを扱うタイミングを決める信号である。CPU側と描画側は異なるクロックで動くので、その境界でデータを受け渡すAMD製IPを組み込んだ。

命令の内容を別の命令へ翻訳する、という意味ではない。描画回路用の命令はCPU上のライブラリが用意し、接続回路はその値を受け渡す。

**質問例：二つともAMD製なのか。**

> 形式に合わせる部分は追加した回路です。クロック間の受渡しにはAMD製の回路を使っています。

**質問例：周波数が違うと何が困るのか。**

> 送る側が値を切り替えるタイミングと、受け取る側が値を読むタイミングがそろいません。そのままではデータを正しく渡せない可能性があるので、クロック間の受渡し用IPを使いました。

詳しい仕様では、CPU側はAPB、描画回路側はAXI4-Stream、標準の動作周波数はそれぞれ20 MHzと100 MHzである。非同期FIFOの内部設計や他方式との性能比較は、本編の主張に含めていない。

対応するスライド：9。

## 7. 実機で何を確認したか

パドルは自動操作である。ゲームコントローラは今後の候補に含める。録画のフレームレートをゲームの描画FPSとして報告しない。

## 9. FPGA使用量から分かること

11枚目は、「Wally基本構成」と「ゲーム機構成」の二列で比較する。前者は描画機能を追加する前に保存したCPU・周辺回路の構成であり、LUTは36.22%、Block RAMは23.01%だった。ゲーム機ではそれぞれ49.90%、58.90%となる。どちらもCPU単体の使用量ではなく、メモリ制御などを含む全体の値である。


使用率は、その種類の資源がFPGAに何個あり、そのうち何個を使ったかを表す。例えば、LUTは134,600個のうち67,166個を使い、49.90%となる。LUTは論理演算や条件判定を実現する。Block RAMはFPGAチップ内のメモリで、215 / 365 = 58.90%を使う。ボード上のDDR3はこの割合に含めない。

今回の値は、CPU、描画、表示、メモリ制御などを含む回路全体について、配置配線した後のレポートから取り出した。回路設定データのハッシュを確認し、実機動画で使ったものと一致させた。これにより、ゲーム機の回路が対象FPGAに収まる規模であり、その構成でゲームが動いたことを説明できる。

**質問例：使用率が100%未満なら、それだけで動くのか。**

> 使用数だけでは動作は決まりません。今回の回路では配置配線とタイミングを確認したうえで、実機でゲームを動かしています。使用量の表は、その実装に必要だった規模を示しています。

**質問例：余っている資源で何を追加できるのか。**

> 未使用の資源はありますが、追加できる内容は回路の種類や配置にも依存します。コントローラやGUIなどの拡張時には、変更後の使用量とタイミングを確認します。

**質問例：基本構成とゲーム機構成の差がRasterIXの使用量なのか。**

> 11枚目は、保存していたCPU構成とゲーム機構成の全体を比べたものです。その間にほかの回路も変更されているため、差のすべてをRasterIXの使用量とはしていません。

対応するスライド：11。[レポートと動画の対応、数値、比較範囲](../../experiments/standard-display-resources-20261110/README.md)を参照できる。

一番外側はNexys VideoというFPGAボードである。ボードの中にFPGAチップがあり、その内側にCPUや描画回路を実装する。SDカードスロット、DDR3メモリ、HDMI端子はチップの外にある部品なので、チップの枠の外、ボードの枠の内側に置いている。
