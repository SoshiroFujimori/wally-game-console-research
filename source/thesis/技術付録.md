# 二次元ゲーム機の設計を再現するための技術付録

公開用資料では、個人情報を除去し、参照先を本研究リポジトリの配置へ対応付けた。`再現資料`はこの文書と同じフォルダーにある。`../../experiments`はリポジトリ直下の補足実験を指す。`RESEARCH_ROOT`は取得した研究リポジトリの絶対パスとして設定する。保存物の一覧と旧参照先の対応は[参照先の一覧](../references.md)にある。


## この付録の使い方

この技術付録は、同梱の本文「FPGAを用いた二次元ゲーム機の設計と実装」を読み、実装を自分で組み立て、設計変更の影響を調べるための詳説である。本文は研究の目的、接続の設計、動作確認、測定結果を扱う。こちらではファイル、信号、計算、試験手順を深く追う。両冊の図表は、各冊内の本文から参照する。

この冊子は学習順ではなく、知りたい分野へ直接移れる五部構成とした。第I部はHDLとFPGA、第II部はWally、第III部はLinuxとシステムソフトウェア、第IV部はRasterIX、第V部はNexys Videoへの統合、実験、再現を扱う。各部では、用語の定義だけで終わらず、具体例、データまたは信号の流れ、固定版ソースの入口、確認方法、説明からは断定できない範囲まで示す。

![図案内.1 五部の分野と実機システムの関係](figs/deep-topic-map.png)

ハードウェアは、SystemVerilogから推論される回路、LUT・FF・BRAM・DSP、組み合わせ経路、pipeline、clock、reset、CDC、bus、Wally内部、RasterIX内部、映像出力まで扱う。ソフトウェアは、cross compile、ELF、ZSBL、OpenSBI、Linux kernel、device tree、仮想memory、MMIO、C++の描画API、ゲームloop、診断方法まで扱う。hardwareとsoftwareを別々に覚えるだけでなく、C++の一回の書込みがCPU命令、cacheとbus、周辺register、command FIFO、描画pipeline、framebuffer、映像信号へ変わる境界を追えることを目標とする。

付録A〜Zの文字は既存の参照を壊さないために維持している。分野別に配置したため、冊子内ではアルファベット順に並ばない。例えばFIFOとclock境界は第IV部の付録I、Nexys Video対応の再現は第V部の付録Aにある。章番号は本技術付録内、単に「第7章」のように本文中で示す従来の表記は同梱の研究本文を指す。Word版の目次と内部リンクから移動できる。

固定版、実験条件、引用の意味は本文と共通である。従来の解説と再現演習は初期の固定版を対象とし、2026年10月8日の更新版とFIFO比較E6は、第V部の技術付録第29章にまとめた。特に、FIFO比較が未実施だった時点の説明を更新し、ソースから分かることと実測したことを区別する。説明用の周期数や小さなFIFOと、実機で採用した値を区別する。試験計画と書いた部分は未実施であり、保存済みの測定結果へ加えない。将来のオンライン公開へ向け、図、資料、相対リンクを同じフォルダで扱える形にしている。

### A.3 値を一つ変更するときの練習

練習として、512 MiBの値がどこへ伝わるかを追う。まずderivlist.txtのEXT_MEM_RANGEを見る。次に生成手順がRANGE + 1で容量を求め、起動コードへ渡すことを確認する。さらにデバイスツリーのmemoryに書いた容量と比較する。

ここで、DDR3の実物が512 MiBだから、容量を知らせる設定を512 MiBへ合わせたのである。設定を1 GiBへ増やしても、実物のメモリが増えるわけではない。この区別ができれば、パラメータを書き換える意味を理解できている。

同じようにCPU20 MHzの値を追う。MakefileのSYSTEMCLOCK、Clocking Wizardの出力、UART等の設定、デバイスツリーを対応付ける。どの値が物理回路を作り、どの値がその説明をソフトウェアへ伝えるかを色分けして読むとよい。

### A.4 最上位回路を読む順番

fpgaTopNexysVideo.svの先頭には、外へ出る端子が並ぶ。clkやresetnは基板から入る信号、DDR3の信号は基板上のメモリにつながる信号である。次に内部の配線が宣言され、その後に部品の実体が置かれる。

部品の実体を作る記述は、モジュールの種類、実体の名前、接続する端子の組で読む。例えば回路Aの出力をwire1へつなぎ、回路Bの入力にもwire1を指定すると、両者が接続される。ソフトウェアの関数を順番に呼んでいるわけではなく、これらの回路は同時に存在して動く。

読み順は、外部入力の同期、クロック生成、リセット、Wally本体、AHBからAXIへの変換、クロック変換、DDR3制御とする。一回のメモリ読み出しがCPUから外へ出て戻る経路を、アドレスとデータの両方向に追う。付録Eでは、この初期版の組み立てをファイルごとに説明する。さらに、付属教材の8.1〜8.10節には、この233行の全コードを小さく分けた解説がある。

## 付録B 信号とコードを数値で追う

### B.1 命令の書き込みを一行ずつ読む

次は`rasterix_apb.sv`の抜粋であり、単独で完結するモジュールではない。接続全体は7.2〜7.8節で説明した。

```systemverilog
assign CmdValid = CommandWrite;
assign CmdLast = PADDR[2];
assign CmdData = WriteData;
```

CommandWriteは、この回路が選ばれた書き込みのアクセス段階で、必要な4 byteが有効、かつ命令用番地であるときに1になる。三行はそれぞれ「有効な語がある」「最後の語か」「語の値」を出す。受け取りはCmdValidとCmdReadyが両方1の立ち上がりで一度だけ成立し、同時にCPUへPREADYを返す。

| CmdValid | CmdReady | そのクロックでの動作 |
|---:|---:|---|
| 0 | 0 | 命令は渡らない |
| 0 | 1 | 受け取り側に空きがあるが、命令は渡らない |
| 1 | 0 | 命令とその値を保持して待つ |
| 1 | 1 | 命令を一つ受け取る |

### B.2 64 bitバスの中から32 bitを選ぶ

CPU側のPWDATAは64 bit、RasterIXへ送る一語は32 bitである。次の条件演算は、PADDR[2]が1なら上半分、0なら下半分を選ぶ。

```systemverilog
assign WriteData = PADDR[2] ? PWDATA[63:32] : PWDATA[31:0];
```

0x10080000のbit 2は0、0x10080004では1である。したがって図B.1のように、通常命令は下位、最後の命令は上位から取り出す。濃い青の「選択」がこの条件演算で、出力CmdDataはどちらも32 bitとなる。

![図B.1 64 bitの書き込みデータから32 bitを選ぶ位置](figs/data-lanes.png)

PSTRBは各byteが有効かを示す。選ぶ32 bitの4 byteすべてが有効であることも、7.7節のWordWriteの式で確かめる。ソフトウェアの32 bit単位・4 byte境界という約束と、この回路の選択を対応させる。

### B.3 三つの命令データを送る具体例

説明用に0x11111111、0x22222222、0x33333333という三つの32 bit値を考える。実際の有効な描画命令の内容ではなく、転送の順番を示すための値である。

| 書く順序 | CPUが書く実アドレス | データ | CmdLast |
|---|---|---|---:|
| 1 | 0x10080000 | 0x11111111 | 0 |
| 2 | 0x10080000 | 0x22222222 | 0 |
| 3 | 0x10080004 | 0x33333333 | 1 |

最初の二回は同じアドレスへ書く。通常の配列へ保存するように、アドレスを4ずつ増やして並べる操作ではない。同じ命令口が毎回データを受け取り、FIFOの中へ順番に並べる。最後だけ終端を表す別の命令口へ書く。

C++のregsとの対応は7.6節の表に示した。一要素は4 byteなので、regs[3]が先頭+12、すなわち識別値の0x0cを指す。

### B.4 完了回数を使う理由

一瞬だけ1になる信号をCPUが直接読むと見逃し得るため、完了のたびに増える回数を回路側で保持する。例えば送信前が125なら、切り替え依頼後も125の間は待ち、126へ変わると新しい完了が分かる。アプリケーションは一回のpresentごとに確認し、旧画像を再利用する区切りにする。

回数が示すのは10.5〜10.6節の回路内の条件であり、ディスプレイの画素を光学的に数えたものではない。

### B.5 未完了の読み出しを数える例

メモリへ出す要求は、受け付けられる時点と返事が戻る時点が異なる。表示回路が古い画像に対して二件の要求を出していて、どちらの返事も終わっていないとする。このときOutstandingは2である。

次に新しい画像の先頭を読む要求が受け付けられる。同じクロックで返事の完了がないなら、待つべき件数は2 + 1 = 3になる。旧画像の二件と新画像の最初の一件が完了するまで待つ。新しい要求が出たという事実だけで、旧画像を再利用してはいけない。

| 出来事 | 残る返事の数 | 表示切り替えの完了を返すか |
|---|---:|---|
| 新画像の最初の要求を受理 | 3 | まだ返さない |
| 旧画像の一件目が完了 | 2 | まだ返さない |
| 旧画像の二件目が完了 | 1 | まだ返さない |
| 新画像の最初の一件が完了 | 0 | 返す |

実装の式には、同じクロックで返事が一件完了した場合の引き算もある。Remaining <= Outstanding + 1 - ReadCompletedという関係で、追加した一件と同時完了の一件を両方反映する。ここを省くと、一件余分に待ったり、早く完了を返したりする。

この数え方は、使用している表示側の要求と応答の順序に合わせた制御である。任意のAXI接続へ条件を確認せず流用できる一般的な完了判定として扱わない。


図B.2は、上の表を時間順に並べ直したものである。

![図B.2 旧画像の要求と新画像の最初の要求を待つ例](figs/outstanding-reads.png)

青い箱の時点で新しい画像の要求が一つ加わり、返事を待つ件数が2から3に増える。その後、返事が終わるたびに3、2、1、0と減る。この例では最後の0で切り替え完了を通知する。図は説明用の一例であり、同時に要求と返事が成立する場合は、本文の式どおり増減を同時に計算する。

### C.2 APBの最小試験を実行する

付属のrun-apb.shは、FPGA実機を使わずに接続回路を試す。引数には、固定版を取得したWallyの場所と、新規の試験出力先を渡す。実行場所はUbuntuであり、VerilatorとC++コンパイラが必要になる。以下を実行する前に、Ubuntuの端末で付属の「再現資料/試験と測定」ディレクトリへ移動する。また、M.4節に従って、固定版のリポジトリを指すWALLY環境変数を設定しておく。

```bash
bash run-apb.sh "$WALLY" "$HOME/apb-reproduce-output"
```

スクリプトはrasterix_apb.svとtb_apb.svから試験用プログラムを作り、実行結果を出力先へ保存する。成功した場合はAPB_PASSで始まる行を表示する。行の後ろには、データ位置、試験側が与えた受取可に対する待ち、応答待ち、識別値、回数を確認したことが記される。

この試験はDVIの電気信号や実機DDR3を動かさない。合格したらAPB接続の検査として記録し、実機まで合格と記さない。今回の原稿に付属する再実行記録も、この限定した範囲で保存する。

### C.3 測定プログラムの引数を読む

E4の測定ソースv009には、全体描画、呼び出し統合、部分描画を選ぶ引数がある。通常のrasterix-breakoutとは別のプログラムである。--frames 180は測る画面数、--warmup 30はその前の準備数、--state-frameはどの状態から始めるか、--waitは待ち方を指定する。

例えば保存計画の序盤・全体描画は、--state-frame 0、--frames 180、--warmup 30、--wait sleepという条件である。呼び出し統合では--groupedを追加する。部分描画の正確な引数は、付属するcontrolled-finalhdmi.jsonのretainedという試行を参照する。すべての引数を新しい文章から推測する必要はない。

測定後の画像を保存する--dumpの出力先は、試行ごとに変える。同じ名前で上書きすると、どの条件の画像だったか分からなくなる。保存した計画ファイルは、実行順とラベルも含めて再現の入力になる。

### C.4 CSVから時間を再集計する

`frames.csv`の一行が一画面分の記録である。`logic_ns`はゲーム処理、`write_ns`は転送、`wait_ns`は完了待ちで、nsをmsへ直すには1,000,000で割る。例えば57,000,000 nsは57 msになる。描画準備は`api_ns + swap_ns - write_ns`で求める。引き算の理由と具体例は12.6節に示した。

列の定義はMETHODS.mdと測定ソースで照合する。準備時間が負になる場合は、範囲の解釈や列の対応を見直し、そのまま結果表へ使わない。一試行180行の平均を求め、同条件三試行の中央値を取る。付属の`summarize-controlled.py`は保存した27試行を再集計するものであり、新たな実機計測ではない。試行数と状態列の一致も出力し、欠けた条件を黙って省かない。

### C.5 画素比較と動画の比較の違い

RGB565ファイル同士なら、同じ場所の16 bit値を厳密に比較できる。動画では、拡大、色の変換、圧縮が入るため、元の16 bit値とそのまま同一にはならない。動画は、映像の有無、縦横比、欠けた行、ボールの移動などを確認するために使う。

例えば録画が一秒60フレームでも、同じゲーム画像を繰り返して取り込んだ可能性がある。録画ファイルのフレーム数をゲームの新画像数と読み替えない。本研究は、切り替え完了の記録と動画の動きを別々の証拠として組み合わせる。

### C.6 新しい実験を記録する書式

新しい確認では、次の項目を一つの実験フォルダへ保存する。これを行えば、後で「どの構成の結果だったか」を思い出して埋める必要が減る。

| 項目 | 記す内容 |
|---|---|
| 問い | 何が正しいか、何の効果を確かめるか |
| 入力 | ソース版、bitstream、DTB、実行ファイルのハッシュ |
| 条件 | クロック、画面、入力、開始状態、回数、順番 |
| 出力 | 生ログ、各画面の記録、画像、必要なら動画 |
| 判定 | あらかじめ決めた一致条件、合格・不合格 |
| 解釈 | その結果から言えること、別途確認が必要なこと |

### D.3 理解を確かめる小さな課題

「ボールのxを100から103へ変えたとき、どこが変わるか」を説明してみる。まずGameの位置が変わり、sceneの四角形の位置が変わり、Rendererが違う頂点を渡し、命令と画素が変わる。最後に表示回路が新しい画像を読む。この順を自分の言葉で追えれば、ゲームの変数と映像がつながる。

次に、「命令FIFOが満杯なら何が起こるか」を説明する。CPU側の書き込みが待ち、空きができたときに同じデータが一度受け取られる。書き込み完了と表示完了は異なる。ここまで言えれば、命令の接続と画面切り替えを区別できている。

最後に、「速くなった結果が正しいと言うには何を比べるか」を説明する。同じゲーム状態、同じ最終画素、同じハードウェア条件を確かめ、その上で時間を比べる。単に数字が大きい、映像が滑らかという印象だけで判断しない理由が分かれば、実験の説明へ進める。


## 付録E Nexys Video対応をファイルごとに組み立てる

### E.1 この演習で作る段階と、ファイルの開き方

この付録は、WallyだけをNexys Videoへ載せる最初の変更を扱う。出発点は2345ec2ad、答え合わせの対象はf0764f003である。RasterIXを追加した後の完成版へ、以下の変更をさらに加える演習ではない。先にこの段階を分けると、「基板を動かすための変更」と「画像を描くための変更」を混同しなくなる。

ファイル名の先頭にあるfpga/やconfig/は、リポジトリ直下から見たフォルダ名である。例えばfpga/generator/Makefileを開くとは、リポジトリのfpgaフォルダ、その中のgeneratorフォルダ、その中のMakefileを開くことである。Vivadoが後で作るIPフォルダ内のコピーを直接直すと、次の生成で消えることがある。ここでは、生成の入力となるファイルを扱う。

付属する再現資料/ボード対応/変更前と変更後を並べて開く。既存ファイルの編集は両者を比べ、新規ファイルは変更後を参考に作る。さらに詳しい全行の説明は、同じフォルダのNexysVideo対応を変更前から再現する.mdにある。論文では変更理由と接続を順に理解し、その教材では実際の全コードと答え合わせする。

以下のコードは、対象ファイル中の要点を抜き出したものである。断片だけをファイル全体として保存してはいけない。説明用に省いた接続は、付属する変更後の全ファイルで確認する。自分で作業する場合は第14章と同じく、元の作業場所を残した演習用クローンを使う。

### E.2 CPUへ512 MiBの範囲を知らせる

編集するのはconfig/derivlist.txtである。ここにfpganexysvideoという設定を、既存のfpga設定から派生させて追加する。「派生」とは、共通する設定を引き継ぎ、違う値だけを指定することである。CPUの命令セットなどを一から書き直す必要はない。

```text
deriv fpganexysvideo fpga
EXT_MEM_RANGE 64'h1FFFFFFF
```

64'hは、続く値を64 bit幅の16進数として読む記法である。1FFFFFFFは容量そのものではなく、開始番地から最後のbyteまでの差である。先頭を0番と数えるため、容量は1を足した0x20000000 byte、すなわち512 MiBになる。外部メモリの開始番地0x80000000を足すと、最後の番地は0x9fffffffである。

この値を使って、CPUのアドレス判定回路が外部メモリ宛てかを判断する。CPUが0xa0000000へアクセスしたときまで、この512 MiBのメモリへ通してよいわけではない。第6章の範囲の計算と対応させ、生成された構成のEXT_MEM_RANGEが一致することを確認する。

### E.3 実物のDDR3に合うMIG設定を用意する

追加するのはfpga/generator/xlnx_ddr3-nexysvideo-mig.prjである。MIGは、FPGAとDDR3の間の細かい信号制御を作るためのIPである。基板メーカーのNexys Video用mig.prjを元にすることで、DDR3の種類とピンのつながりを引き継ぐ。

引き継いだ設定のうち、FPGA内部のCPU側との接続に関係する値を変更した。外へ出るDDR3のデータ線は16本のままである。一方、内部のAXIは一回に64 bitを運ぶ設定にする。MIGが内部の転送と外部メモリの転送を対応付ける。64 bitへ設定することは、基板の配線を64本へ増やすことではない。

| 設定項目 | 今回の値 | 何と一致させるか |
|---|---|---|
| C0_S_AXI_DATA_WIDTH | 64 | CPU側のAXIデータ幅 |
| C0_S_AXI_ID_WIDTH | 4 | 接続したAXIの識別番号の幅 |
| C0_S_AXI_SUPPORTS_NARROW_BURST | 1 | 幅の狭いアクセスも受け付ける条件 |
| C0_C_RD_WR_ARB_ALGORITHM | ROUND_ROBIN | 読み書き要求の選び方 |
| ModuleName | ddr3 | 最上位回路から呼ぶモジュール名 |
| SystemClock | No Buffer | MMCMの内部出力から受け取る構成 |
| UIExtraClocks | 0 | 追加クロック出力を使わない構成 |

例えばCPUが1 byteだけを書きたい場合でも、64 bitの線全体を一つの値として上書きするとは限らない。どのbyteを有効にするかを示す信号と転送サイズで、書き換える範囲を伝える。幅の狭い転送に対応させる設定は、このようなアクセスを接続先が扱えるようにするためである。

MIGのsys_clk_iを基板のR4へ直接割り当てる設定は外す。今回R4のクロックを最初に受けるのはClocking Wizardであり、その出力をMIGへ渡すからである。電気的な出力強度の指定も含む全9項目の差は、mig-setting-differences.jsonに残してある。出力強度の違いを性能改善の成果とは扱っていない。

### E.4 DDR3制御回路を生成する手順を書く

追加するのはfpga/generator/ddr3-nexysvideo.tclである。prjが「どの構成にするか」という設定なのに対し、Tclは「Vivadoへ何をさせるか」という手順である。create_ipでmig_7seriesを作り、CONFIG.XML_INPUT_FILEに前節のprjを渡し、generate_targetなどで必要な生成物を用意する。

作る部品の名前はddr3でそろえる。設定ファイルではddr3、最上位では別の名前という状態になると、部品を接続できない。後のwally.tclが読むddr3.xciも、この生成結果である。xciはIPの設定をVivadoが管理するファイルであり、CPUが実行するプログラムではない。

この段階の確認は、指定したFPGA部品でMIGが生成され、AXIが64 bit、アドレスが29 bitとなることである。29 bitで表せるbyte位置は0から2の29乗−1までで、512 MiBと一致する。実機のDDR3初期化完了は、生成成功とは別に、FPGAを書き込んだ後で確認する。

### E.5 必要な三つのクロックを作る

追加するのはfpga/generator/mmcm-nexysvideo.tclである。基板から来る100 MHzを受けて、MIG入力用100 MHz、基準用200 MHz、CPU用20 MHzを作る。主要な設定値は次のとおりである。

```tcl
CONFIG.PRIM_IN_FREQ {100}
CONFIG.NUM_OUT_CLKS {3}
CONFIG.CLKOUT1_REQUESTED_OUT_FREQ {100}
CONFIG.CLKOUT2_REQUESTED_OUT_FREQ {200}
CONFIG.CLKOUT3_REQUESTED_OUT_FREQ $SYSTEMCLOCK_MHz
```

これはset_propertyへ渡す設定項目の抜粋である。$SYSTEMCLOCK_MHzは、Makefileから渡したSYSTEMCLOCKを1,000,000で割って求める。20,000,000 Hzが20 MHzになる。CPU用の値だけ違う場所に20と直接書くより、同じ入力値から生成すると設定の不一致を防ぎやすい。

Clocking Wizardはクロック生成回路を作り、XDCのcreate_clockは解析用の時間条件を伝える。この二つは別の仕事である。今回の構成ではClocking Wizard側が基板入力の主クロック制約を供給するため、同じ入力に別名のcreate_clockを追加しない。手動でクロックを定義する構成とは、ここが異なる。

### E.6 AHBとAXIの受け渡し条件を合わせる

編集するのはfpga/generator/ahbaxibridge.tclである。Wallyの外部メモリ側はAHB、MIG側はAXIなので、既存のAHBからAXIへの変換IPを使う。データや番地だけでなく、「いま要求している」「受け取れる」「応答に問題があった」といった条件も変換する。

Nexys Videoのボード名に一致する場合に、CONFIG.C_M_AXI_SUPPORTS_NARROW_BURSTを1にする。MIG側だけ幅の狭い転送を有効にしても、手前の変換部が対応していなければ、CPUから最後まで条件がつながらないためである。他のボードの設定を一律に変更しないよう、ボード名の分岐を使う。

確認では、CPU側のアドレスとサイズを変えたときに、対応するAXIのアドレス、転送サイズ、byteの有効信号になるかを見る。値を一回読めたことと、1、2、4、8 byteなどのアクセスを正しく扱えることは別である。実装コードを読む際も、データ線だけでなくHSIZEやWSTRBなどの制御信号まで追う。

### E.7 20 MHzと100 MHzの間をつなぐ

編集するのはfpga/generator/clkconverter.tclである。S側をCPU側、M側をDDR3側として、Nexys Videoの場合はS側をSYSTEMCLOCK、M側を100,000,000 Hzと設定する。このSとMは接続部の向きを示す名前であり、プログラムを順番に実行する二つの段階という意味ではない。

CPUの一周期は50 ns、DDR3側の回路の一周期は10 nsである。CPU側で変わる複数の信号を、DDR3側が別々の途中時刻で読み取ると、一つの要求が崩れる可能性がある。クロック変換IPに要求と応答を預け、両側で正しく受け渡す。第7章のCDCと同じ問題を、AXI全体について扱う。

確認するのは、周波数の数字だけではない。最上位回路でS側へCPUCLK、M側へDDRCLKを実際につないでいるか、それぞれのリセットを接続しているかを見る。設定ファイルの数値と、RTLの配線の両方が一致して初めて、意図した回路になる。

### E.8 最上位回路で部品を配線する

追加するのはfpga/src/fpgaTopNexysVideo.svである。moduleの端子宣言は、この回路と基板との接点を表す。内部ではWally、クロック生成、リセット制御、AHBからAXIへの変換、クロック変換、DDR3制御の実体を置く。付録L.2の「モジュールは部品の種類、インスタンスは置いた実体」という読み方を使う。

次は、全体にある多数の端子から、クロックのつながりだけを抜き出した読み方である。ピリオドの後は部品側の端子名、括弧内はそこへ接続する信号名である。

```systemverilog
.clk_out1(DDRSysCLK), .clk_out2(DDRRefCLK),
.clk_out3(CPUCLK)

.sys_clk_i(DDRSysCLK), .clk_ref_i(DDRRefCLK),
.ui_clk(DDRCLK)
```

上の二行はClocking Wizardの出力、下の二行はMIGの入力と出力である。DDRCLKは、DDRSysCLKと同じ信号名へ置き換えてよい線ではない。MIGが出すユーザー回路用クロックを、DDR3側のAXIに使うという接続を表している。

リセットでは、ClockLockedがクロックの安定、DDRCalibCompleteがDDR3初期化の完了を伝える。CPUを先に動かしてDDR3を読ませると、まだデータを正しく受け取れない。そのためCPU用のリセット回路は、DDR3が準備できるまでCPUを開始させない。解除の時刻はCPUCLKに合わせる。DDR3側のAXIの解除はDDRCLKに合わせる。

AXIには、書く番地、書くデータ、書き込みの応答、読む番地、読み出しデータの五つの経路がある。すべてを「バス」という一本の線で考えてしまうと、返事の配線を見落とす。付属教材ではAW、W、B、AR、Rという信号名の先頭で分け、各経路を端から端まで並べている。

メモリへの読み出しを一回追う。CPUの0x80000010という物理番地が外部メモリとして選択され、AHBからAXIへ渡り、クロック変換を通る。MIGへはアドレスの下位29 bitが渡るため、メモリ内部の位置は0x00000010になる。これは0x80000000から16 byte先を指す。戻るデータはMIG、クロック変換、AHBへの変換を通ってCPUへ戻る。

上位bitを落としてもよいのは、先に外部メモリ範囲を選別しているからである。任意の番地から上位bitを捨ててよいわけではない。この前提を含めて、E.2の範囲設定と最上位の[28:0]という指定を一緒に読む。

図E.1は、fpgaTopNexysVideo.svの接続を読むため、MMCMとMIGの端子名をそのまま残したものである。端子から出る矢印をたどると、コード中で同じ信号名を渡している相手が見つかる。

![図E.1 最上位回路に現れるクロック名とIP端子の接続](figs/nexys-clock-port-map.png)

特に、MIGのsys_clk_iへ入るDDRSysCLKと、MIGのui_clkから出るDDRCLKを取り違えない。CPUCLKとDDRCLKは別の利用側のクロックなので、その間の要求を渡すにはクロック変換回路が必要になる。この図はクロックの配線に絞っており、リセットやメモリ要求の線は省いている。



### E.9 XDCで基板の端子と時間条件を指定する

追加するのはfpga/constraints/constraints-nexysvideo.xdcである。例えば基板の発振器につながるR4を、最上位のclkへ割り当てる。次の二行は、「clkという端子をR4に置き、その端子を3.3 VのLVCMOSとして扱う」という意味になる。

```tcl
set_property PACKAGE_PIN R4 [get_ports clk]
set_property IOSTANDARD LVCMOS33 [get_ports clk]
```

get_ports clkは、設計の中からclkという外部端子を選ぶ命令である。PACKAGE_PINは物理的な端子位置、IOSTANDARDは電気的な規格を指定する。名前だけ合っていても別の位置へ割り当てれば発振器とつながらない。位置だけ合っていても電気規格が違えば正しい接続とはいえない。

スイッチ用のGPIはVADJの既定値1.2 Vに合わせてLVCMOS12、LED用のGPOはLVCMOS25、resetnはLVCMOS15である。端子群によって異なるため、clkのLVCMOS33をすべての端子へコピーしてはいけない。DDR3の端子と専用の時間条件はMIGの設定から供給する。担当するファイルを分け、同じ条件を重複して指定しない。

さらに、外部信号が来る時刻や、外へ出すまでに使える時間を記す。SDカード用SPIでは、CPUの周期50 nsのうち、出力とカード側の応答に時間を割り当てた条件を使う。これはカードがどんなに遅くてもよいという指定ではない。選んだカードがその条件で動くことも確認する必要がある。

### E.10 Linuxへ実機の構成を伝える

追加するのはlinux/devicetree/wally-nexysvideo.dtsである。Linuxは、FPGA内部で何MHzのクロックを作ったかや、基板に何byteのメモリが付いているかを、この文章を読まずに自動で全て知るわけではない。起動時にデバイスツリーを渡して知らせる。

```text
memory@80000000 {
  device_type = "memory";
  reg = <0x00 0x80000000 0x00 0x20000000>;
};
```

このregでは、最初の二つが開始番地、次の二つが容量である。各組の先頭の0は上位32 bitで、後ろが下位32 bitになる。開始0x80000000、容量0x20000000 byteと読む。E.2のEXT_MEM_RANGEとは異なり、ここは「容量−1」ではなく容量を書く。

CPU、時刻計数の基準、UARTにも、回路に合う20,000,000 Hzを指定する。例えばUARTが実際と異なる周波数を前提にすると、文字を送る間隔が合わず、受信側で文字化けする可能性がある。DTSを直しただけでは回路の周波数は変わらない。回路の設定と、それをソフトウェアへ知らせる情報をそろえる作業である。

この初期段階には画像用の予約領域はない。RasterIXを追加した最終版では、第10.8節のとおり、Linuxと画像用の領域をさらに分ける。初期版と最終版のDTSを混ぜて使わない。

### E.11 makeの入口とVivadoの読込先を追加する

編集するのはfpga/generator/Makefileとfpga/generator/wally.tclである。Makefileにはnexysvideoという入口を加える。利用者がmake nexysvideoと指定したときに、次の値が生成手順へ渡るようにする。

```make
nexysvideo: export XILINX_PART := xc7a200tsbg484-1
nexysvideo: export XILINX_BOARD := digilentinc.com:nexys_video:part0:1.2
nexysvideo: export board := nexysvideo
nexysvideo: export SYSTEMCLOCK := 20000000
nexysvideo: export MAXSDCCLOCK := 5000000
```

型番にはFPGAの種類だけでなく、パッケージと速度等級も含まれる。違う部品を指定して配置した結果を、実物へそのまま使うことはできない。MAXSDCCLOCKは起動コードで使う上限である。Linux側のSD設定は別なので、両者の値が違う場合に、同じ処理の設定が矛盾していると即断しない。

Makefileの依存関係では、クロック、DDR3、リセット、変換IPなどを先に生成し、それから全体を生成する。wally.tclではboardがnexysvideoの場合に、fpgaTopNexysVideo.sv、DDR3とMMCMのIP、constraints-nexysvideo.xdcを選ぶ。新しいRTLを保存しただけでは、自動で生成対象へ入らないため、この読込先も必要である。

ほかに、出力先のsimフォルダ作成と、このボード向けの配置配線後の物理最適化を有効にした。最初のボード構成では回路内のロジックアナライザーを追加していない。全変更は11-wally.tcl.patchで確認できる。現在の完成版には描画回路用の追加読込もあるため、初期の変更を学ぶときはこの差分を読む。

### E.12 READMEと答え合わせまでを含める

最後にfpga/README.mdへ、Nexys Videoの生成対象と起動条件を書く。READMEは回路を動かすコードではないが、利用者が正しいボード名、SDカード、端末条件を選ぶために必要になる。専用の別説明書を増やす代わりに、ほかのボードと同じ入口へ情報を足す。

ここまでで、E.2の1ファイル、E.3〜E.10の8ファイル、E.11の2ファイル、READMEの1ファイル、合計12ファイルになる。E.3の設定は新規追加、E.6の共通スクリプトは既存編集というように、新規と変更を区別して数える。

答え合わせは三段階に分ける。まずソースを対象コミットと比較し、意図した12ファイルになったことを確かめる。次にVivadoで生成し、端子、クロック、配置配線、時間条件のレポートを見る。最後に実機で起動、メモリ、文字入出力を確かめる。ソースの一致だけで実機動作の確認を省かない。


## 付録F 発表の前に、理由を含めて答える練習

### F.1 「結局、何を自分で作ったのですか」

短い答えは、「公開CPUをNexys Videoに対応させ、公式の描画回路へ指示を渡す接続と、画像を安全に切り替える接続を加えました」である。詳しくは第5〜10章を使う。CPUやRasterIXの全内部を一から設計したという意味ではない。利用した部分と作った部分を図5.1で指せるようにする。

相手がさらに知りたい場合は、CPUの一回の書き込みが、番地の判定、APBの接続、FIFOを通って描画回路へ届く例を説明する。単なる部品名の一覧より、「相手が忙しい間は書き込みを待たせ、受け取ったときだけ次へ進む」という問題と対処を添えると、接続の仕事が伝わりやすい。

### F.2 「FPGAでなければならないのですか」

二次元ゲームを遊ぶだけなら、一般のパソコンなど別の方法もある。本研究では、CPUと周辺回路の接続を自分で変更し、動作を確かめることが対象なので、内部回路を変更できるFPGAを用いた。パソコン上で同じゲームを作ることと、ゲームを実行する回路の接続を作ることを分けて説明する。

また、FPGAを使うだけで研究上の価値が決まるわけではない。どの接続問題を扱い、どう実装し、どの条件で確認したかが成果である。Wallyの学習者が設計を参照できるという目的は、その具体的な資料と対応させる。教育効果を測っていないのに「学習効率が向上した」とは言わない。

### F.3 「OpenGLなら全部自動でつながるのですか」

OpenGLに沿った関数を使うと、図形や色をプログラムから指定できる。しかし、その呼び出しを回路用の命令へ変え、実機のどの番地へ送るかは別の問題である。今回、その橋渡しをライブラリとWallyBusConnector、APB接続回路が担当する。使いやすい描画の入口と、装置固有の接続の両方が必要だったと答える。

CPUが全画素を直接書く方法との厳密な速度比較は行っていないため、必ずそちらより速いとは言わない。本研究では、図形を指定するプログラムと公開描画回路を使う構成を選び、その接続と動作を示した。別方式との優劣は、条件をそろえた追加比較の問いになる。

### F.4 「命令を送り終わったら、その画像がもう見えていますか」

送信完了だけでは、その画像が表示済みかは分からない。CPUから渡された命令をFIFOが受け取り、描画回路が処理し、画像をメモリへ書き、表示回路が読み出す。先に送った命令の描画は、後の命令をまだ送っている間にも進むので、送信が終わってから初めて描画が始まるわけでもない。送信完了、描画完了、表示先の切り替え完了を別の出来事として確認する。第7章と第10章の図で、この三つの位置を示す。

完了回数が増えたという記録も、ディスプレイの全画素をカメラで確認した記録ではない。本研究では回路の完了記録、メモリ内の画素比較、録画の動きを組み合わせた。異なる確認を組み合わせる理由を、どれか一つが不十分だからというだけでなく、見ている対象が違うからと説明する。

### F.5 「部分描画は、描くものを省いているのですか」

前と同じまま残っている画素を再利用し、変化した結果に必要な場所を描き直している。例えばボールが動いたら、古い位置を消し、新しい位置へ描く。ただし古い位置に壁が重なれば壁も復元する。さらに画像AとBに残る前回の内容が違うので、二枚の履歴を別々に持つ。

同じゲーム状態から、CPU側の比較用プログラムで全体を塗った期待画像を作り、実機の画像と比較する。これにより、速さのために必要な物体を省いていないかを確かめる。期待画像の作り方は12.5節で説明した。確認したのは保存した試行の範囲であり、すべての入力や全時刻について正しさを数学的に証明したという意味ではない。

### F.6 「測定結果のどこまでが確かなのですか」

まず、どの構成の値かを答える。標準DVI構成での実機受け入れ確認と、実験用HDMI構成での方式比較は、第13.1節で分けている。次に、何を数えた値かを答える。例えば一秒当たりの画面切り替え完了数を、そのまま実際に見えた新画像のFPSと言い換えない。

最後に、比較から何が言えるかを答える。同じ状態列で描画準備時間と命令量が減ったことは、仕事量を減らす改善を裏付ける。一方、それだけでCPU内部の全命令やキャッシュの費用まで分かったことにはならない。「結果が分かった部分」と「さらに分けて測る部分」を、第13章の具体的な数字で説明する。

## 付録G RasterIXとの接続を自分で組み立てる

### G.1 この付録で再現する設計と答え合わせの場所

本付録は、Nexys Video上でWallyが起動するところから、公式RasterIXを接続する設計を再現するための説明である。CPU自体のRTLや、公式RasterIXの内部の描画算法を一から書き直す課題ではない。設計する対象は、両者の間の接続、共有メモリ、表示切り替え、ソフトウェアの送信口である。

完成版の主な値は、CPU20 MHz、RasterIX100 MHz、画面640×480、内部作業領域65,536画素、命令ポート0x10080000、画像用予約領域32 MiBである。まずこの組み合わせを再現し、動く基準ができてから値を変える。理由を理解せずに複数の値を同時に変えると、どの約束が崩れたか判断しにくい。

付属の`再現資料/詳説用ソース/Wally`には、固定した完成版から取得したファイルを置いた。`RasterIX`フォルダには、解説に使った公式サブモジュールのファイルを置いた。`manifest.json`で取得元コミットと各ファイルのSHA-256を確認できる。これらのソースは説明用にコメントを書き換えた版ではなく、指定版の内容を保持した資料である。

`RasterIX導入.patch`は導入コミット5b6adcd97の差分であり、初期の完成版d3e181ac4までの全変更ではない。導入後に行った画像初期化やゲーム追加などの変更は、付録Aのコミット表と区別して読む。導入時点の再現と、論文が評価する完成版の再現を混ぜない。

### G.2 最初に部品同士の約束を表にする

回路を書く前に、入口、出口、クロック、待ち方を決める。入口の名前を決めるだけでは足りない。例えば「CPUが書ける」と決めても、データが何bitで、FIFOが満杯ならどうなるかを決めていなければ、回路を最後まで配線できない。

| 決める対象 | 本設計の約束 | その約束を満たす場所 |
|---|---|---|
| CPUからの命令 | 整列した32 bit書き込み | WallyBusConnectorとrasterix_apb |
| 転送の終わり | 最後の一語を+0x04へ書く | CmdLastとAXI StreamのTLAST |
| 受け側が満杯 | APBの完了を待たせる | PREADYとCmdReady |
| CPUと描画器の速度差 | 非同期FIFOを通す | axiscdc |
| 画像の保存先 | Linuxと重ならない予約領域 | dtsとCMakeLists |
| 切り替え完了 | 新画像の最初の読出し返却まで待つ | rasterixdisplay |
| 公式コードとの境界 | 公式の入口を使い、外側で変換 | IBusConnectorとRTLラッパー |

この表の各行について、「別の値にすると、どのファイルを一緒に変えるか」を答えられれば、設定を暗記した段階から一歩進める。例えば命令ポートの番地は、CPU側のアドレス判定だけでなく、mmapとデバイスツリーも同じ値にそろえる必要がある。

### G.3 外部I/OをWallyの構成に追加する

Wallyは構成値を一つのファイルだけで完結させず、構成ファイルの値をパラメータ構造体へ渡して各回路で使う。このため、新しい外部I/Oを追加するときも、その受け渡し経路へ値を通す。[Console26]

本導入では`EXT_IO_SUPPORTED`、`EXT_IO_BASE`、`EXT_IO_RANGE`を追加した。SUPPORTEDは外部I/Oを使うか、BASEは先頭アドレス、RANGEはその範囲を定める。通常の構成では無効を既定にし、`fpganexysvideo_rasterix`という派生構成で有効にする。これは、描画回路を使わない既存のボードまで常に同じ周辺回路を要求することを避けるためである。

![図G.1 外部I/Oの設定値が回路へ渡るまで](figs/config-chain.png)

具体的には、`config/rv64gc/config.vh`などの基底構成、`config/derivlist.txt`、`src/cvw.sv`、`config/shared/parameter-defs.vh`を対応させる。構造体のメンバだけを増やして各構成の値を用意しなければ、別構成の生成で未定義や値の不一致が出る可能性がある。今回、描画に使わないrv32系の構成ファイルにも追加があるのは、このパラメータの入口をそろえるためである。

読み方は、まずderivlistで選んだ構成を見て、生成されるconfig.vhの値を確認し、その値がparameter-defsからcvw_tへ入ることを追う。Vivado側ではwally.tclが選択済み構成のEXT_IO_SUPPORTEDを確認している。外部I/Oを無効にした構成でRasterIXを生成しようとすると、ここでエラーにする。

### G.4 アドレス判定からAPBの戻り値までを配線する

CPUが0x10080000へアクセスしても、その番地を選ぶ回路がなければRasterIXには届かない。`adrdecs.sv`で外部I/Oの領域を判定し、`uncore.sv`へその選択結果を渡す。`uncore.sv`ではAPBブリッジが扱う周辺回路の数を8にし、外部I/OをPSELのbit 7へ対応させる。[Console26]

書き込み要求を外へ出す線だけでは不十分である。CPUへ返すPRDATAと、その転送を完了してよいかを示すPREADYも戻す。PREADY=0なら待ち、1ならその転送を完了できる。もしPREADYを常に1に結線すると、FIFOが満杯でもCPUが次へ進み、命令を受け取れなかった事実を伝えられない。

```systemverilog
if (P.EXT_IO_SUPPORTED) begin : extio
  assign PSELEXT = PSEL[7];
  assign PREADY[7] = PREADYEXT;
  assign PRDATA[7] = PRDATAEXT;
end else begin : extio
  assign PSELEXT = 1'b0;
  assign PREADY[7] = 1'b1;
  assign PRDATA[7] = '0;
end
```

この抜粋は`uncore.sv`の外部I/Oの分岐である。有効な場合は外部回路の返事を使い、無効なら外部選択を0にする。未使用の入力が不定のまま残らないよう、戻り値の扱いも決めている。

外へ出すAPB信号は、`wallypipelinedsoc.sv`を通してFPGAの最上位回路へ出す。そのため、既存のテストベンチや他ボードの最上位回路にも、追加したポートの接続を反映する。RasterIXを実装しないところでは、未使用として結線する。特定のゲームの信号名をCPU内部へ直接追加するより、汎用の外部APBとして出す方が、別の周辺回路にも用途を広げやすい。

### G.5 APBの変換回路を三部分に分けて書く

`rasterix_apb.sv`は、データの選択、受け渡しの条件、読出しと状態保存、の三部分に分けて読む。データの選択は7.7節の上半分・下半分の選択である。受け渡し条件は、アクセス段階にあり、32 bitすべてが有効で、命令用番地であることを調べる。

```systemverilog
assign CommandWrite = PSEL & PENABLE & PWRITE & WordWrite
                      & (PADDR[7:3] == 5'b0);
assign ResponseRead = PSEL & PENABLE & ~PWRITE
                      & (PADDR == 8'h18);
assign CmdValid = CommandWrite;
assign CmdLast = PADDR[2];
assign CmdData = WriteData;
```

原ソースの式を、紙面に収まるように改行した抜粋である。PADDRの上位5 bitが0という条件は、下位8 bitで0x00から0x07に相当する。ソフトウェアはこの範囲に対して0x00と0x04の整列した書き込みだけを使う。PADDR[2]で通常語か最後の語かが決まる。

```systemverilog
assign PREADY = CommandWrite ? CmdReady :
                ResponseRead ? RespValid : 1'b1;
assign PRDATA = {(XLEN/32){ReadData}};
```

PREADYへの代入は、命令書込みならFIFOの空き、応答読出しなら応答の有無に合わせて待つことを表す。それ以外のアクセスでは待たせない。PRDATAへの代入は、32 bitの読出し値をXLEN/32個並べる。64 bit構成なら同じ32 bitを上下へ複製し、どちらのレーンから32 bitを取り出しても同じ値になるようにする。

状態を保存する部分では、FrameDoneを受けたらFrameCountを1増やし、そのときのFrameAddrをDisplayAddrへ保存する。リセット中なら両方を0にする。この部分はクロックに合わせて値を覚える処理なので`always_ff`を使う。一方、アドレスに応じて読出し値を選ぶ部分は`always_comb`である。C言語のようにファイルの上から毎回順番に実行すると考えず、同時に存在する選択回路とレジスタとして読む。

図G.2の各行は、rasterix_apb.svの異なる役割を表している。上段ではデータのどちら半分を使うか、中段では今のアクセスを待たせるか、下段では完了回数など何を覚えるかを読む。

![図G.2 APBのデータ選択と待ち条件と状態保存を分ける](figs/apb-concurrent-circuits.png)

三つの行は、CPUが上から順に呼び出す三つの関数ではない。FPGA内では、入力に応じた選択回路と、クロックで値を覚える回路が同時に存在する。FrameCountの更新にはクロックが関係する一方、PREADYは現在のアクセス条件と受け側の状態から選ばれる。



### G.6 配線する前に受け渡しの試験を置く

APB回路だけを試す場合、CPU全体やDDR3を用意する必要はない。試験コードがCPU側の信号を代わりに出し、FIFO側のReadyを意図的に止める。これにより、設計した「待つ」条件を短い試験で確認できる。

付属の`tb_apb.sv`は、上半分と下半分の書き込み、FIFO側の待ち、応答読出しの待ち、識別値、完了回数を確認する。例えば下のassertは、受け側を待たせた間、PREADYが上がらず、データも終端の印も維持されることを確かめる。[E1]

```systemverilog
assert(!Ready && CmdValid && CmdData==expected
       && CmdLast==address[2])
  else $fatal(1,"command changed during backpressure");
```

assertは条件が成立するかを試験中に検査する記述である。失敗すると、ここでは$fatalにより試験を停止する。assertが通ったという結果は、書いた条件と試した入力で成立したことを意味する。例えば部分byte書込みや任意のクロック比を網羅した試験ではないので、試していない性質までこの結果に含めない。

付録Cのスクリプトを使うと同じ最小試験を実行できる。編集前に保存版が通ることを確認し、自分の実装へ差し替えた後も同じ受信語と回数になるかを見る。この段階を通してから、FIFOや描画器をつなぐと、停止箇所を絞りやすい。

### G.7 命令と応答のクロック境界を作る

`axiscdc.tcl`で生成するFIFOは、データ4 byte、深さ512、非同期クロック、有効なTLASTを持つ。必要な情報は32 bitデータと終端の印なので、byteごとの有効信号TKEEPとTSTRBは使わない。[Console26]

```tcl
set_property -dict [list CONFIG.TDATA_NUM_BYTES {4} \
    CONFIG.FIFO_DEPTH {512} CONFIG.IS_ACLK_ASYNC {1} \
    CONFIG.HAS_TLAST {1} CONFIG.HAS_TKEEP {0} \
    CONFIG.HAS_TSTRB {0}] [get_ips $ipName]
```

同じIPの生成結果を、命令用と応答用の二か所に置く。命令用では入口がCPUCLK、出口がDDRCLK、応答用では入口がDDRCLK、出口がCPUCLKとなる。クロックの向きだけでなく、入口側のリセットにどの領域のリセットを渡すかも見る。

FIFOの512という値は、画面の横幅や命令リストの大きさではない。32 bitの語を512個置くため、データ部分だけなら2048 byteであり、別途終端の印なども保持する。C++側で確保する1 MiBのリストは、このFIFOへ一度に丸ごと入る必要はない。受け側が順に消費する間、CPUは空きを待ちながら続きを送る。

### G.8 共有メモリと表示の接続を完成させる

CPU、描画器、表示器がDDR3を使う構成では、CPUの外部メモリ経路を共有接続回路のS00へつなぎ、GPUをS01、表示器をS02へつなぐ。RasterIXの接続を追加した後も、CPUのSD起動や通常のメモリ読書きが必要である。GPUだけがDDR3へつながれば完成、とはならない。

`rasterix.sv`は多数のAXI信号を持つが、最初は五種類のまとまりとして読む。AWが書込み先、Wが書込みデータ、Bが書込み応答、ARが読出し先、Rが読出しデータである。VALIDとREADYが各まとまりの受け渡しを決める。例えばARのアドレスをつないでもRの返り道がなければ、CPUやGPUは読出しを完了できない。

![図G.3 AXIの五つのまとまりと要求側から見た向き](figs/axi-directions.png)

図G.3では一本の矢印に一群の信号をまとめた。AWとWは別のまとまりなので、任意のAXI相手でいつでも同じ周期に受理されるとは限らない。本構成の表示設定の小さな制御接続は、採用したDVI部品の受理方法を前提にしている。汎用のAXI-Lite制御器を新しく設計したと説明するものではない。

表示切り替えは10.5〜10.6節の約束で組み立てる。特に「FrameDoneをどの条件で出すか」を決めてからソフトウェアの待ち方を実装する。意味が曖昧な完了信号を先に配線すると、ソフトウェアが画面を早く再利用しても、どちら側の設計が誤っているか判断しにくい。

### G.9 ソフトウェアが送る単位と受け側の単位をそろえる

`writeData`のsizeとoffsetはbyte単位で受け取る。一方、内部のバッファはuint32_tの配列なので、offset/4で開始要素を求め、size/4回の書き込みを行う。例えばsize=12、offset=8なら、配列の要素2、3、4を送り、最後の要素4だけをCMD_LASTへ書く。[Console26]

| ループ内のi | 読む要素 | 書くレジスタ | その語の意味 |
|---:|---:|---|---|
| 0 | 2 | regs[0] | 通常の語 |
| 1 | 3 | regs[0] | 通常の語 |
| 2 | 4 | regs[1] | 今回の転送の最後 |

最後の語の印は、「一画面の描画がすべて終了した」という印ではない。あくまでライブラリがwriteDataで依頼したこの転送の終端である。画像一枚を作るために複数の転送が行われることもある。

`checkRange`は、バッファ番号が範囲内か、sizeとoffsetが4の倍数か、offsetからsize byteが領域内へ収まるかを調べる。サイズの単位を間違え、12語のつもりでsize=12を渡すと、実際には3語しか送られない。逆にbyte数をさらに4倍すれば、意図した範囲の外まで読んでしまう。送信口を自分で作るときは、単位を関数ごとに書き出す。

図G.4は、offsetが8 byte、sizeが12 byteの場合を線で追ったものである。左の配列では要素[2]から三語を読む。右では最初の二語が同じCMDへ入り、最後の一語だけCMD_LASTへ入る。

![図G.4 転送元の配列の位置と転送先のレジスタを対応させる](figs/command-offset-vs-register.png)

一語ごとに配列の添字が増えるので、転送先の番地も増やすと誤解しやすい。しかしCMDは命令を入れる入口である。先ほど書いた語はFIFOへ進むため、次の語も同じ入口へ書ける。最後の印はこの転送範囲の終わりを示し、一画面の表示完了を表すものではない。



### G.10 ビルドに追加したファイルを読み込ませる

ソースファイルを置いただけではVivadoに読まれない。`wally.tcl`でラッパーRTL、公式RTL、IP、制約、共有メモリの設計を追加する。パッケージ定義を使うSystemVerilogは、定義を先に読み込めるようにコンパイル順序を整える。`include_dirs`は、includeされたファイルを探す場所を指定する。[Console26]

公式RasterIXに含まれるAXI用部品と、Wally側の別依存関係にある同名の部品が衝突しないよう、RasterIX由来のファイルはライブラリ`rasterix`へ入れている。これは、描画算法を変更する処理ではなく、Vivadoがどのモジュールを採用するかを整理する処理である。

Makefileでは`nexysvideo-rasterix`が、ボード名、派生構成、RasterIX有効化、必要なIPをそろえて選ぶ。回路の最上位だけ有効にし、IP生成の依存関係を追加し忘れると、モジュールが見つからず生成できない。逆に古いIPが残った場所では、一見通っても別の条件を使っている可能性があるため、14章で示した新規クローンからの再現が役立つ。

### G.11 段階ごとに期待する結果を決める

接続を設計したら、最後にゲーム画面だけを見て終わらせず、段階ごとに確認する。下表の結果は再現時に読者が確かめる項目であり、この原稿改訂で再測定した結果ではない。

| 段階 | 実施する確認 | 成功時に言えること |
|---|---|---|
| 構成を生成 | 展開されたパラメータと読込ファイルを照合 | 意図した回路を生成対象にした |
| APB単体 | 待ち、32 bitレーン、受信回数を試験 | 試験した条件で語を正しく渡した |
| 表示制御単体 | 古い読出しを残してAckを監視 | 試験した条件で早過ぎる完了を出さない |
| 配置配線 | クロック、タイミング、CDC、DRCを確認 | 指定した実装条件の結果を得た |
| 実機起動 | DDR利用、UART、Linux起動 | CPU側の起動経路が動いた |
| 描画と表示 | メモリの画素比較と映像確認 | 計算結果と外部出力を別々に確認した |
| ゲーム | 入力、進行、衝突、終了を確認 | 対象のゲームとして進行した |

各段階の結果を、ソースのコミット、bitstream、dtb、実行ファイルの識別情報と一緒に保存する。古いbitstreamでの成功と、新しいソースの状態を結び付けてしまうと、第三者は同じ結果を作れない。どの設計を確かめたかを残すことも、再現可能な設計の一部になる。

## 付録H 設定を変えるための計算と設計判断

### H.1 内部作業領域を増やす案を計算する

現在の内部作業領域は2の16乗で65,536画素である。これを2の17乗、131,072画素へ増やす案を考える。307,200画素の画面を収めるために必要な帯は切り上げて3本、各帯は480÷3=160行となる。一帯は102,400画素で、131,072画素に収まる。コネクタのバッファ数は2×3+1=7個になる。

| 項目 | 現構成LG=16 | 検討例LG=17 |
|---|---:|---:|
| 内部作業領域 | 65,536画素 | 131,072画素 |
| 必要な帯数 | 5 | 3 |
| 一帯の高さ | 96行 | 160行 |
| 一帯の画素数 | 61,440 | 102,400 |
| コネクタの1 MiBバッファ | 11個 | 7個 |

右列はコードと寸法から求めた検討値であり、実装して動作を確認した値ではない。内部メモリを増やせばFPGA内の資源が必要になる。命令の準備量が減る可能性があっても、配置配線の混雑や周波数の条件が変わるため、速くなることまではこの表だけで分からない。

変更する場合は、RTLの`FRAMEBUFFER_SIZE_IN_PIXEL_LG`とCMakeの`RIX_CORE_FRAMEBUFFER_SIZE_IN_PIXEL_LG`を一致させる。片方だけ変えると、ソフトウェアが一帯に描けると思う画素数と、実際の内部メモリの容量が食い違う。回路生成後にはBRAMの合計、階層別使用量、タイミングを調べ、同じ画像と状態列で速度を比較する。[RasterIX][Console26]

### H.2 画面の大きさを変えるときの落とし穴

640×480を320×240へ変える案では、76,800画素なのでLG=16の内部作業領域でも2本の帯が必要になる。一帯は120行で38,400画素になる。これだけを計算して「解像度変更は終わり」としてはいけない。描画の寸法、表示回路の寸法、画素クロック、フレームバッファの行の幅、ゲームの座標が一致する必要がある。

例えば表示回路が引き続き一行640画素を読むのに、ソフトウェアが一行320画素分だけ保存すると、表示側は隣の行を続けて読んでしまう。これはGPUの描画速度以前に、メモリ中の画像の並び方が合っていない問題である。

また、公式Dispatcherは高さを帯数で整数除算する。別の解像度を選ぶ場合、最後の帯をどう扱うかを実装から確かめる必要がある。本構成の480行は5で割り切れるが、すべての高さがそうなるわけではない。「画素数が内部容量以下に分割できる」という計算だけでは、すべての行を扱える保証にはならない。[RasterIX]

図H.1は、横320と640の違いを、見やすい横4と8の違いに置き換えた模式図である。画素の番号0〜7がメモリに順に並ぶ点は同じだが、どこまでを一行と数えるかが異なる。

![図H.1 画像を保存する一行と読み出す一行の幅が違う場合](figs/row-stride-mismatch.png)

保存側が4画素で次の行へ進んだつもりでも、表示側が8画素を一行として読むと、元の二行を一行につなげてしまう。先頭アドレスが正しくても、行を進める幅が一致しなければ画像は崩れる。このため解像度の変更では、描画側と表示側の両方を確認する。



### H.3 CPUを速くしたいときに一緒に見る場所

CPUを20 MHzから別の周波数へ変える場合、最初に変える対象はMMCMの出力と、そのクロックを使う接続条件である。6.3節のcreate_clockの例で解析上の周期だけを変えても、基板から来る100 MHzや、CPUへ実際に届くクロックの周期は変わらない。この例のBoardClockという名前を、完成版のXDCに書かれた設定だと解釈しない。本構成の入力クロック制約はClocking Wizardが生成する。実際のクロックを作る設定と、解析へその条件を伝える制約の両方を合わせる必要がある。

さらに、起動用プログラムはSYSTEMCLOCKを使ってUARTやSDの速度を設定する。ここを古い20 MHzのままにすると、回路が動作していてもUARTの通信速度がずれ、文字化けする場合がある。Linuxへ渡すクロック情報、クロック変換IPの条件、CPU領域を含む時間解析もそろえる必要がある。[Console26]

![図H.2 CPUクロック変更で確認する関連箇所](figs/change-dependencies.png)

新しい周波数でbitstreamが生成できても、時間条件を満たしたとは限らない。まず負の時間余裕や未制約の経路がないか調べ、その後、起動とゲームを確認する。性能を比較するときは、解像度や描画方式を同じにし、クロックを変えたことでどの処理時間が変わったかを見る。

読み終わったら、次の変更を実行せずに考えてみる。CPUを25 MHzにする場合、Makefileの数字だけでなく、クロック生成、時間条件、UART、時刻計数、DTSをどのようにそろえる必要があるか。実物のメモリ容量を変えないままEXT_MEM_RANGEだけ増やしたら何が起こるか。この二つを理由付きで説明できれば、既存設定の写し方だけでなく、設定同士のつながりを理解できている。

### H.4 アドレスを変える場合の三者の一致

命令ポートの基点を変える場合、回路のEXT_IO_BASE、Linuxへ伝えるdtsのreg、アプリケーションのmmapをそろえる。さらに既存のUARTやSDなどの番地と重ならないか調べる。空いているように見える値を一か所へ書くだけでは、接続先を変更したことにならない。

画像用領域を変える場合は、GRAM_MEMORY_LOC、色・深度・ステンシルのオフセット、予約領域の開始と大きさを対応させる。例えば本設定の色画像の一つは、基点0x9e000000とオフセット0x01e00000を足して0x9fe00000となる。オフセットをすでに物理アドレスだと思って渡すと、基点を二度加えた誤った値になり得る。

| 値の種類 | 現構成の例 | 意味 |
|---|---|---|
| I/Oの物理アドレス | 0x10080000 | 命令レジスタがある場所 |
| GPU用メモリの基点 | 0x9e000000 | 予約領域の開始 |
| 色画像のオフセット | 0x01e00000 | 予約領域の開始からの距離 |
| 色画像の物理アドレス | 0x9fe00000 | CPU側の番地として表す画像位置 |
| DDR3内のオフセット | 0x1fe00000 | DDR3先頭0x80000000からの距離 |

これらの値はすべて「アドレスに関係する数」だが、基準にする開始位置が違う。設計を変更するときは、変数名だけでなく、どこから測った値なのかを式で確認する。

図H.3では、画像Aの物理アドレス0x9fe00000を固定し、二つの先頭からの距離を別々に計算する。下段の値は、画像が二か所に複製されたことを意味しない。同じ場所を異なる基準から数えている。

![図H.3 同じ画像の場所を異なる先頭からの距離で表す](figs/three-address-origins.png)

DDR3制御側へ渡す距離なら0x80000000を基準とし、描画用領域の先頭からの画像オフセットなら0x9e000000を基準とする。どちらもオフセットと呼ばれるため、変数名だけで判断せず、何の先頭を加え戻すと物理アドレスになるかを確認する。



### H.5 理解できたかを確認する課題と解答

課題1は、32 bitの最後の一語を送るとき、regsの添字と物理アドレスを答えることである。解答は添字1、0x10080004である。根拠は、uint32_t一要素が4 byteで、CMD_LASTが+0x04だからである。CPU自体が64 bitだから添字を8倍する、という計算はしない。

課題2は、FIFOが3クロック満杯で、4番目の立ち上がりで空いた場合、受け取る語数を答えることである。解答は1語である。最初の3回はValidが1でもReadyが0なので受理しない。4回目に両方1となって初めて受理する。同じ語を4回送ったとは数えない。

課題3は、幅640のRGB565画像で(x,y)=(3,2)の画素の位置を計算することである。先頭からの画素番号は2×640+3=1283、byteのオフセットは2566=0x0a06である。画面Aなら0x9fe00a06から2 byteを使う。横座標と縦座標を逆にすると、別の行の画素を書いてしまう。

課題4は、完了回数を読む値が42で、新しい切り替え後に43になったとき、何が分かったかを説明することである。解答は、回路で定めた切り替え完了が一回通知された、である。画像の全画素が正しいことや、ディスプレイの描画が終了したことまでは、この値だけでは分からない。

課題5は、古いボールを黒で消したときに文字の一部まで消えた場合、どの処理を確認するかを答えることである。解答は、変更領域に重なる文字も描き直し対象へ含めたか、元の描画順を守ったか、対象バッファに対応する履歴を使ったか、である。新しいボールだけを描けばよいという方法では、消した文字は復元されない。

課題6は、CPUを速くした後にUARTが文字化けした場合、何を疑うかを答えることである。解答の一つは、起動コードやLinuxが計算に使うクロック値と、実際のCPUクロックが合っていない可能性である。ただし配線や端末設定でも文字化けするため、これだけを原因と断定せず、変更前後の条件を照合する。

答えの数値だけでなく、その値を確認するファイルと信号を指せるかを確かめる。分からなかった項目は、第7章、10章、11章、14章と付録Gへ戻る。単語を言えることより、どこで値が変わり、どこで受け渡しが完了するかを追えることが、同じ接続を設計するための理解になる。



## 付録I 命令の受け渡しとクロック境界を設計する

この付録では、CPUの一回の書き込みを出発点にして、APB、AXI4-Stream、FIFO、非同期FIFOの関係を説明する。到達点は、名前を覚えることではなく、配線を変えたときに「どの条件を保たなければ命令を失うか」を説明できることである。本文7章の概要から入り、I.1〜I.8で動作を追い、I.9以降で採用理由と確認方法を検討する。

### I.1 まず保存する場所と接続の約束を分ける

まず、描画命令の三語D0、D1、D2が、CPUの使うメモリに並んでいる場面を考える。CPUはD0を読み、MMIOの命令口へ書く。接続回路はその書き込みをFIFOへ渡す。D0はそこで一時的に保存され、FIFOの出口からRasterIXへ渡る。次にD1、D2も同じ道を進む。ここでD0などは、具体的な命令値を省いて順番だけを表す名前である。

この道の途中で、CPUが使うメモリの保存場所をコマンドバッファ、回路側の順序付きの保存場所をFIFOと呼んでいる。APBやAXI4-Streamは保存場所の名前ではなく、その場所の間で語を渡す規則の名前である。まず、保存する物と、渡すための信号を分けて読めばよい。

CPUのメモリにある命令バッファ、CPUとRasterIXの間にあるFIFO、RasterIX内部の画素用作業領域は、どれもデータを保存するが、同じものではない。命令バッファには、CPUが用意した描き方の数値列が入る。FIFOには、CPUが送信した数値列のうち、まだ次へ渡していない語が入る。画素用作業領域には、描画処理によって計算した色などが入る。

一方、APBとAXI4-Streamは保存場所の名前ではない。「どの信号を出し、どの瞬間に一回の受け渡しが成立するか」という接続の約束である。箱をFIFO、箱の入口と出口で使う受け渡し方法をAXI4-Streamと考えると、同じ経路に両方の名前が出ても矛盾しない。

![図I.1 命令の保存場所と接続方式を分けて追う](figs/command-route-detail.png)

図I.1の黒い矢印は命令データが進む向き、青い矢印は受け取り可否が戻る向きである。淡い青の領域はCPUCLKで動く部分、中間の青の領域はDDRCLKで動く部分を表す。色の違いは速い回路と遅い回路の優劣ではない。どのクロックの立ち上がりで受け渡しを数えるかが違うことを表している。

Wallyの既存のバス変換を経て、CPUの要求はAPBで`rasterix_apb`へ届く。この追加回路が、番地と書き込みデータをAXI4-Streamのデータ・有効・終端へ変換する。FIFOを出た先は、公式RasterIXの命令入力である。RasterIXがDDR3へ画像を書き出すAXIメモリ接続は、図の命令の道とは別に存在する。

### I.2 一語と一命令と一枚の画像は大きさが違う

この接続の一語は32 bit、すなわち4 byteである。一回の書き込みは、その一語を運ぶ。一つの描画操作を指定するために必要な語数は操作により異なる。一語を受け取ったから一個の図形を描き終えた、とは限らない。さらに、一個の図形を描くと多数の画素が変わる。

説明用に、命令列がA、B、Cという三語からなる場合を考える。Aなどの文字は32 bitの値に付けた名前であり、実機に送れる命令コードではない。CPUはメモリからAを読み、命令レジスタへ書く。次にBを読み書きし、最後のCは終端用レジスタへ書く。三語は順にFIFOへ入る。受け側は同じ順で取り出し、意味を解釈する。

`WallyBusConnector.hpp`の`writeData`は、この読み出しと書き込みをループで行う。CPUが完成済みの命令列を送る区間と、描く図形から命令列を作る区間は別である。本研究のプログラムは`NoThreadRunner`を使うため、「CPUが常に次フレームの命令を作りながら前フレームを描いている」とは説明しない。回路の並行動作と、プログラムの実行順は分けて確認する。

### I.3 APBで一回の書き込みが終わる瞬間

APBでは、最初に対象回路、番地、書き込みデータを提示する準備段階がある。その後、`PENABLE`を1にするアクセス段階へ進む。アクセス段階で対象が選ばれ、`PREADY`も1になったクロックの立ち上がりで、その転送が成立する。`PREADY`が0なら、送り手は同じ要求を保って待つ。

今回の変換回路は、命令への書き込み中、FIFOの`CmdReady`を`PREADY`へ返す。したがってCPUに「書き込みが終わった」と返す瞬間と、FIFOがその一語を受け取る瞬間が対応する。受け取っていないのに完了を返すと、その語を失う。受け取った後も同じ転送を何回も成立させると、語が重複する。この対応を守ることが変換回路の重要な役割である。

`CmdValid`は、有効な命令書き込みのアクセス段階で1になる。待っている間も1のままでよい。1である時間の長さだけで受け取った回数を決めるのではなく、次節の成立条件で数えるからである。APB試験では、`CmdReady`を意図的に0にしてもデータと終端が保たれることを確認している。

### I.4 AXI4-Streamでは有効と受取可の両方を見る

AXI4-Streamのこの接続では、データを`TDATA`、有効を`TVALID`、受取可を`TREADY`、列の終端を`TLAST`で表す。送り手はデータを用意したら有効を1にし、受け渡しが成立するまでデータと終端を保持する。受け手は、受け取れるときに受取可を1にする。[AMDAXI]

同じクロックの立ち上がりで、有効と受取可がともに1なら一語を渡す。片方が0なら渡さない。例えば下表で、Bを提示する時間は長いが、Bの転送回数は一回である。次の立ち上がりに別の語を用意し、有効と受取可が1なら、続けて別の一語を渡せる。

| 立ち上がり | データ | 有効 | 受取可 | この瞬間に渡る語 |
|---|---|---:|---:|---|
| 1 | A | 1 | 1 | A |
| 2 | B | 1 | 0 | なし |
| 3 | B | 1 | 0 | なし |
| 4 | B | 1 | 1 | B |
| 5 | C | 1 | 1 | C |

この表は受け渡し規則を説明する例であり、実機波形を測定した表ではない。また、FIFOの入口で成立した転送と出口で成立した転送は別々に数える。入口で受け取ったBが、同じ瞬間に出口からも出るとは限らない。

### I.5 FIFOの出口が止まっても入口はすぐには止まらない

FIFOは、先に入れた語から取り出す記憶回路である。説明用に四語入るFIFOを考える。中にAとBがあり、RasterIX側が受け取りを止めると、Aを出口に提示したまま保持する。その間も空きがあればCとDを入口から受け取れる。四語とも埋まった後でEを入れようとすると、入口側も受取可を0にする。

![図I.2 停止がFIFOの出口からCPUへ伝わる順序](figs/backpressure-four-stages.png)

図I.2では、右端が次に取り出す語である。箱は待ち順を表す。描画回路の停止、FIFOの空き、CPUが待つ時点を分けた。実機の設定は512語である。四語という数は動きを図に収めるために選んだ。描画回路が再びAを受け取ると、空きが増える。ただし非同期FIFOでは、その空きの情報が入口側に伝わるまで時間があるため、CPUが同じ瞬間に再開するとは限らない。

受け手から送り手へ、受け取れないことを伝えて止める仕組みをバックプレッシャーと呼ぶ。この仕組みがあれば、受け手が一時停止しても保存容量を超えて書き込まない。永久に停止した場合は永久に処理が進まない可能性が残る。データを失わないことと、必ず有限時間で完了することは別の性質である。

### I.6 20 MHzと100 MHzだけでは処理の速さを比べられない

20 MHzのクロックは50 nsに一回、100 MHzのクロックは10 nsに一回立ち上がる。しかしCPUが一周期ごとにAPBへ新しい一語を書けるわけではない。メモリから値を読み、番地を計算し、繰り返し条件を調べ、バス転送を行う。キャッシュ、命令の依存、バスの待ちも関係する。

描画回路についても、一周期ごとに一枚の画像を描き終えるわけではない。例えば画像を一色で消去する仕事は、短い指示で多数の画素を書き換える。説明用に一周期に一画素を処理する回路を考えると、64画素を塗るには64周期分の仕事になる。この64周期はRasterIXの実測値でも、その実装の正確な周期数でもない。「短い指示に長い仕事が対応し得る」ことを示すための例である。

したがって、CPUの方が低い周波数だから受取可を無視できる、とは言えない。反対に、この説明だけでCPUが実際にFIFOを満杯にした、とも言えない。初期の記録E1〜E5には、実機のFIFO入口で待たされた時間の計測はなかった。追加実験E6では、命令書き込み中に入口の受取可が0だった周期を数え、16語と512語の両方で待ちを確認した。全占有量の時系列や、内部の停止原因ごとの時間は未計測である。この一般説明だけから満杯を想像することと、E6の実測結果を使うことを区別する。

### I.7 公式RasterIXに受け取りを止める処理がある

固定した公式版の`CommandParser.v`には、フレームバッファ操作を受けた際に受取可を0にし、`WAIT_FOR_IDLE`という状態へ移る処理がある。その状態では、描画処理、フレームバッファ、テクスチャ処理などが完了したかを調べてから先へ進む。`InternalFramebufferCommandHandler.v`の消去処理も、対象アドレスを進めながら作業する。[RasterIX]

これは「遅いかもしれない」という推測だけで作った根拠ではない。公式回路に停止条件があることをソースで確認した根拠である。ただし、このパーサの前には別の処理や保持段もある。パーサの受取可が0になった同じ周期に、最上位の命令入力やCPUまで必ず止まる、という意味ではない。停止は途中の空きと制御に応じて伝わる。

読み直すときは、公式版`9fdcf97a31b2e4247594e06d605871980cd5e9e1`の`rtl/RasterIX/CommandParser.v`で`OP_FRAMEBUFFER`、`WAIT_FOR_IDLE`、`s_cmd_axis_tready`を検索する。その後、`RasterIX_IF.v`と`FrameStreamingCore.v`で、最上位の命令入力からパーサへ至る接続を追う。停止条件の存在、外部へ伝わる時刻、CPUの実測待ち時間を、別々の問いとして扱う。

### I.8 同期FIFOは一つの時計で入口と出口を管理する

例えば入口からAを入れ、出口から前の語を出す処理を、すべて同じクロックの立ち上がりで決める。こうして入った数と出た数が分かれば、いま何語残っているかも更新できる。これが同期FIFOの基本である。

入口だけが別の時計で勝手に書き始めると、管理側の立ち上がりの間に何が起きたかを、そのままでは同じ規則で数えられない。非同期FIFOでは、入口側と出口側がそれぞれ数を管理し、相手の進み具合を安全に受け取る仕組みを加える。単に保存領域を二つの時計へ配線する、という違いではない。

回路の時計であるクロックは、値を記憶するタイミングを決める。同期FIFOは、入口で語を保存する処理と、出口で語を取り出す処理を、同じクロックで管理する。書いた位置と読んだ位置を同じ時計で比べられるので、空きや残りを決めやすい。

非同期FIFOは、入口を動かすクロックと出口を動かすクロックが別々でよいFIFOである。CPU側はCPUCLKの立ち上がりで一語を渡し、RasterIX側はDDRCLKの立ち上がりで一語を取り出す。二つの立ち上がりがいつ重なるかに依存せず、語の順番を保つように管理する。

![図I.3 同期FIFOと非同期FIFOで時計を接続する場所](figs/fifo-clock-comparison.png)

「非同期」は、回路が時計を使わないという意味ではない。両側はそれぞれ自分の時計で動く。「FIFO」は保存の順序を表し、「同期・非同期」は入口と出口の時計の扱いを表す。保存容量を大きくしても、一つの時計用に作られた管理回路が自動的に二つの時計へ対応するわけではない。

### I.9 遅い側の信号を速い側へ直結すると何が足りないか

ここでは、誤った接続を説明用に考える。CPUの一周期だけ1になる書き込み許可信号を、100 MHzで動く回路の書き込み許可信号へ、そのままつなぐ。CPUの一周期は50 nsあり、その間に100 MHz側には複数の立ち上がりが来る。受け側が各立ち上がりで書けば、同じ語を複数回保存してしまい得る。

![図I.4 一周期という言葉の長さはクロックごとに違う](figs/two-clock-pulse.png)

図I.4は、CPU側の一周期分の幅に、高速側の複数の立ち上がりが入る模式図である。実際のAPB要求をこの図のように直結しているわけではなく、図の失敗を実機で観測したわけでもない。直結する場合には「一回だけ」を保証する追加の受け渡し制御が必要だと分かる例である。

もう一つの問題は、データが変わる瞬間と受け取る瞬間が近い場合である。レジスタには、立ち上がりの前後に入力を安定させておく時間条件がある。その条件を守れないと、出力がどちらの値に決まるか遅れることがある。これをメタステーブル状態という。低速側は変更回数が少なくても、変更する瞬間が高速側の立ち上がりに近付かない保証にはならない。

### I.10 一ビットを二段で受けるだけでは一語を守れない

一ビットの状態を別クロックへ伝えるとき、受け側に二段以上のレジスタを置く方法がある。最初の段が不安定になった場合にも、次の段が取り込むまでに落ち着く時間を設ける。失敗確率を十分小さくするための設計であり、物理的な不安定さを数学的にゼロにする操作ではない。

32 bitのデータすべてへ独立に同じ二段を置くだけでは、語のまとまりは保証できない。説明用に二ビットを01から10へ変える場合、二本が同時に受け側へ反映されなければ、途中で00や11に見えることがある。各ビットが最終的に正しい値へ落ち着くことと、同じ更新に属する二ビットをまとめて読むことは別である。

したがって、まとまった語では「値を安定に保存してから、その語が利用可能だと知らせる」方法が必要になる。非同期FIFOは、そのような管理を連続する多数の語に対して行う部品である。一つの値だけを、返事が来るまで保持して渡すハンドシェイクも別の選択肢になる。

### I.11 非同期FIFOは何を同期するのか

入口側の係が保存場所0へAを書き、出口側の係がそのAを読む、と考える。出口側が必要なのは「入口の時計と同じ速さで動くこと」ではなく、「場所0のAは書き終わっていて、読んでよい」と知ることである。入口側が次に場所0を使い直すには、「出口側はAを読み終わった」と知る必要がある。

この二つの通知が逆向きに進む。書込み済みの位置は入口から出口へ、読出し済みの位置は出口から入口へ伝える。データの各ビットを別々に届いたことにする代わりに、保存を終えたまとまりを読めるよう管理する。以下の模式図では、この管理情報とデータ本体を別の矢印で示す。

理解用に四つの保存位置0〜3を描く。入口側は次に書く位置を覚え、出口側は次に読む位置を覚える。入口側でAを書き終えた後、その進み具合を出口側へ安全に知らせる。出口側はAが利用可能だと認識してから読む。読んだ位置の進み具合も入口側へ戻し、上書きしてよい場所を判断する。

![図I.5 語を保存する場所と書き込み位置の通知を分ける](figs/async-fifo-pointers.png)

図I.5は一般的な非同期FIFOを理解する模式図であり、使用したAMD IPの内部回路をすべて再現した図ではない。データを保存する記憶部と、書き込み・読み出しの進み具合を交換する管理部がある、と分けて読む。今回、これらを自作したのではなく、AMDのAXI4-Stream Data FIFOを利用した。[AMD085]

一般的な実装では、位置情報をグレイ符号へ変換して同期する方法が使われる。例えば二ビットの順序を00、01、11、10とすれば、隣へ進むときに変わるのは一ビットである。普通の二進数01から10では二ビットが変わるため、位置情報をそのまま別クロックで受ける問題を避ける工夫である。ただしグレイ符号にしただけで配線条件や同期回路が不要になるわけではない。[AMDGray]

入口が一語を書いてから、出口が利用可能と認識するまでには遅れがある。出口が読んで空きを作ってから、入口が空きを認識するまでにも遅れがある。そのため、一瞬だけ空きの利用を待つことはある。これはクロックを同じ位相へそろえた結果ではなく、違う時計のまま安全に情報を渡した結果である。

#### 保存位置が一周したときの空と満杯

四つの保存位置では、0、1、2、3まで書くと、次の位置は0へ戻る。このように同じ場所を順に使い回す。空のときに書く位置も読む位置も0であり、まだ一語も読まないまま四語を書いた後も、位置だけなら両方0に見える。位置番号だけでは、空と満杯を区別できないのである。

そのため、一般的な管理では一周したことを区別する情報も持つ。説明用に、リセットから何語書いたかと何語読んだかを数えると、差が保存中の語数になる。実回路のカウンタは有限の幅なので、周回を含めて比較できる幅と方法が必要になる。表では分かりやすく総数を用い、AMD IPの内部信号名としては扱わない。

| 操作の後 | 書いた総数 | 読んだ総数 | 保存中の語数 |
|---|---:|---:|---:|
| 初期状態 | 0 | 0 | 0 |
| A、Bを書く | 2 | 0 | 2 |
| C、Dも書く | 4 | 0 | 4 |
| Aを読む | 4 | 1 | 3 |
| 空いた位置へEを書く | 5 | 1 | 4 |

実際の非同期FIFOでは、入口が読む側の最新の総数を直ちに知ることはできない。逆も同じである。この表の差を、二つのクロックの信号へ直接組合せ回路で計算すればよいわけではない。相手の進み具合を安全に受け取ってから、書いてよいか、読んでよいかを各側で判断する点が重要になる。

### I.12 周波数が違えば非同期FIFOだけが正解なのか

周波数の違いだけで、非同期FIFOが唯一の解になるわけではない。同じクロックから作った整数比のクロックで、立ち上がりの関係を設計上保証し、タイミング制約も与えられる場合は、同期式のクロック変換を使える。AMDのPG085も、位相がそろった整数比の条件で同期式の変換を説明している。[AMD085]

逆に、二つの発振器がどちらも100 MHzという仕様であっても、立ち上がりの位置やわずかな周波数差を管理できなければ、同じクロックとして扱えない。必要なのは周波数の数値だけでなく、どの信号を、どの時間関係を前提として受け渡すかである。

今回のCPUCLKはClocking Wizardの出力、DDRCLKはMIGの`ui_clk`である。どちらも基板のクロック生成系に属するので、「物理的に無関係な二つの発振器」とは説明しない。`axiscdc.tcl`はこの接続を`IS_ACLK_ASYNC=1`で生成しており、命令の受け渡しでは特定の位相関係を前提としない構成を採っている。同期式へ変えられるかを調べるなら、両クロックの生成、位相関係、IPの対応条件、経路の時間条件をまとめて確認する必要がある。

### I.13 実装した設定を一行ずつ読む

次は保存した`fpga/generator/axiscdc.tcl`の設定と同じ値である。見やすく改行している。この設定からVivadoがIPを生成し、`rasterix.sv`が生成された回路を接続する。

```tcl
create_ip -name axis_data_fifo -vendor xilinx.com \
    -library ip -module_name axiscdc
set_property -dict [list \
    CONFIG.TDATA_NUM_BYTES {4} \
    CONFIG.FIFO_DEPTH {512} \
    CONFIG.IS_ACLK_ASYNC {1} \
    CONFIG.HAS_TLAST {1} \
    CONFIG.HAS_TKEEP {0} \
    CONFIG.HAS_TSTRB {0}] [get_ips axiscdc]
```

4 byteは一語のデータ幅である。512は保存できる語数で、データだけなら512×4=2,048 byteとなる。実際の回路には終端や管理の情報もあるため、これをIP全体の物理メモリ使用量と同一視しない。非同期を1にして二つのクロックを用い、`TLAST`も各語と一緒に保存する。`TKEEP`と`TSTRB`は、このストリームでは使わない。APB側の`PSTRB`まで存在しないという意味ではない。

命令用のインスタンスでは入口がCPUCLK、出口がDDRCLKである。応答用では逆になる。逆方向もFIFOを置くのは、CPUが応答を読む時点とRasterIXが応答を出せる時点を、それぞれの時計で扱うためである。FIFOにデータだけを入れて終端を別に直結すると、データと終端の対応が崩れ得るため、一緒に運ぶ設定が必要になる。

### I.14 容量512語とFIFOそのものの採用理由を分ける

公式RasterIXのNexys Video用接続例にも、命令入力の前へ深さ512のAXI4-Stream FIFOを置いた構成がある。ただし、その例は同じクロックで接続されている。公式の例にFIFOがある事実と、今回二つのクロック間に非同期FIFOを置いた判断は分けて説明する。公式例の存在だけでは、本研究の512語が最適だとは言えない。

容量を考えるときには、一時的な到着量と処理量の差を見る。説明用に受け取りが停止した間に10語が到着し、そこに6語の空きしかなければ、6語を入れた後は送り手を待たせる。正しい待ち制御があれば、容量を超える4語を捨てる必要はない。容量が大きいほど待ちを吸収できる場面は増えるが、回路資源を使い、設計によっては遅延も変わる。

定常的に到着する方が処理より速ければ、有限のFIFOはいずれ満杯になる。大きくすることは根本の処理能力を増やすことと同じではない。今回の512語は当初の採用値であり、E6で16語と1語方式を比較して維持を判断した。最大占有量や中間容量まで調べて決めた最適値という主張はしない。FIFOを採用すること、正しく止めること、容量を最適化することは、それぞれ違う設計・評価の問題である。

### I.15 同じ機能を作る別の方法と比べる

| 方法 | 必要な仕組み | 主な性質 |
|---|---|---|
| 二つのクロックを同じにする | 回路全体の周波数と時間条件の再検討 | この境界のCDCは消せるが他の条件が変わる |
| 一語ずつ保持して返事を待つ | データ保持と要求・応答の同期 | 構造を追いやすいが往復を待つ |
| 同期FIFOと別の変換回路 | FIFOの外で安全なクロック変換 | 同期FIFOだけでは境界は解決しない |
| 非同期FIFO | 二つの時計と正しいリセット・制約 | 複数語を保存しながら境界を渡せる |

今回の非同期FIFOは、既存IPで順序を保つ受け渡しと二つのクロックへの対応をまとめて得られる選択である。この表は設計候補の整理である。そのうち、1語ずつ保持する4相方式と、16語・512語の非同期FIFOについては、E6で同条件の実装比較を追加した。比較していない候補まで含めて「これが最も小さく速い」とは主張しない。

### I.16 ソースで分かることと実験で確かめること

| 問い | 現在の根拠 | ここからは言えないこと |
|---|---|---|
| CPU側がAPBなのか | `rasterix_apb.sv`の信号と接続 | 外側までAPBで統一されているとは限らない |
| FIFOが非同期設定なのか | `axiscdc.tcl`と二つのクロック配線 | 設定だけで全接続の安全が証明されたとは言えない |
| 受け側が停止する設計なのか | 公式CommandParserの状態と条件。E6ではCPU入口の待ちも実測 | パーサ単体の停止時間や全占有量の時系列 |
| APBが待ちを正しく返すか | E1の変換回路試験と、E6の実IPを含む接続試験 | 任意のクロックやリセットに対する網羅的保証 |
| 512語が必要十分なのか | E6で1語方式・16語・512語を比較 | 未比較の容量や方式まで含む最適性 |

E1のAPB試験は、FIFOから来るはずの`CmdReady`を試験側で操作する。実際の非同期FIFOを満杯にしているのではない。変換回路の試験と、生成IPを含むクロック境界全体の試験を同じものとして記述しない。配置配線後のCDCレポートも、検出した構造を調べる根拠であって、任意の動作について命令の順序と内容が必ず正しいという万能の証明ではない。

### I.17 接続を変更するなら何を試すか

今後FIFOの容量や方式を変更する場合には、実IPを含めた試験で、入力として受理された語と出力として受理された語をそれぞれ記録する。入力側では`valid && ready`の瞬間だけ一覧へ追加する。出力側でも同じ条件の瞬間だけ比較し、順序、内容、終端の一致を調べる。提示したが受け取られていない語を一覧へ加えてはいけない。

受け側を長く停止させて満杯へ到達させ、満杯中にCPU側が同じ値を保持し、再開後に全語が一回ずつ出ることを確認する。時計の開始位相をずらす、異なる周波数の組を使う、空と満杯の境界を何度も通る、といった条件を与える。リセット中の語は別扱いにし、リセットをまたいだ保存を契約していないなら、破棄する範囲を決めてから比較する。

この方針に基づき、E6では1語方式の単体試験、生成したAMD FIFOを含む順序・停止・リセット試験、実機の画像・時間・資源比較を追加した。実施した条件は技術付録第29章と保存ログに示す。全占有量の時系列やすべての容量を試したわけではない。今後さらに小さいFIFOで同じ性能を得られると主張する場合には、その容量の回路を作り、同じ条件で正しさと性能を確かめる必要がある。

通常のRTLシミュレーションは0と1の動きを扱うため、実際のレジスタのアナログ的な不安定さをそのまま再現するわけではない。シミュレーションで順序と停止・再開を調べ、CDC解析で受け渡し構造を調べ、タイミング解析とIPの制約で物理的な時間条件を調べる。それぞれ違う種類の誤りを探しているため、一つの試験の成功だけで他を省略しない。

### I.18 自分の言葉で採用理由を説明する

「CPUが20 MHzだからGPUより速くデータを作る」と説明する必要はない。今回の理由は、「APBの書き込みを公式RasterIXの命令ストリームへ変換し、CPUCLKからDDRCLKへ一語ずつ順序を保って渡すため、非同期FIFOを使った。受取可が0のときは受け渡しを成立させず、FIFOも満杯ならAPBを待たせる」である。さらに現在は、「同じクロック条件で1語方式と16語FIFOも比べ、512語FIFOでCPUの送信待ちを減らせた。追加資源が小さかったため維持した」と、E6の結果を添えて説明できる。

この説明ができた後、別の設計を考える練習をする。例えば、FIFOを100 MHzだけの同期FIFOに交換すると何が足りなくなるか。答えは、CPUCLK側の一回を出口側の一回へ正しく対応付けるクロック変換である。保存容量を増やすだけでは補えない。逆に、両側を本当に同じクロックで動かす構成へ変えたなら、同じ理由で非同期FIFOが必須とは言えない。

## 付録J 設計を変更できる理解へ進む

この付録は、各部品の名前を知った後に、ゲーム機全体をどう設計し、どこを確かめるかを説明する。専門家が設計を検討するときには、正常に動く一例だけでなく、停止、再起動、設定変更の条件も扱う。ここでいう理解の目標は、本構成の入力、出力、状態、所有者、完了条件を示し、変更によって影響する場所と確認方法を選べることである。CPU全命令やDDR3 PHYの内部を一から設計する知識まで、このゲーム機の再現に必須とするわけではない。

### J.1 部品の仕様から接続で守る条件を取り出す

部品Aの出力を部品Bの入力につなぐ前に、「何が運ばれるか」「何bitか」「どの時計か」「どの条件で受け取ったことになるか」「止められるか」「リセットすると何を失うか」を書き出す。線の名前だけが似ていても、この六点が一致しなければ、そのまま接続できるとは限らない。

例えばCPUのAPB書き込みは、番地を伴う操作である。一方、RasterIXの命令入力は語の列を受け取る。ここには形式の変換が必要である。さらに両者の時計も違うため、形式を変換しただけでは接続は完成しない。このように、互換でない点を一つずつ埋めると、追加した回路の理由を説明できる。

| 境界 | 運ぶもの | 守るべき条件 | 実装を読む入口 |
|---|---|---|---|
| CPUから命令入口 | 32 bitの命令語 | 一回の書き込みと一回の受理の一致 | `rasterix_apb.sv` |
| CPUCLKからDDRCLK | 命令語と終端 | 順序とまとまりの保持 | `axiscdc.tcl` |
| 描画から表示 | 画像の物理番地 | 古い画像の読出し完了まで再利用しない | `rasterixdisplay.sv` |
| OSと描画用メモリ | 利用できる番地範囲 | OSが画像を別用途へ割り当てない | デバイスツリーと`RenderConfigs.hpp` |

### J.2 クロックとリセットは別々の仕事をする

クロックは状態を更新する時刻を決め、リセットは状態を出発点へ戻す。例えばFIFOがどこまで書かれたか、表示がどの画像を読んでいるかは状態である。リセットを解除しても、DDR3に以前保存した画像の全画素が自動で消えるとは限らない。制御用レジスタを初期状態へ戻す処理と、画像の内容を塗り直す処理は別に必要になる。

![図J.1 クロックの準備と状態の初期化を分ける](figs/reset-and-startup.png)

図J.1は起動条件の依存関係である。時間を正確な長さで描いた波形ではない。基板クロックからClocking WizardとDDR3制御を準備し、クロック安定やDDR3初期化完了を見て、利用する回路を動かす。実配線の信号名と極性は本文6.5節にある。`resetn`のような名前の末尾のnは、0でリセットとなる信号を読む手掛かりになるが、名前だけで決めず代入式を確認する。

非同期の解除を各クロックへそろえる必要があるのは、同じ状態機械のレジスタの一部だけが先に動き始める状況を避けるためである。また、非同期FIFOを使う場合はIPのリセット仕様も満たす必要がある。片側だけの再起動で途中の語がどう扱われるかを決めずに、一語も失わないことを期待してはいけない。保存したリセット試験が扱った条件と、今後追加する途中リセットの試験は区別する。

### J.3 番地と所有者とキャッシュを三つに分ける

例として、次の画像を置く範囲Bを考える。まず「Bはどの番地からどこまでか」を決めなければ、読書きする場所を指定できない。次に「今は描画回路がBを書いてよいか」を決める必要がある。表示回路がBを読んでいる間なら、番地が正しくても、そのまま書き換えてよいとは限らない。

さらにCPUがBへ何かを書いた場合、その値がCPUのキャッシュだけに残り、別の回路が読むDDR3まで届いているかという問題がある。「場所が正しい」「今そこを使ってよい」「別の回路にも新しい中身が見える」は、それぞれ別に確かめる。ここで所有者という語は、その時点で領域を更新・再利用してよい主体を表し、ファイルの著作権などを意味しない。

同じ番地の数字を使っていても、CPUのプログラムが扱う仮想番地と、外部回路がDDR3へ出す物理番地は別である。`mmap`によってプログラム内に得たポインタを、そのまま描画回路の物理番地として渡せるとは限らない。今回のMMIO入口は物理番地`0x10080000`を対応付け、その対応先へ32 bit単位で書いている。

メモリの所有者も考える。Linuxが通常のプログラムへ自由に配る領域と、描画回路が画像を置く領域が重なると、双方は自分の正しい操作のつもりで相手のデータを壊せる。デバイスツリーで画像用領域を予約するのは、この割り当ての衝突を防ぐためである。

ただし、領域を予約することはキャッシュの内容を一致させることと同じではない。一般にCPUのキャッシュに新しい値が残り、DDR3に古い値が残っていれば、外部回路は古い方を読む可能性がある。その場合は、非キャッシュの対応付け、キャッシュの書き戻し・無効化、ハードウェアの一貫性機構など、構成に合う方法が必要になる。

![図J.2 同じメモリを使う設計で別々に確認する三つの条件](figs/memory-three-contracts.png)

今回の描画命令は、CPUが通常メモリから値を読み出してMMIOへコピーする。RasterIXがCPUの命令バッファを直接DMAで読む方式ではない。この違いがあるため、「命令バッファの番地を教えるだけで送信が終わる」という説明は当てはまらない。もしDMA方式へ変更するなら、番地変換、キャッシュ、バッファの寿命、完了通知を新たに検討する。

### J.4 volatileとfenceだけで描画完了は分からない

`volatile`は、コンパイラに対して、その場所へのアクセスを通常の不要な読み書きのように省略しないことを求めるために使う。`fence`は、CPUのメモリアクセスやI/Oの順序を扱う命令である。どちらも、その先のGPUが全画素を描き終えたことや、ディスプレイが画素を表示したことを直接返す機能ではない。

今回の送信関数は、一語ずつのMMIO書き込みを完了し、その順序を整えてから返る。これにより元の命令バッファの内容を送信用に保持し続ける段階を終えられる。一方、描画回路や表示回路には続きの仕事がある。アプリが次へ進める時点は、表示切り替え完了の回数など、目的に対応した通知で判断する。

この違いを理解すると、「関数が返った」「回路が受け取った」「画像が完成した」「古い画像を再利用できる」「人の目に届いた」を一つの完了へまとめずに説明できる。本文7.11節の表は、この区別を本構成の観測点へ対応させている。

### J.5 メモリ共有では平均帯域と待ち時間を分ける

CPU、描画回路、表示回路はDDR3への要求を共有する。表示回路は、画面を送り続けるために画素を読みたい。描画回路は、新しい画像を書いたりテクスチャを読んだりしたい。CPUは命令やデータを必要とする。接続回路は、同時に来た要求を順に処理できるように調整する。

平均的な転送量がDDR3の能力より小さくても、必要な時刻までに表示用のデータが来なければ困る。例えば、表示用FIFOに十分な画素が蓄えられていれば一時的な待ちを吸収できるが、蓄えが尽きるほど長く待たされると映像の生成に間に合わない。この考え方は命令FIFOと似ているが、表示側には送り出す時刻の制約がある。

本構成の有効な画像だけを60回/秒読み出す量は、640×480×2×60=36,864,000 byte/秒となる。これはRGB565の画素データ量を計算した値であり、実測したDDR3使用帯域ではない。メモリ要求の粒度、空き時間、他の要求、キャッシュ、コマンドの負担を含んでいない。この計算だけで帯域に十分余裕があるとは結論しない。

### J.6 AXIの一件の要求はすぐに一件の応答にならない

メモリへ「この番地から読んでほしい」と伝える時刻と、読んだデータが返る時刻は違う。例えば要求1を受け付けても、DDR3の読出しや他の要求の処理に時間がかかり、返事が後になる。その間に要求2を受け付けることもある。したがって、要求1の受付を見ただけでは、要求1の読出しが終わったとは判断できない。

AXIの読出しでは、番地の要求を受け取った後、データは別の信号で後から返る。一度の要求で複数のデータを返すまとまりをバーストという。最後のデータには`RLAST`が付く。要求が成立した回数から、最後のデータを受け取った回数を引くと、まだ完了していないバーストの数が分かる。

表示先の番地をAからBへ変更しても、既に受け付けられたAへの読出しが残る場合がある。ここで描画側にAを書かせると、表示回路が必要としているAの内容を途中で変えてしまう。従って、設定レジスタを書き換えたことだけでAを再利用してはいけない。

`rasterixdisplay.sv`は未完了の読出しを数え、新しい画像からの読出しを検出した後、その応答まで確認して完了を通知する。これは、接続している表示回路の読出し順序と応答の扱いを前提とする設計である。将来、複数IDで応答順序が変わる構成へ変更するなら、数だけを引き継いでよいか再検討が必要になる。詳細な現在の計算例は本文10.5節と付録B.5にある。

### J.7 表示の通知は一回の要求に一回の返事を対応させる

表示切り替えでは、GPU側が新しい画像の番地を保持し、要求を出す。画素クロック側が要求を受け取り、表示回路へ設定し、必要な読出し完了を待って返事を出す。GPU側が返事を受け取った後に要求を下げ、相手が返事を下げたことを見て次の要求へ進む。

表示変換回路の入力名は`GPUCLK`で、外側から`DDRCLK`を接続している。別の新しい周波数のクロックを作ったという意味ではない。ソースを読むときは、部品の入力名と、その入力へ接続された外側の信号名を区別する。

![図J.3 画像の番地を保ったまま要求と返事を往復させる](figs/swap-handshake-lifetime.png)

この手順では、番地そのものを毎周期書き換えない。要求を出す前に用意し、相手が受け取って処理を終えるまで保持する。要求や返事の一ビットを同期させる方法と、番地を安定して置いておく方法が組み合わさっている。多ビットのすべてを独立な同期器へ通す方法とは違う。

CPUへ完了を伝える経路では、完了に応じて値を反転させ、CPUCLK側で反転を検出する。速いクロックの一周期だけのパルスを遅い側が見逃す問題を避ける考え方である。ただし、反転方式ならどんな頻度のイベントも無制限に運べるわけではない。受け側が確認する前に二回反転すれば元に戻る。今回の一回ずつ進める切り替えの手順と通知の頻度を併せて考える。

### J.8 描画の速さと映像の速さとゲーム時間を分ける

ボールの位置を60回/秒更新すること、一秒間に58枚の描画を完了すること、表示回路が約60 Hzで信号を送ることは別である。ゲーム状態の更新は位置を計算し、描画はその時点の状態を画素へ変え、表示は完成画像を繰り返し読む。新しい画像が間に合わなければ、表示回路は前の画像を送ることがある。

![図J.4 三つの繰り返しを同じ時間軸で分ける](figs/three-loops-timeline.png)

図J.4は関係を示す説明用の時系列であり、保存した映像や実機の波形を写した図ではない。研究の数値を説明する際は、どの列を数えたかを述べる。`FRAME_COUNT`から得た切り替え完了数を、そのまま人の目で数えた異なる画像の数と呼ばない。

部分描画は状態更新を省く操作ではなく、前に残っている画像を利用して、同じ次の画像を少ない書き換えで作る操作である。このため、同じゲーム状態を与える比較と、画像の一致の確認が必要になる。本文11.6節の二枚別の履歴は、描画先ごとに残っている画像を正しく把握するためにある。

### J.9 FPGA資源の余りと動作周波数の余裕は違う

LUTやBRAMの使用率は、使った部品の量である。タイミング余裕は、信号が次の記憶時刻に間に合うかという時間の量である。部品が空いていても、長い配線や複雑な組合せ計算を一周期で通す経路があれば、周波数を上げられない。逆に、レジスタを追加して処理を何段かに分ければ、資源を少し多く使いながら周波数を上げられる場合もある。

ただし段を増やせば、入力から出力までの周期数や、停止したときに保持すべきデータも変わる。回路へレジスタを追加するだけで既存のプロトコルが保たれるとは限らない。変更後に、有効信号、データ、終端が同じ処理に対応して遅れるかを確認する。

タイミングレポートの正の余裕は、指定された制約に対する結果である。解析されていない経路が残っていないか、例外指定が広過ぎないかも読む。特にCDCの経路を時間解析から除外する指定は、安全な受け渡し回路を作る代わりにはならない。今回の保存結果と警告件数は本文13.3節に明示している。

### J.10 起動の失敗をどの層で調べるか

FPGAへbitstreamを書き込めたこと、Wallyが命令を実行できること、Linuxが起動すること、ゲームが命令を送れること、映像が見えることは段階が違う。一番外側の「画面が黒い」だけでは、どの段階が失敗したか決められない。

まず使用したbitstreamとソースの版を一致させ、クロックとリセット、DDR3初期化の条件を見る。次にUARTに起動ログが出るか、Linuxが必要なメモリ範囲を認識しているかを確認する。アプリではMMIOの識別値を読む。ここで期待する値が返らなければ、描く四角形の座標より先に、アドレス判定、ビルド設定、マッピングを調べる。

識別値が読めた後は、小さな既知の画像、表示先の番地、切り替え完了数、映像信号の順に観察する。各段階で入力と期待結果を決めると、別の層の不具合を推測し続けずに済む。詳しいコマンドと成功の判断は付録Mにある。SDWire3や取り込み機器は実験を助ける道具であり、公開設計の機能とは分ける。

### J.11 計測で原因を絞るとは何をすることか

長い処理区間が見つかっただけでは、その区間の中で何を減らせばよいかは分からない。保存したE5では、まず画像と図形数を保って描画呼び出しのまとめ方を変えた。次に呼び出しのまとまりを固定して図形数を変えた。この二つの操作で、繰り返す呼び出しと、図形に伴う準備量を改善対象として選んだ。

これはCPUのすべての命令の費用を測ったことではない。例えばキャッシュミスの回数を計測していなければ、残りの時間をすべてキャッシュのせいだと決められない。専門的な説明では、測った量、操作した条件、その結果から言える範囲をそろえる。分解していない原因を認めても、得た比較の価値がなくなるわけではない。

結果を再集計する人は、平均の速さだけでなく、対象の状態列、ウォームアップ、試行数、代表値、時間区間の定義を見る。さらに、標準DVI構成と実験用HDMI構成を混ぜない。本文12・13章に方法と結果を分けて示し、付録Cには再集計へ戻る入口を置いた。

### J.12 設定変更を一つ選び影響を最後まで追う

例えば画像の幅を640から別の値へ変えたい場合、画面上の座標だけを変更して終わらない。一行のbyte数、画素番地、フレームバッファ容量、内部作業領域へ入る行数、帯の数、命令バッファ数、映像のタイミングを順に確認する。幅×高さ×2という計算はRGB565の画像一枚の必要量であり、深度やテクスチャ、管理領域まで含めた総量ではない。

CPU周波数の変更なら、生成クロックだけでなくUARTなどの時間を決める設定、ソフトウェアへ知らせる値、タイミング解析、各クロック間の接続を確認する。MMIO番地の変更なら、CPU側の判定、外部I/Oの属性、ソフトウェアのマッピングをそろえる。付録Hには現在の値を使った計算がある。

設計を理解できたかは、「どの一行を直すか」だけでなく、「他のどこを合わせ、何を観測すれば誤りを見つけられるか」まで答えて確かめる。これは新しい変更を直ちに実機へ入れる指示ではない。まず固定した動作基準と比較できる別の作業場所で検討する。

### J.13 説明できるかを確認する課題と解答

問1。FIFOが空いているがRasterIXが受取可を0にしたとき、CPUの次の書き込みは必ず止まるか。答えは、必ずは止まらない。FIFOの入口に空きがあり入口側が受取可を返せば、CPUは一語を保存して先へ進める。停止がCPUまで伝わる条件は、出口の停止と入口の空きを分けて考える。

問2。Linux用領域から画像用領域を除外すれば、どんなCPUキャッシュ構成でもGPUに最新値が見えるか。答えは、除外だけでは保証できない。割り当ての衝突と、保存された値の一貫性は別だからである。今回の命令のCPUコピー方式と、将来のDMA方式も分ける。

問3。画像AからBへ表示設定を書き換えた直後、Aへ描画してよいか。答えは、古い読出しが残っていないことを本接続の完了条件で確認する必要がある。設定の変更と要求済みデータの受信は別の時刻に起こる。

問4。LUTが半分近く空いていれば、CPUを二倍の周波数にできるか。答えは、使用率からは判断できない。遅い経路、配線、クロック条件、IPの対応範囲を調べ、変更後の時間解析と動作を確認する。

問5。画素の最終一致が0不一致なら、ゲーム中の全画面を検査済みか。答えは、最終画像だけの比較からは言えない。保存した結果が扱った画像の枚数と時点を述べる。途中の画像すべてについて主張するには、その時点に対応した比較が必要である。

問6。今回の方式が唯一の正解か。答えは、そうではない。CPU直描き、別の転送方式、同期式の変換などの候補はある。本研究の到達点は、採用した方式をソースと動作条件に結び付けて説明し、保存した確認結果の範囲で成立を示すことである。


## 付録K 回路とFPGAの基礎

### K.1 0と1で値を表す

デジタル回路は、電気信号を0と1の二つの状態として扱う。実際の電圧は基板や端子の規格によって異なるが、論理の説明では0と1に整理する。一つの0または1をビットと呼ぶ。八つのビットをまとめた単位がバイトである。

二つのビットなら00、01、10、11の四通りを区別できる。数字に対応させれば0、1、2、3を表せる。三つなら八通り、八つなら256通りになる。一般にnビットで区別できる組合せは2のn乗通りである。32ビットの信号とは、32本分の0または1を同時に扱うまとまりである。

同じ32ビットでも、位置、色、命令、住所に相当する番号など、意味は用途によって違う。回路は名前から意味を理解するのではなく、設計した決まりに従ってそのビット列を処理する。送信側と受信側が同じ決まりを使うことが必要になる。

#### bitとbyteと16進数を小さな数で読む

bitは0か1を入れる一桁である。二桁なら00、01、10、11の四通りを区別できる。三桁なら八通り、八桁なら256通りを区別できる。8 bitをまとめた単位が1 byteである。32 bitは4 byte、64 bitは8 byteになる。

ソース中の0xは「後ろの数を16進数で読む」という印である。16進数は0〜9の次にA、B、C、D、E、Fを使い、その次に桁が上がって10になる。したがって0x10は十進数の16であり、十進数の10ではない。先頭の0x自体は数値に含めない。

| 十進数 | 4 bitの二進数 | 16進数 | この論文での例 |
|---:|---|---|---|
| 0 | 0000 | 0x0 | 最初の要素や通常命令口 |
| 4 | 0100 | 0x4 | 32 bit一個分のbyte数 |
| 8 | 1000 | 0x8 | 状態レジスタまでの差 |
| 12 | 1100 | 0xc | 識別値レジスタまでの差 |
| 15 | 1111 | 0xf | 4 bitをすべて1にした値 |

16進数の一桁は4 bitに対応する。0x04の下位4 bitを二進数で書くと0100なので、右端をbit 0として数えたbit 2が1になる。この関係を使い、付録Bでは0x00と0x04の操作で64 bitデータのどちら半分を選ぶかを説明する。

図K.1は、0x04を8 bitで書き直したものである。箱一個をbit一桁とし、右端から番号を付けている。薄い青の箱は1が入った桁であり、その桁の値を読む。

![図K.1 0x04の値とbit番号を対応させる](figs/bit-byte-value.png)

この図では、1が入っているのはbit 2だけなので、値は2の2乗で4になる。左側の0は、桁をそろえるために表示している。例えばbit 2を取り出す回路は、数値の「2」を取り出すのではなく、この列の特定の一桁を取り出す。



容量のKiBとMiBは、それぞれ1,024 byteと1,048,576 byteを単位にする。例えば512 MiBは512×1,048,576 byteである。「512」という数字だけでは、画素数かbyte数か回路の個数か分からないため、単位まで一緒に読む。

### K.2 論理ゲートをつないで回路にする

ANDゲートは、二つの入力が両方1のときだけ1を出す。NOTゲートは0を1へ、1を0へ反転する。例えば、「指示がある」と「受け取れる」が両方1なら受け渡す、という条件はANDで表せる。このように、複数の信号から条件を計算する回路を組み合わせ回路と呼ぶ。

入力が変われば出力も変わるが、現実の回路には変化が伝わる時間がある。たくさんのゲートを順につなぐと、その時間が積み重なる。後で説明するクロックを速くしすぎると、計算結果が安定する前に次の回路が値を読み取る可能性がある。

```systemverilog
assign Transfer = Valid & Ready;
```

これはSystemVerilogという回路記述言語の例である。Validは「渡したいデータがある」、Readyは「受け取れる」を表す信号名として使っている。&はビットごとのANDであり、ここでは二つが両方1ならTransferを1にする。assignは、この関係を持つ回路の接続を表す。プログラムの一行が一度だけ実行される、という意味ではない。

#### 論理ゲートをつなぐと何ができるか

「書き込み要求がある」と「受け取る場所が空いている」を、それぞれ1 bitの信号で表す。要求をValid、空きをReadyと名付けると、両方が1のときだけ転送を成立させたい。その条件を計算するのがANDゲートである。

![図K.2 二つの条件から受け取り条件を作る小さな回路](figs/gate-transfer.png)

図K.2の左側二本は別の信号であり、右側は条件を計算した結果である。入力が1と0なら右側は0、1と1なら右側は1になる。ここで計算しているのは「今回受け取るか」であり、描画命令の32 bitデータそのものではない。実際の接続には、条件を伝える信号と、中身を運ぶ信号の両方がある。

`assign Transfer = Valid & Ready;`は、そのANDの関係を回路として書いた記述である。CPUがこの一行を繰り返し実行して条件を調べる、という意味ではない。FPGAには入力の組合せに応じて出力が変わる回路が用意される。

### K.3 値を覚える回路

ゲームには前の位置が必要であり、接続回路にも前に受け取った命令を覚える場所が必要である。そこで、値を保持する回路を使う。ある決めたタイミングで入力を取り込み、その後は次の取り込み時点まで値を保つ回路がフリップフロップである。複数のビットをまとめて保持する部分をレジスタと呼ぶことがある。

```systemverilog
always_ff @(posedge clk)
  if (reset) Count <= 0;
  else if (Transfer) Count <= Count + 1;
```

この説明用回路は、転送回数を覚える。clkが0から1へ変わる時点をposedgeと書く。その時点でresetが1ならCountを0にする。resetが0でTransferが1なら、前のCountに1を加えた値を保存する。それ以外では前の値を保つ。<=は、この取り込み時点で次の値を記憶するための記法である。

ここまでを組み合わせると、「いつ受け渡しが起こるかをANDで決め、その回数をレジスタへ覚える」という回路を作れる。後で登場する表示切り替えの回数も、同じように出来事を数えた値である。

#### 計算する回路と覚える回路を組み合わせる

ANDゲートのように、現在の入力から現在の出力を決める部分を組合せ回路と呼ぶ。それだけでは「さっき何回受け取ったか」を覚えられない。回数を覚えるには記憶素子が必要になる。クロックに合わせて値を記憶するものを、この論文ではレジスタと呼ぶ。

例えばCountが4を覚えているとき、組合せ回路で4+1=5を求める。受け取り条件Transferが1なら、次のクロックの立ち上がりで5をCountへ保存する。Transferが0なら4を保持する。次のクロックでは、保持された値から再び次の候補を計算する。

![図K.3 計算した次の値をクロックで保存する](figs/register-cycle.png)

図K.3の箱のCountが現在の値、足し算の先が次の候補である。矢印で戻っているのは、記憶した値を次の計算へ使うためである。時計の一回の合図で一回保存するので、足し算の出力ができた瞬間に何度も増え続ける回路ではない。

`always_ff @(posedge clk)`は「clkが0から1へ変わるときに記憶を更新する」と読む。`Count <= Count + 1`の右辺は更新前の値、左辺は次に保存する値である。`<=`をここでは大小比較と読まない。`if`は、次に保存する候補をどちらから選ぶかを決める。

一つのalways_ffの中で、Countと別のレジスタを更新していても、記述した順に古い値が順次上書きされるC言語の代入と同じには扱えない。本稿の回路例では、立ち上がり直前の値から、立ち上がり後に保持する値を考える。

### K.4 CPUがプログラムを実行する

第2章では「CPUがballXへ3を加える」と説明した。CPUの中にも、前節で扱った値を覚える回路と、足し算などを行う回路がある。CPUは、メモリから読み出した機械語命令に従って、どの値を読み、何を計算し、どこへ結果を残すかを選ぶ。

例えばballXが100のときは、値100をCPU内で使える場所へ読み、3を加え、得られた103を次の計算で使えるように保存する。CPU内で少量の値を覚える場所をレジスタという。よく使う値を毎回外部メモリから取り出す代わりに、レジスタに置いたまま計算を続ける場合もある。したがって、C++の一行が必ず一回の外部メモリ読み出しと書き込みになるわけではない。

C++をCPU用の機械語命令へ変換する道具がコンパイラである。CPU自身がC++の文章を読んで解釈するのではなく、変換後の命令列を実行する。同じように、描画ライブラリのglVertex2fという関数も、実行時にはCPUの命令列になる。「関数を一回呼ぶ」とは、CPUがその関数の中の処理へ進み、必要な計算をして戻ることであり、一つの論理ゲートだけを動かすことではない。

ここでいうCPUの機械語命令と、第2章の描画命令は別のものである。CPUは機械語命令を実行して計算やメモリへの保存を行う。その処理によって、描画回路へ渡すための描画命令をデータとして作る。後で描画命令を受け取って実行するのは描画回路である。「命令」という語を読むときは、どちらの回路に対する指示なのかを区別する。

RISC-Vは、この機械語命令やレジスタの使い方などの決まりの名前である。Wallyは、その決まりに従って命令を実行する具体的な回路設計である。FPGAは、そのWallyの回路を組み立てる場所になる。RISC-V、Wally、FPGAは同じ物の別名ではなく、それぞれ「命令の決まり」「CPUの設計」「回路を実現する部品」を指している。

### K.5 FPGAの中へ回路を作る

FPGAには、論理機能、値を覚える回路、内部メモリ、配線を切り替える仕組みなどが用意されている。設定データによって、それらをどのようにつなぐかを決める。この設定によってCPUや描画回路を構成する。CPUという別の物理チップをFPGAへ載せる操作ではない。

論理機能を作る主な部品がLUTである。LUTは入力の組合せに対する出力を記憶する表のように働く。例えば二入力ANDなら、00、01、10には0、11には1を対応させればよい。実際のFPGAのLUTはもっと多くの入力を扱えるが、必要な論理を小さな表へ割り当てるという考え方は同じである。

Block RAM、略してBRAMは、FPGA内にあらかじめ用意されたメモリのまとまりである。多くの値を保存する用途に使う。DSPは乗算などの計算に使える専用回路である。これらの使用率は、FPGAに用意された数のうち、作った回路がどれだけ使ったかを表す。

#### 論理式がFPGAの中へ入るまで

FPGAには、組合せの計算に使うLUT、値を覚えるレジスタ、まとまった量を覚えるBlock RAM、配線の接続を選ぶ仕組みなどが用意されている。LUTは、入力の組合せに対する答えを保持する小さな表として理解できる。先ほどのANDなら、00、01、10には0、11には1という答えを設定する。

Vivadoは、回路ソースに書かれた計算や記憶を、これらの実物の部品へ割り当てる。この対応付けの大枠を作る処理が合成である。さらに、どの場所の部品を使い、どの配線を通るかを決める処理が配置配線である。最後に、その設定をFPGAへ送るbitstreamを作る。

![図K.4 論理式とFPGA資源と設定ファイルの関係](figs/logic-mapping.png)

図K.4は、説明用の小さな回路を資源へ対応させる考え方である。一つのANDが必ず一個のLUTになるという個数の予測図ではない。Vivadoは複数の式をまとめたり、不要な計算を消したりできる。実際に使った個数は第13章の配置配線後のレポートで確かめる。

#### CPUをFPGAに作った後、ゲームのfor文はどこで動くか

FPGAへWallyの回路を設定すると、FPGA内に機械語命令を読んで実行するCPUができる。そのCPUが、SDカードから起動したLinux上でゲームの実行ファイルを動かす。ゲームのfor文やwhile文は、このCPUが繰り返し命令を実行することで進む。本研究では、ゲームのC++を直接、ボール専用の論理回路へ変換しているわけではない。

一方、描画回路の信号の接続やFIFOの容量は、FPGAへ設定する回路の一部である。ゲームを終了して別のゲームを起動しても、この配線や容量は変わらない。変えるには回路の設定ファイルを作り直す。ここが、ゲームのプログラムを変更する場合と、ゲーム機そのものの回路を変更する場合の違いである。

20 MHzというCPUのクロックは、毎秒2,000万回、回路の値を更新するための基準が来ることを示す。一回の基準でゲーム画面が一枚できるという意味ではない。CPUは多数の命令を実行し、メモリや周辺回路を待つこともある。そのためゲームの描画回数は、CPUのクロックの数字だけからは求められない。

### K.6 FPGAチップと基板を区別する

Nexys Videoは、FPGAチップの周りにDDR3メモリ、microSDスロット、映像端子、スイッチ、LEDなどを載せた基板である[NexysVideo]。DDR3は基板上の別のメモリ部品であり、FPGA内のBRAMとは別である。画像を保存する大きな領域にはDDR3を使い、描画途中の作業などにはBRAMも使う。

![図K.5 基板上の部品とFPGA内部の関係](figs/board.png)

図のゲートは、回路をつなぐという考え方を示した小さな例である。実際のCPUを数個のゲートだけで実装したという意味ではない。FPGAの外側の部品と、内側の制御回路を分けて描いている。基板上の配線は製造時に決まっており、設計者はその配線につながるFPGAの端子を使う。

## 付録L 設計ファイルと開発手順

### L.1 開発用パソコンで行うこと

開発用パソコンでは、回路のソースを編集し、FPGAを設定するファイルを生成する。ゲームのソースも編集し、Wally上で動く実行ファイルを生成する。この二つは異なる生成物である。回路の設定ファイルはFPGAへ送り、ゲームの実行ファイルは実機が使うSDカードへ置く。

今回、開発環境にはWindowsとWSL上のUbuntuを使った。WSLはWindows上でLinux環境を利用するための仕組みである。一方、ゲーム実行中のLinuxは、FPGA内のWallyで動くLinuxである。開発用Ubuntuのターミナルと、実機へつないだ端末では、実行する場所が違う。本稿の作業手順には「開発用Ubuntu」「実機のLinux」などと実行場所を記す。

### L.2 ファイルの種類

| 種類 | 例 | 何を記すか | 使用する道具 |
|---|---|---|---|
| 回路の記述 | .sv、.v | 信号、計算、記憶、部品同士の接続 | Vivado、回路シミュレータ |
| FPGA生成の手順 | .tcl | 部品の生成、ソースの読み込み、配置配線の指示 | Vivado |
| 制約 | .xdc | 外部端子の割り当て、電気規格、時間条件 | Vivado |
| メモリ制御の設定 | .prj | DDR3の種類、幅、配線など | MIGというIP生成機能 |
| Linuxへ渡す説明 | .dts | メモリ範囲、周辺機器の位置、クロック値 | dtc |
| ゲームのソース | .cpp、.hpp | 入力、規則、描画の呼び出し | C++コンパイラ |
| 生成対象の選択 | Makefile、CMakeLists.txt | どの設定とファイルを使って生成するか | make、CMake |

「この値を変える」ときは、どの種類の値なのかを先に決める。例えばCPUのクロックを実際に作る設定と、LinuxへCPUのクロックを知らせる設定は別のファイルにある。片方だけ変えると、実際の回路とソフトウェアが前提とする値がずれる。

#### ファイルと回路部品と信号の名前を区別する

例えば`fpga/src/rasterix_apb.sv`は保存場所を含めたファイル名であり、その中の`module rasterix_apb`は回路部品の種類を定義する名前である。その種類の部品を別の回路の中へ一個置く記述を、インスタンス化と呼ぶ。置かれた一個には、識別するための名前も付く。

説明用の部品Adderを、一個calcという名前で置く例を考える。AdderにA、B、Sumという端子があるとき、`.A(left)`は「この部品のAという端子を、外側のleftという信号へつなぐ」と読む。端子名Aと接続する信号名leftが同じである必要はない。

```systemverilog
// Explanatory example, not the Wally top module.
Adder calc(.A(left), .B(right), .Sum(total));
```

![図L.1 ファイル内の部品と端子と接続する信号](figs/ports.png)

図L.1の枠の内側にあるA、B、Sumが部品の端子名で、枠の外のleft、right、totalが接続先である。この記述を読むと、数百行の最上位回路も「どの部品のどの端子へ、何をつなぐか」の集まりとして分けられる。端子を列挙する順番は、部品を時間順に動かす順序ではない。

IPという言葉は、このように再利用できる回路部品を指す場合に使う。本稿のMIGやClocking WizardはVivadoで生成するIPである。IPの設定を変えるTcl、生成されたIP、IPをつなぐSystemVerilogを別々に確認する。

### L.3 回路をFPGAへ入れるまで

回路のソースを、FPGAで使える論理部品の組合せへ変換する工程を合成と呼ぶ。次に、どの部品をFPGA内のどこへ置くかを決め、配線をつなぐ。これを配置配線と呼ぶ。最後に、その接続を設定するデータを生成する。このデータがビットストリームであり、通常は.bitという拡張子のファイルになる。

FPGAへビットストリームを書き込むと、その設定に従った回路が働く。回路を配置できても、必要な時間内に信号が届くとは限らない。そのため、配置配線後の時間解析も確認する。さらに、時間解析が成功しても、プログラムと回路の約束が一致しているかは別に確かめる。


図L.2では、設計ファイルから実機へ渡すまでを上下二段に分けた。

![図L.2 回路設定と実行ファイルを作る二つの経路](figs/build-paths.png)

上段の.bitファイルは、FPGAの中にどの回路を作るかを指定する。下段の実行ファイルは、その回路の中のCPUが順に実行する命令を持つ。青い箱はファイルを変換する道具、白い箱は入出力のファイルを表す。C++をコンパイルしただけでは、FPGAの回路設定は変わらない。逆に、回路を設定しただけではゲームの命令列は用意できない。

#### 同じビルドという言葉で二種類の生成を呼んでいる

ゲームのC++をコンパイルすると、Wallyが順に読み取る機械語命令ができる。CPUの配線はこの操作だけでは変わらない。回路のSystemVerilogをVivadoへ渡すと、FPGAの計算・記憶・配線を設定するデータができる。こちらはCPUや周辺回路そのものの構成を変える。

例えばボールの移動量を変えたい場合は、通常はゲームのソースを変更して実行ファイルを作り直す。一方、命令FIFOの容量を変えたい場合は回路の生成設定を変え、合成と配置配線を行い、FPGAへ新しいbitstreamを設定する。さらに、ソフトウェア側が容量に依存していればその設定もそろえる。

ソフトウェアだけ直したのに古い実行ファイルをSDカードから起動すると、修正は実機へ届かない。同じように回路ソースを直しただけでFPGAを書き換えなければ、動いている回路は以前のままである。再現手順でファイルのハッシュを照合するのは、編集したものと実行しているものを結び付けるためである。

### L.4 Linuxとゲームを準備する

Linuxを起動するには、OS本体、起動時に使うプログラム、ファイル群、実機の構成を説明するデータが必要になる。本研究ではWallyが用意するBuildrootの設定を利用した。Buildrootは、小さなLinuxシステムと、そのCPU向けの開発道具を生成する仕組みである。

ゲームを開発用パソコンでコンパイルするときも、実行先はWallyである。そのため、パソコン用のコンパイラではなく、RISC-V Linux向けのコンパイラを指定する。別の機械向けに実行ファイルを作ることをクロスコンパイルと呼ぶ。ビルドに成功したら、fileなどで実行ファイルの対象がRISC-Vであることを確認する。

### L.5 同じソースの版を使う

ソース管理のGitでは、ある時点の変更をコミットとして記録する。コミットには識別番号があり、その番号を指定すれば、後で更新が入っても同じ版を取得できる。初期版の再現演習はd3e181ac434a01a1f174549b5fbc7ee03a8875b4を基準とする[Console26]。更新版E6は未コミットのため、技術付録29.2節の親HEADと保存差分を使う。

サブモジュールは、別のリポジトリを特定の版で組み込む仕組みである。今回、addins/rasterixには公式RasterIXの9fdcf97a31b2e4247594e06d605871980cd5e9e1を固定した。親のリポジトリを取得しただけで中身がそろっていない場合があるので、サブモジュールも取得する。第14章でそのコマンドを示す。

版をそろえる理由は、同じファイル名でも中身が違えば、接続条件や実行結果が変わり得るからである。再現では、版番号、設定、生成したファイル、実行した入力を一緒に記録する。画像が似ていることだけで、同じ条件を使ったと判断しない。


### L.6 ソースを直したのに回路が変わらない理由

FPGAでは、画面上でソースを書き換えただけでは、基板の回路は変わらない。例えば、CPUのクロックを作るTclの数値を変えても、そのTclからIPを再生成し、回路全体を配置配線し、新しいbitstreamを書き込むまで、基板は以前の回路のまま動く。この途中にある「生成されたファイル」を把握することが、再現作業の出発点になる。

本構成では、編集する設定、生成された設定、実機へ渡すデータを分けて考える。`config/derivlist.txt`は人が編集する派生構成の記述であり、生成後の`config.vh`はその結果である。`fpga/generator/axiscdc.tcl`はFIFOの生成条件であり、`.xci`はVivadoが保存するIPの構成である。最終的な`.bit`はFPGAへ渡す回路設定であり、C++の実行ファイルとは別のものになる。[Console26]

![図L.3 編集するファイルから実機へ渡す二種類の成果物まで](figs/build-artifacts.png)

図L.3の上下二本の経路は、回路とアプリケーションを表す。上の経路だけを更新しても、アプリケーションが古いアドレスへ書き込めば動かない。下の経路だけを更新しても、FPGA内のレジスタ配置は変わらない。両経路が合流する場所が、実機上のバス接続である。

| 変更したもの | 作り直すもの | 実機で取り替えるもの |
|---|---|---|
| RTL、XDC、IP生成条件 | FPGA全体の生成物 | bitstream |
| C++、描画ライブラリのコンパイル設定 | ゲーム実行ファイル | SD上などの実行ファイル |
| デバイスツリーの予約領域 | dtb | SDの起動用dtb |
| CPUクロックと起動コードの定数 | IP、回路、起動コード、関連するdtb | bitstreamとdtbなど |

ここで、`CopiedFiles_do_not_add_to_repo`というフォルダ名にも意味がある。元ソースからビルドのためにコピーしたファイルを置く場所なので、そこだけ直しても、次の生成で元の内容へ戻り得る。変更を残す場所は元ソースであり、コピー先は生成結果を確認する場所である。修正が反映されない場合は、まず「編集した元ファイルが、今回の生成で読まれたか」を調べる。

### L.7 どのコードを自分が設計するのか

同じゲーム機を作れるという目標は、CPU、DDR3制御回路、描画器をすべて一から作ることとは異なる。本研究でも、それらの既存部品を利用した。その上で設計者が決めるのは、部品に渡すクロック、使うアドレス、命令の受け渡し方法、メモリの分け方、画面切り替えの完了条件である。

既存部品を使う場合でも、入口と出口の約束を説明する必要がある。例えば「命令を渡せる」という説明を具体化すると、32 bitのデータを渡すこと、最後の語に印を付けること、受け側が止まった間は同じデータを保つことになる。この約束を回路とソフトウェアの両方で満たすのが、接続を設計する仕事である。第7章と付録Gでは、この約束からコードを組み立てる。

### L.8 一つの変更を、編集から実機まで追う

「ボールを速くする」と「CPUのクロックを速くする」は、画面ではどちらも動きに関係しそうに見える。しかし、変える物が違う。ボールの移動量はゲームの計算で使う数であり、CPUクロックは回路を動かす信号である。最初に、どちらを変えたいかを決める。

ボールの移動量なら、まずBreakout.hppのゲーム規則を調べる。変更したC++をRISC-V用コンパイラで実行ファイルへ変換し、実機側のファイルと取り替えて起動する。FPGA内のCPUや描画回路は、同じ回路を使い続けられる。コンパイルするパソコンと、生成したファイルを実行するWallyは別のCPUなので、コンパイラの対象もRISC-Vにする。

CPUクロックなら、まずクロック生成用のTclと、それを使う回路を調べる。IPを再生成し、全回路の合成と配置配線を行い、時間条件を確認してから新しい.bitをFPGAへ渡す。CPUの周波数をソフトウェアへ伝える定数やデバイスツリーも一致させる必要がある。C++をコンパイルし直すだけでは、このクロック信号は変わらない。

![図L.4 同じ「変更」でも、実機へ渡す物が異なる二つの例](figs/change-delivery.png)

図L.4の上段と下段で、最後に取り替える物を確認する。上段はCPUが読むプログラム、下段はFPGAの回路設定である。実機が変わらないときは、最後の受け渡しまで進めたかを調べる。この図は変更の種類を示す例であり、周波数を上げても必ず動くという実験結果ではない。

ここからは、これまで説明した接続を同じ版のソースから生成し、実機で確認する順序を示す。コマンドの前に実行場所を確認し、後に何が出来たかを確認する。開発用Ubuntuでの成功、FPGAの設定成功、Wally上のLinux起動、ゲームの画像表示は、それぞれ別の段階である。前段が出来たことを確かめてから次へ進む。

### M.1 再現の二つの進め方

完成した構成を動かす場合は、本章の手順で固定した版を取得し、回路とソフトウェアを生成する。変更そのものを理解して再実装する場合は、付録Aと付属の「NexysVideo対応を変更前から再現する.md」を使う。後者は、対応前の版から12ファイルを順に変更する演習である。

完成形のクローンだけでは、どこを設計したかは分かりにくい。一方、最初から全差分を手で書くと、動作する基準を持てない。まず完成形のソースと生成物を確認し、その後、別の作業場所で変更を再現すると、誤った箇所を比べやすい。

以下のコマンドは、これから読者が再実行するための手順である。原稿作成時にFPGAを書き換えたりSDカードへ書き込んだりした、という記録ではない。保存済みの実機結果は第13章に区別して示した。

### M.3 固定したソースを取得する

実行場所は開発用Ubuntuである。新しい空のディレクトリへ取得し、現在使っている開発フォルダを上書きしない。次のwally-reproduceは、この説明で新しく作る作業用フォルダ名である。

```bash
mkdir -p "$HOME/projects"
cd "$HOME/projects"
git clone --recurse-submodules \
  https://github.com/SoshiroFujimori/wally-game-console.git \
  wally-reproduce
cd wally-reproduce
git checkout d3e181ac434a01a1f174549b5fbc7ee03a8875b4
git submodule update --init --recursive
```

cloneは親リポジトリを取得する。checkoutは本稿の版へ合わせる。submodule updateは、親が指定するRasterIXなどの版を取得する。初回のcloneが将来のmainを取っていても、checkout後のsubmodule updateで本稿の指定へそろえる。

次に版を確認する。長いハッシュ値は、その版を特定する識別子である。出力が違う場合は、そのまま「同じ構成」として先へ進まない。

```bash
git rev-parse HEAD
git -C addins/rasterix rev-parse HEAD
git status --short
git submodule status --recursive
```

最初の二行の期待値は8.1節の二つのハッシュである。git status --shortが何も出さなければ、追跡対象ファイルに変更がない。サブモジュールに先頭の+や-がある場合は、指定版との差や未初期化を調べる。

### M.4 開発用の道具を準備する

WALLYは、このリポジトリの場所を示す既存の環境変数である。独自の変数名へ置き換える必要はない。リポジトリの直下で次のように設定する。

```bash
export WALLY="$PWD"
```

まだWally用のツール群がない新規環境では、固定版のREADMEに従い、必要なパッケージとツール群を準備する。利用者権限でツールを入れる場合、既存手順は次の形である。

```bash
sudo "$WALLY/bin/wally-package-install.sh"
"$WALLY/bin/wally-tool-chain-install.sh"
source "$WALLY/setup.sh"
```

最初の行はUbuntuのパッケージを追加する操作である。二行目はコンパイラ、エミュレータ、Buildrootなどを生成する。時間と数十GBの空き領域を使うため、既存のツール群がある環境で無条件にやり直す手順ではない。三行目は、その端末で必要なパスや変数を設定する。[Console26]

この導入スクリプトが取得する外部プロジェクトには、ブランチ名による指定もある。親リポジトリの版を固定しただけで、後日生成される全ツールが同一になるとは限らない。再現記録には、Vivado、各コンパイラ、Buildrootのコミット、Linux設定を残す。保存済み数値との完全な再現性を論じるときは、ソースだけでなく道具の版も対象になる。

```bash
command -v vivado
riscv64-unknown-elf-gcc --version
command -v dtc
printf '%s\n' "$WALLY" "$RISCV"
```

ここでunknown-elfは主に起動用のプログラムなどに使う道具である。後でLinux上のゲームを作るときは、別のriscv64-buildroot-linux-gnu-g++を指定する。名前が似ていても、実行環境が違う。

### M.5 FPGAの回路を生成する

Vivadoのsettings64.shを、そのインストール場所から読み込む。保存した環境の例は次の通りである。別のパソコンではインストール先を実際の場所へ合わせる。

```bash
source "$HOME/AMD/2025.2/Vivado/settings64.sh"
cd "$WALLY/fpga/generator"
make nexysvideo-rasterix
```

nexysvideo-rasterixは、Nexys VideoとRasterIXを有効にする生成対象である。描画なしの基板対応だけを確認する場合はmake nexysvideoを使う。生成されるIPのフォルダは共有されるため、同じ作業場所で別の基板設定から切り替える場合は、既存READMEのcleanIPの説明も確認する。新規の再現用クローンでは、他の作業の生成物を消す必要はない。

生成の途中には、構成設定の展開、起動コードの生成、IP生成、合成、配置配線、bitstream生成がある。最後に文字端末がVivadoの入力待ちになる場合もある。単に処理が止まったように見えるだけで失敗と決めず、ログとrunの状態を確認する。

成功の判断は、.bitファイルが存在することだけでは足りない。wally.log内のERROR、配置配線の終了状態、reports以下の時間解析を確認する。生成途中の古い.bitを、今回成功したものと取り違えないよう、生成時刻とハッシュを記録する。

### M.6 実装レポートを保存する

VivadoでWallyFPGA.xprを開き、配置配線結果impl_1を開いた状態で、次のようなレポートを作る。report_timing_summaryは時間条件、report_utilizationは資源使用量、report_drcは設計規則の指摘を保存する。

```tcl
open_run impl_1
report_clocks -file reproduced-clocks.rpt
report_timing_summary -file reproduced-timing.rpt
report_utilization -hierarchical -file reproduced-use.rpt
report_drc -file reproduced-drc.rpt
report_cdc -file reproduced-cdc.rpt
```

CPU20 MHz、描画側100 MHz、画素25.2 MHzなど、意図したクロックが認識されているかを見る。時間余裕が負であれば、その生成物を成功扱いにしない。元のレポートと値が少し違う場合は、ツール版や生成条件を比較する。元の+0.170 nsを、再生成していない結果の欄へ写してはならない。

### M.7 Linuxとデバイスツリーを用意する

Wallyの導入手順でBuildrootが準備できたら、そのoutput/imagesにLinuxのImage、fw_jump.binなどがあるか確認する。新しくLinuxを生成する必要がある場合はlinux/README.mdに従う。既存のlinux/Makefileの既定処理には掃除や移動も含まれるため、既に使用しているBuildrootを無条件に上書きする操作として使わない。

RasterIX付き構成では、wally-nexysvideo-rasterix.dtsを使う。描画なし用のdtsでは画像領域の予約が一致しない。次は作業用ディレクトリへdtbを生成する例である。

```bash
mkdir -p "$HOME/wally-reproduce-output"
cd "$HOME/wally-reproduce-output"
dtc -I dts -O dtb \
  -i "$WALLY/linux/devicetree" \
  -o wally-nexysvideo-rasterix.dtb \
  "$WALLY/linux/devicetree/wally-nexysvideo-rasterix.dts"
```

dtsは人が読む設定、dtbは起動時に渡すバイナリ形式である。生成したdtbを逆変換して、メモリ容量とreserved-memoryを確認できる。32 MiBの予約領域が0x9e000000から始まること、CPU等のクロック値が20,000,000であることを、元のdtsと照らす。

### M.8 SDカードへ起動データを入れる

SDカードへの書き込みは、そのカードの内容を置き換える操作である。まずカードを挿す前後でlsblkを読み、容量と機種名で対象を特定する。本稿では、特定の/dev/sdbなどを正解として固定しない。パソコンによって番号が変わるためである。

```bash
lsblk -o NAME,SIZE,MODEL,TRAN,MOUNTPOINTS
```

対象カードが分かったら、必要な既存データを保存し、そのカード上のファイルシステムをアンマウントする。linux/sdcard/flash-sd.shへ、Buildrootの場所、生成したdtb、カード全体のデバイスを渡す。次は置き換える項目を示した書式であり、山括弧のまま実行するコマンドではない。

```text
sudo "$WALLY/linux/sdcard/flash-sd.sh" \
  -b <Buildrootの場所> \
  -d <wally-nexysvideo-rasterix.dtbの場所> <カード全体>
```

書き込み完了後に同期と取り外しを行い、Nexys VideoのmicroSDスロットへ入れる。操作補助としてSDWire3を使う場合も、共有先の切り替えは実験環境の手順であり、回路ソースへ専用処理を追加する理由にはならない。

### M.9 FPGAを書き込み、文字端末で起動を見る

基板を指定の電源で動かし、JP4はJTAG設定、VADJは標準の1.2 Vとする。USB PROGはJ12、UARTは別のJ13である。VivadoのHardware Managerで対象を開き、今回生成した.bitを指定してFPGAへ書き込む。[NexysVideo][Console26]

文字端末は115200 bpsで接続する。Ubuntu側でUARTの実デバイス名を確認してから使う。次の/dev/ttyUSB_UARTは、実際に検出した名前へ置き換えるための表記である。

```text
picocom -b 115200 /dev/ttyUSB_UART
```

CPU RESETを押すと、CPU側が再起動する。FPGA設定を消す操作とは区別する。端末に起動ログが出てLinuxのプロンプトへ到達するか確認する。何も出なければ、まず端子の取り違え、デバイス名、通信速度、書き込んだbitstreamを確認する。いきなり描画ライブラリを変更する段階ではない。

### M.10 ゲームをクロスコンパイルする

実行場所を開発用Ubuntuへ戻す。Buildrootのhost/binをPATHへ加える。次の例はRISCV配下の標準的な場所を使うため、実際の導入場所が異なる場合は合わせる。

```bash
export PATH="$RISCV/buildroot/output/host/bin:$PATH"
cd "$HOME/wally-reproduce-output"
cmake -S "$WALLY/examples/rasterix" -B rasterix-build \
  -DCMAKE_SYSTEM_NAME=Linux \
  -DCMAKE_SYSTEM_PROCESSOR=riscv64 \
  -DCMAKE_C_COMPILER=riscv64-buildroot-linux-gnu-gcc \
  -DCMAKE_CXX_COMPILER=riscv64-buildroot-linux-gnu-g++ \
  -DCMAKE_BUILD_TYPE=Release
cmake --build rasterix-build -j
file rasterix-build/rasterix-breakout
```

fileの結果がRISC-V向けELFになっていることを確認する。x86-64などと出た場合は、開発用パソコン向けに作っている。成功した実行ファイルはSDカードの実機から読める領域へコピーし、開発側と実機側でSHA-256を照合する。

ファイルの置き場所とマウント先はカードの構成に依存する。起動用の生データ領域へ、通常ファイルを直接書き込んではならない。実験で使用するフォルダをファイルシステム上に作り、そこへ実行ファイルと記録を置く。

### M.11 実機でゲームを動かす

実行場所はWally上のLinuxである。/dev/memを使える権限で、実行ファイルを置いたフォルダへ移る。まず識別値の不一致やタイムアウトが出ないかを見ながら、時間を区切って実行する。

```bash
./rasterix-breakout --demo --seconds 80
```

--demoは自動操作、--seconds 80は約80秒で終了する指定である。終了時にはscore、lives、frames、ticks、elapsedを含む行が出る。保存した基準実行では400点、残機3でクリアした。ただし、処理時間や完了数まで一文字単位で一致することを期待しない。

手動操作では引数を付けずに実行し、Aで左、Dで右、Sで停止、Spaceで開始、Rで再開始、Qで終了を使う。移動は押した方向へ継続する方式であり、キーを離した瞬間を受け取る方式ではない。Wiiコントローラーをつないだ試験としては扱わない。

### M.12 正しさの確認を段階的に行う

最初に文字端末の起動を確認し、次に描画回路の識別値、単色画像、ゲームの順に進める。単色で色がおかしい場合は、ゲームの当たり判定より先に、画素形式とアドレスを調べる。最終画像を読み戻して期待値と比べ、さらに映像として表示されることを確かめる。

専用の試験コードは、製品リポジトリの通常ソースへ混ぜず、付属の再現資料/試験と測定へ置く。APBの最小試験を再実行するスクリプトと、過去の測定ソース、設定、集計対象ファイルを添えた。試験のREADMEには、何を検査し、どこまでを合格と扱うかを記す。

### M.13 性能比較をやり直すときの順番

まず、測定プログラムの版と出力回路の構成を決める。次に、比較する描き方、場面、入力、準備30画面、測定180画面、反復三回を保存する。試行順も実行前に決め、途中で都合の良い試行だけを選び直さない。

各試行から、時間、命令量、状態列、最終画像を保存する。方式間で状態が同じか、最終画像が同じかを調べてから、時間を比較する。速くても画像が間違っている場合は、性能改善の成功として扱わない。三試行ごとの代表値とばらつきを求め、図表には出力回路の条件も書く。

今回付属させたE4の記録には、実験用HDMI構成の結果が含まれる。標準DVI構成で新たに比較する場合は、新しい実験番号を付け、同じ手順でも別の構成の結果として保存する。元のJSONやCSVへ新しい値を上書きしない。

### M.14 動かないとき、どこへ戻るか

| 症状 | 最初に確認するもの | 次に読む説明 |
|---|---|---|
| Vivadoが対象を見つけない | USB PROG、電源、JTAG設定 | M.9節、基板資料 |
| UARTに何も出ない | UART用USB、速度、bitstream | 6章、M.9節 |
| Linux起動で止まる | SDの起動データ、DTB、DDR3 | 6.6〜6.7節、M.7節 |
| 識別値が違う | RasterIX付き回路か、MMIO番地 | 7.1節、7.5節 |
| 命令転送が止まる | FIFO、リセット、応答経路 | 7.3〜7.4節、8.5節 |
| 画像は正しいが映らない | 表示の設定、映像形式、受信側 | 10.5〜10.7節 |
| 起動し直すと古い絵が出る | 内部領域と二枚の初期化 | 10.4節、11.8節 |
| 部分描画だけ残像が出る | 二枚分の履歴、重なる物体 | 11.5〜11.6節 |

症状だけから原因を断定するのではなく、表の確認で、どの段階まで正しいかを絞る。例えば映らない場合でも、画像を読み戻せれば「図形を描く段階までは動いた」と分かる。修正対象を小さくしてから変更する。

#### ログが出た場所から、動いている部分を一つずつ確定する

Vivadoで.bitを生成できた時点では、まだボード上でゲームが動いたとは言えない。そのファイルをFPGAへ書き込み、CPUが起動し、UARTから文字が届けば、少なくとも起動処理と文字の送信経路が進んだことが分かる。さらにLinuxのプロンプトまで来れば、Linuxが動き、端末から操作を受けられる段階にある。

ゲームを実行して識別レジスタを読めたら、CPUから描画回路の操作口への往復を確認できる。画像メモリを読み戻して期待する色が得られたら、描画命令からメモリへの保存を確認できる。映像として出たことは、その後に表示と映像経路で確認する。どこまで成功したかを分ければ、映像が出ないという一つの症状でも、先に調べる範囲を絞れる。

新しく作った実行ファイルを開発用Ubuntuで見つけても、実機のLinuxが同じファイルを使っているとは限らない。起動に使うSDカード上のコピー、実機側の実行パス、ファイルのハッシュを照合する。同様にFPGAへ書いた.bitも、今回生成したファイルと同じかを確認する。これは、古い生成物を動かしてからソースを直し続ける取り違えを防ぐためである。

### M.15 FPGAの書き込みからゲーム開始までの起動経路

「SDカードのゲームをCPUが実行する」を実装に結び付けるには、その前に何を実行しているかを見る必要がある。FPGAへbitstreamを書き込むと、CPU、メモリ制御回路、周辺回路と、起動用ROMの内容が用意される。CPUは最初からLinuxを実行できるわけではなく、まず小さな起動プログラムを実行する。

本リポジトリの`fpga/zsbl`がその起動コードである。`boot.c`はUARTを初期化し、SDカードを初期化して、`gpt_load_partitions`を呼ぶ。`gpt.c`はSD上の区画表を読み、デバイスツリー、OpenSBI、Linuxカーネルを、それぞれ指定したDDR3上の場所へコピーする。[Harris26][Console26]

![図M.2 回路の設定からLinux上のゲームが動くまで](figs/boot-stages.png)

OpenSBIは、RISC-Vの特権機能をLinuxへ提供するファームウェアである。Linuxはデバイスツリーを読み、この機械にあるメモリや周辺機器の配置を知る。その後、Linuxの環境からゲームの実行ファイルを起動する。ゲームの命令は必要に応じてメモリへ読み込まれ、CPUが実行する。「CPUがSD端子へ直接つながり、その場の命令を一語ずつ読む」という接続ではない。

| 段階 | 読むファイルまたは記述 | 確認すること |
|---|---|---|
| 起動ROMを作る | fpga/zsbl/Makefileとbios.S | 対象クロック、メモリ範囲、入口 |
| SDから読む | boot.c、gpt.c、sd.c | SD初期化、区画、コピー先 |
| Linuxへ機械情報を渡す | wally-nexysvideo-rasterix.dts | クロック、メモリ、予約領域 |
| Linuxアプリを作る | examples/rasterix/CMakeLists.txt | RISC-V Linux向けコンパイラ |
| 描画回路へ送る | WallyBusConnector.hpp | MMIOの基点とID |

起動しないときは、この順序のどこまで進んだかをUARTの表示で判断する。SDの読み出し中に止まる状態と、Linuxは起動するがRasterIXのIDが合わない状態では、調べる場所が違う。前者は起動経路、後者は描画用I/Oの構成を先に確認する。

### M.16 デバイスツリーの四つの数字を読む

RasterIXの予約領域の記述には、次の行がある。

```dts
reg = <0 0x9e000000 0 0x02000000>;
no-map;
```

この場所では、アドレスとサイズをそれぞれ二つの32 bitの値で表す。最初の二つが64 bitのアドレス、後ろの二つが64 bitのサイズである。上位がいずれも0なので、開始アドレスは0x9e000000、サイズは0x02000000、すなわち32 MiBになる。「四つの別々のメモリ」を表しているのではない。[Console26]

`reserved-memory`は、Linuxが通常のメモリ割り当てでこの領域を他の用途へ渡さないための記述である。`no-map`も指定している。しかし、この記述はFPGAにメモリ保護回路を追加するものではない。RasterIXへ誤ったアドレスを与えたときに、自動で予約範囲内へ丸めてくれるわけではない。

描画レジスタ側の`reg = <0 0x10080000 0 0x100>;`は、開始0x10080000、長さ256 byteを意味する。ソフトウェアのmmapはページ単位のため4096 byteを指定しているが、それによって4096 byteすべてにレジスタが増えるわけではない。この二つの長さの違いを区別する。

図M.3では、四つの数値を左の二個と右の二個に分けて読む。この構成はアドレスにも容量にも32 bitの値を二個ずつ使うため、先頭の0は不要な飾りではなく上位32 bitを表す。

![図M.3 reserved-memoryの先頭番地と容量を二組に分けて読む](figs/device-tree-reg-cells.png)

左の組は予約する先頭、右の組は予約する大きさである。右の0x02000000を十進数へ直すと33,554,432 byte、すなわち32 MiBになる。先頭番地と終端番地を二組で書いているわけではない。



### M.17 エラーを一つの部品へ絞っていく実例

例えば`RasterIX register ID does not match`が出た場合、最初に描画の頂点座標を直しても解決につながりにくい。まだ「この番地に期待する周辺回路がいるか」の確認で失敗しているためである。RasterIXを有効にしたbitstreamか、派生構成のEXT_IO_SUPPORTEDが1か、外部APBの基点がソフトウェアと一致するかを順に確認する。

一方、IDは合うが`RasterIX display swap timeout`が出る場合は、命令の受理だけでなく表示完了の経路を見る。CPUのFIFO書き込みが進むか、描画器が切り替えを要求するか、表示側が新アドレスから読むか、FrameCountが増えるかを分ける。回路中の信号を見る場合はシミュレーションやILAなどが必要であり、文字端末の出力だけですべての内部状態を断定しない。

| 観察した症状 | 最初に比較するもの | この段階で結論にしないこと |
|---|---|---|
| UARTに何も出ない | J12/J13、通信速度、reset、bitstream | GPUが遅いからだという推測 |
| IDが違う | FPGA構成、APBアドレス、IDレジスタ | OpenGLの図形指定の誤り |
| 描画の途中で停止 | FIFOの受理、応答待ち、共有DDR経路 | 容量不足とだけ決めること |
| 完了回数は増えるが映らない | 表示回路、出力時刻、映像受信条件 | 外部表示まで正常という判断 |
| 動くが以前の画像が残る | 二枚の履歴、初期化、完了待ち | 処理速度だけの問題 |

この表は診断の出発点であり、症状と原因を一対一に固定するものではない。一つ確認できたら、その観察で除外できた候補を減らし、次の経路へ進む。同じエラーのまま無関係な設定を多数変えると、何が効いたか分からなくなる。
